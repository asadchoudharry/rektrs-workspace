# Evaluation — SMS Gateway for Android (capcom6/android-sms-gateway)

**Date:** 2026-11-28 · **Evaluated for:** (1) Phone-as-portable-SMS-API goal, (2) Sendqon gateway-app line
**Sources:** GitHub repo + API (checked 2026-11-28), README, docs.sms-gate.app (API, Webhooks, Multi-SIM, Status Tracking, FAQ, Privacy Policy), sms-gate.app. Every claim below traces to one of these; where the docs are silent, that is stated.

## What it is

An open-source Android app ("SMSGate") that turns a smartphone into an SMS gateway: send/receive SMS (plus MMS and binary Data SMS) through a REST API, with webhooks for incoming messages and status events. Built in Kotlin with an on-device Ktor HTTP server; the companion cloud/private server is a separate open-source Go project (`android-sms-gateway/server`). Three operating modes share one API: **Local** (server on the phone), **Cloud** (their hosted server, `api.sms-gate.app`), **Private** (their server self-hosted in your own infrastructure). Repo stats at evaluation: **6,065 stars, 1,092 forks, 30 open issues**, created 2022-06, not archived. (GitHub API, 2026-11-28)

⚠️ Name caution: a different, commercial service exists at **sms-gateway.app** (Secuno LLC). It is **not** this project. The project evaluated here lives at **sms-gate.app** / `api.sms-gate.app`.

## API surface (same API in all three modes)

Base paths: Local `http(s)://<device-ip>:8080/…`; Cloud/Private `https://<server>/3rdparty/v1/…`. Interactive OpenAPI/Swagger is served by the device itself at `:8080/docs` and published online. Official client libraries exist for JS, Python, Go, PHP, Rust, plus a CLI (`smsgate`).

- **Send:** `POST /message` (local) / `POST /3rdparty/v1/messages` (cloud/private). Body: `textMessage.text` (or `mmsMessage` with Base64 attachments, or data-SMS payload), `phoneNumbers[]`, optional `simNumber`, `scheduleAt`, `withDeliveryReport` (default true), `priority` (≥100 bypasses working-hours), `deviceId` (target a specific device in cloud/private). Multipart long messages are auto-split. Pending messages can be cancelled (`DELETE /3rdparty/v1/messages/{id}`).
- **Status / history:** `GET /3rdparty/v1/messages/{id}` returns `id`, `state`, `states` (state→timestamp history), per-recipient states, `createdAt`. `GET /3rdparty/v1/messages` lists with filters `state`, `from`, `to`, `deviceId`, `limit` (1–100, default 50), `offset`, and an `X-Total-Count` header. Local mode exposes the same resources on-device.
- **Devices / SIMs:** `GET /3rdparty/v1/devices` (cloud/private) / `GET /device(s)` (local) — includes per-SIM `slotIndex`, `simNumber`, `carrierName`, `phoneNumber`, `iccid` (nullable without `READ_PHONE_STATE`), `lastSeen`, and the device's E2E `publicKey` when encryption is enabled.
- **Inbox:** received messages are readable via the same webhook mechanism plus an inbox/export API (`POST /messages/inbox/export`); historical export fires batch webhooks.
- **Webhooks:** registered per event via `POST /webhooks`, removed via `DELETE /webhooks/{id}`; local-mode and cloud/private-mode lists are independent; a webhook can be scoped to one `device_id`. **Events:** `sms:received`, `sms:batch:received`, `sms:sent`, `sms:delivered`, `sms:failed` (with `reason`), `sms:cancelled`, `sms:data-received`, `sms:batch:data-received`, `mms:received`, `mms:batch:received`, `mms:downloaded`, `mms:batch:downloaded`, `app:started` (carries the active SIM list), `system:ping` (heartbeat). **Envelope:** `{deviceId, event, id, webhookId, payload}`; payloads carry `messageId`, body/sender/recipient, `simNumber`, and a local timestamp. Batches hold at most 100 messages. **Delivery is from the device itself** (the phone POSTs to your URL), so the phone needs outbound internet and your endpoint must be reachable from it.
- **Webhook reliability & signing:** receiver must answer 2xx within **30 s** or the delivery retries with exponential backoff (10 s, 20 s, 40 s, …), **14 retries ≈ 2 days** by default (configurable). Every delivery is **HMAC-SHA256 signed**: headers `X-Signature` (hex) and `X-Timestamp`; signature = HMAC over `rawBody + timestamp` with a per-device signing key (viewable/rotatable in Settings → Webhooks). The app also has an in-app webhook-queue inspector (pending/failed/permanently-failed with last error). Docs recommend dedup on `deviceId` + envelope `id` (and warn explicitly that MMS `messageId`s are device-local counters — never dedup on them alone).
- **Auth:** HTTP **Basic auth** (username/password generated/shown in the app; local password ≥ 8 chars, cloud ≥ 14) and **JWT Bearer** with fine-grained scopes, revocation and TTL — docs recommend JWT for new integrations and call Basic "legacy". Same auth model in local and cloud/private modes.

## Modes & data flow

**Local mode.** The Ktor server runs on the phone (default port 8080); all data stays on the device; no account, no internet needed. Reachability is the catch, in the docs' own words: "Local Server API: Only accessible within your local network (same Wi-Fi/Ethernet)… External services like Google Apps Script, AWS Lambda, or other cloud functions **cannot** directly access Local Server API endpoints." The app displays a public IP too, but it "is only accessible if you have a public (or 'white') IP and your firewall is configured correctly" — a phone on Pakistani mobile data or NAT'd home Wi-Fi does not have one. So an internet-facing system can only reach local mode through a tunnel/VPN the phone joins (see recommendation).

**Cloud mode.** Device registers an account (sign-up needs **no email or personal data**; also sign-in or by-code pairing; registration is always explicit, never in background). Callers hit `api.sms-gate.app` from anywhere; the server wakes the phone via **FCM push**. What transits their servers, per the project's Privacy Policy: message content + recipient numbers in plaintext **unless** optional end-to-end encryption (AES/RSA-2048; content and numbers encrypted before the API call, decrypted only on the device) is enabled. Without E2E, plaintext is **SHA-256-hashed within 1 minute of processing** (policy updated 2025-03-17, tightened from 15 min), processed messages are **permanently deleted after 30 days**, inactive devices/accounts after **1 year**; SIM phone number/carrier/ICCID are redacted on-device to the last 4 characters before upload; FCM token and device make/model + app version are shared. Received messages in cloud mode are also uploaded to the server for centralised inbox access. Webhooks, however, are dispatched **directly from the device** to your endpoint in every mode — the README notes incoming messages therefore "remain inaccessible to us" on the webhook path.

**Private mode.** The same server, self-hosted (single-command Docker deployment per the site; Go + MariaDB). Message data never leaves your infrastructure; the only external touch is the wake-up push relayed through their cloud, which per the privacy policy contains **only the FCM token** — and the app offers an **SSE-only** option that uses no push at all. A self-hostable web dashboard (devices, messages, webhooks, API tokens) ships alongside.

## Android support & permissions

- **Minimum Android 5.0 (API 21)** — README prerequisites and `minSdk 21` in `app/build.gradle`. FAQ: "The SMSGate app **fully supports Android 15 (API level 35) and higher**", with two stated caveats: (1) on Android 15+, **Play Protect may block the sideloaded APK** because it isn't Play-distributed — the install guide gives a fallback flow and advises re-enabling Play Protect immediately after, downloading only from the official GitHub releases; (2) the **SMS permission may be greyed out** in Settings on Android 15+ and must be granted via a manual route (their guide; community reports in issue #280). (The repo's checked-in `build.gradle` still shows compile/target SDK 33 — evidently lagging the shipped builds; the FAQ statement is the operative one for the released APK.)
- **Permissions:** `SEND_SMS` is the only hard requirement. `READ_PHONE_STATE` is optional but **required to select a SIM**; `RECEIVE_SMS` for incoming-SMS webhooks; `READ_SMS` for reading history; `RECEIVE_MMS`/`RECEIVE_WAP_PUSH` for MMS webhooks.
- **Default-SMS-app:** the project **deliberately does not** become the default SMS app ("we intentionally avoid implementing this to prevent misuse and maintain transparency") — consequence stated in the FAQ: gateway messages remain visible in the phone's stock messaging app. One exception: for **reliable MMS sending** on most carriers the app should be set as default SMS app (README note). No default-app requirement exists for plain SMS send/receive.
- **Background behaviour:** foreground service + wake lock in local mode; battery-optimisation exemption is offered in Settings and recommended; cloud mode leans on FCM and can see delays at high rates under power saving (FAQ). Manifest-declared receivers keep capturing SMS/MMS even if the system kills the app process.

## Dual-SIM handling

Yes — per-message SIM selection is a first-class API feature. SIMs are identified by **`simNumber`, 1-based** (slot 1, slot 2), with `slotIndex` 0-based in device info. Send with `"simNumber": 2` to force SIM 2; every webhook payload also reports the `simNumber` actually used. When `simNumber` is omitted, an in-app setting decides: **OS Default** (delegate to the default messaging app), **Round Robin**, or **Random**. `GET /devices` exposes each SIM's carrier/number/ICCID (subject to permission; redacted to last 4 chars when a cloud/private server is in the path).

## Delivery-status reporting

States: **Pending → Processed → Sent → Delivered**, with **Failed** (terminal, carries a reason) and **Cancelled** branches (full state diagram in the Status Tracking doc). Two channels, both complete: **push** — `sms:sent` / `sms:delivered` / `sms:failed` / `sms:cancelled` webhooks; **pull** — `GET /messages/{id}` (includes per-recipient states and a state-history map) and filtered `GET /messages` lists. Multipart nuance (documented): `sms:sent` fires once after all parts, `sms:delivered` fires **once per part**, `sms:failed` fires if any part fails — handlers should group by `messageId`. Delivery reports are on by default and can be disabled per message (`withDeliveryReport: false`). MMS has no delivery receipts on Android: `sms:sent` is its terminal success state.

## Stated limits & warnings (their words, faithfully)

- README, verbatim in substance: "**It is not recommended to use this for batch sending due to potential mobile operator restrictions.**"
- The FAQ's operator-restriction section is a mitigation toolkit, not a promise: configurable **random delay between messages**, **send limits per period** (minute/hour/day — queue pauses at the cap; docs caution against using limits for time-sensitive OTP traffic), **SIM rotation**, and **working-hours windows** (priority ≥ 100 bypasses).
- No numeric throughput figure is published anywhere in the docs — **docs silent** on messages/minute guarantees. The only hard numbers are webhook-side (30 s response, ~2 days of retries) and list pagination (≤100).
- Sender ID: messages go out under the SIM's own number; alphanumeric sender IDs are a carrier product, not an app feature (FAQ). RCS is **not supported** (no public Google API) and they recommend disabling RCS in Google Messages to avoid issues.
- Cloud mode is free "unless message volumes impact other users" (author's write-up) — i.e., the free cloud is fair-use, not a volume contract.

## Security model (local server focus)

- Every API call is authenticated (Basic or scoped JWT); credentials are generated on-device and shown in the app; passwords are changeable in Settings.
- Transport: the **release build is TLS-only** (cleartext permitted only to `127.0.0.1`); the separate **insecure build** allows cleartext and is explicitly "never to be used in public environments". For private-IP HTTPS the project runs its own **Certificate Authority** tooling to issue trusted certs for LAN addresses. Webhook targets must be HTTPS (only `http://127.0.0.1` exempted).
- Residual risks are the obvious ones and the docs don't hide them: anyone who reaches port 8080 **and** holds the credentials owns the SIMs — so the port must never be exposed to the open internet (no port-forwarding); Basic auth sends credentials on every request, so prefer JWT over any path you don't fully control; webhook endpoints should verify the HMAC signature (their guidance: constant-time compare, ±5 min timestamp window, dedup). Optional E2E encryption (RSA-2048 key per device, fingerprint verifiable out-of-band via `GET /devices`) removes the server — including a private one — from the trust path for content and numbers.

## Comparison with our own Sendqon gateway app

Our app (v5.5.0, `com.rektrs.sendqon`) is a **panel-paired tenant device**: it speaks Sendqon's own protocol, carries per-SIM balance checks with a carrier-reply parser, a USSD engine, SIM enable/disable sync with the panel, panel-driven auto-update, and Sendqon's branding/UX. capcom6's app is a **standalone, protocol-open gateway**: standard REST + signed webhooks + JWT, multi-device/private-server modes, MMS/Data SMS — but no Sendqon panel pairing, no tenant model, no balance/USSD features, no SIM-management sync with our panel. They solve different layers and can coexist on the same phone (different packages).

## Recommendation

### (a) Phone-as-portable-SMS-API goal — **GO**, in Private mode (Local+Tailscale as the zero-server fallback)

This repo is the goal's premise, already built, Apache-2.0, and maintained weekly. Building our own equivalent for *this* goal would be re-inventing it. Concretely:

1. **Server:** deploy the open-source SMSGate **private server** (Docker, single command) on **offbox-1** next to the existing ServerKit stack, behind Caddy at e.g. `smsgate.rektrs.com`. Callers then use `POST https://smsgate.rektrs.com/3rdparty/v1/messages` with JWT auth — an ordinary internet HTTPS call, so **IQRS on shared Hostinger, Operqon, and any future tool can all call it** without agents or tunnels on their side.
2. **Phone side:** install the official **release** APK on the owner's phone (it coexists with our Sendqon app), register it to the private server, grant `SEND_SMS` + `READ_PHONE_STATE` (SIM choice) + `RECEIVE_SMS` (inbound webhooks), exempt it from battery optimisation. The phone needs only **outbound** internet — wake-up arrives via the FCM relay (token-only) or SSE-only mode; no inbound reachability, no port-forwarding, no public IP needed. **What stays on-device:** the SIMs and sending itself, the message store, and (with E2E enabled) plaintext — the server holds only queue/state, and it's *our* server.
3. **Inbound:** register webhooks `sms:received` (+ `sms:delivered`/`sms:failed` for status) to an HTTPS endpoint on offbox-1; verify `X-Signature` HMAC, dedup on `deviceId` + envelope `id`; route into whichever Rektrs system consumes replies.
4. **Fallback / no-server variant:** Local mode + **Tailscale** (the route we already operate): phone and offbox-1 on the tailnet, callers reach `https://<phone-tailnet-ip>:8080/message` — data never leaves our devices at all, but only tailnet members can call it, so internet systems must relay through offbox-1. Prefer Private mode as primary; keep this as the contingency.
5. **Not recommended:** their **Cloud mode** for Rektrs traffic — it's free and E2E exists, but it puts a third party in the path (even if only as hashed-after-1-minute storage) for zero benefit over a private server we can run ourselves.
6. **Volume honesty:** per the project's own warning, this is a transactional/OTP/reminder channel (our actual use: IQRS notifications, OTPs, alerts), **not** a bulk/marketing pipe; keep the in-app per-period limits and random delay on to stay inside carrier tolerance, and pick the SIM per message via `simNumber` (1 = Zong, 2 = Ufone on the owner's phone).

### (b) Sendqon proper — one-line verdict

**No change: Sendqon's own gateway app stays the tenant device (panel pairing, balance/USSD, SIM sync are ours alone); capcom6's app is adopted only as the engine for the separate phone-as-API goal, never as a Sendqon replacement.**
