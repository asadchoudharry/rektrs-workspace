## Item 1 — AI Flow Builder (ai_integration) — ✅ BUILT + LIVE (tenant access plan-gated off)

- **What:** Core carries the whole gate + HTTP surface (`FlowAiController`, `AiFlowBuilderAccess`, plan flags `flows` + `ai_flow_generation`, the `ai-flow-generation` rate limiter, the editor's AI panel + draft notice UI). The plugin supplies the one class core resolves by name — `App\Plugins\AiIntegrations\AiFlowBuilder\FlowBuilder` implementing core's `FlowAiBuilder` contract (`generate` / `draftInto` / `editTurn`) — plus a plugin-owned edit-history table. The prompt's node catalogue is generated from core's **live** `NodeTypeCatalog` (72 types), so prompt and validator can never drift. Drafts are normalised (catalogue defaults filled, ids sanitised, layout assigned, edges checked against real output handles; `tag_names`/`group_names` resolved to workspace ids exactly like core's own template builder — tags firstOrCreate, groups never invented), then engine-validated with core's `FlowValidator` + network-permission check **inside the gateway's charge transaction**: an invalid draft throws, the charge is refunded, nothing is saved; the validator's errors feed one repair attempt (plugin config, default on). All AI calls go through `AiGateway::complete()` (feature `flow_generation`, idempotency key per request — a repeat of a succeeded request is refused as `duplicate`; a failed attempt never claims the key). Generated flows are created **inactive**; `draftInto` fills an empty inactive flow under an optimistic version check (fail-fast before any AI call); `editTurn` returns the editor's exact proposal shape (`reply`/`proposal`/`diff`/`to_fill`/`not_done`/`tags_created`) and saves nothing. Ready-made templates: core already ships 16 in the New Flow gallery — the builder's prompt steers common requests to those shapes rather than duplicating a template store.
- **No-key test strategy:** dev-only platform provider row (OpenAI type, dummy key, feature price `flow_generation` = 7 credits against a flat 5) + `Http::fake()` at the provider wire returning scripted chat completions (invalid canvas → valid canvas → garbage). The full logic — access gate, generation, repair, duplicate, refund, draft fill, edit proposal, test run — is exercised end to end; only the real provider call is faked.
- **Dev battery: 44/44 PASS** — access (`enabledFor`, props credits = 7.0 feature price, Free plan refused); generate-with-repair (flow created inactive, `trigger_type` derived, `validation_errors` empty, draft notice with `placeholder_text` to_fill, history row; **exactly one charged success at 7 credits, the failed attempt refunded to 0, ledger balance 100 → 93, provider called exactly twice**); duplicate request refused with reason `duplicate`, no second flow, no charge; always-invalid output refused with both attempts refunded and no flow; draftInto wrong-version refused **before any AI call**, correct version fills + bumps version, non-empty flow refused; editTurn returns the editor's exact key set, diff counts the 2 added steps, `tags_created` = [VIP], the stored flow is byte-unchanged, 7 more credits charged; **the generated flow runs in core's FlowTestRunner** (dry-run report, no error, `send.reply` step executed); rollback rehearsed (deactivate → access dark; uninstall → table dropped; reinstall → active). The battery caught two real plugin bugs pre-production: tag steps validate on `tag_ids` (names now resolved in the factory), and the idempotency key must be per-request, not per-attempt (a per-attempt key let a duplicate slip past a repaired success).
- **Production:** fresh backup first (status=OK, push=OK) → installed via `PluginManager::installFromZip` + activate — **active, v1.0.0**. Live-safe checks: `installed()` + `installEnabled()` true, history table present (0 rows), site + /login 200, users still 1, **all 7 plans still `ai_flow_generation=false`** (no tenant can use it until the owner's pricing decision — by design). Baked into `~/sendqon-build/src/app/Plugins/AiIntegrations/AiFlowBuilder/`.
- **Pending:** **PENDING-BYOK** — live generation needs an AI provider (Admin → AI Providers, platform key or tenant BYOK on enabled plans) AND the owner's plan-flag decision (`ai_flow_generation` per plan). First live generation verifies end to end at that point; the identical flow is proven in dev.

## Item 2 — Knowledge Base (ai_integration) — ✅ BUILT; production installed INACTIVE + unconfigured (correct end-state, activation awaits a provider)

- **What:** The knowledge machinery is core's — `knowledge_*` tables, ingestion (parse → chunk at 2,048 tokens with overlap → embed → index) on the `knowledge` queue, `knowledge:refresh`/`retry`/`prune`, tenant controllers, quota ledger and the ranked search (cosine ≥ 0.275 + keyword fusion, source citations). The plugin is the activation + configuration layer core's `KnowledgeBaseAccess` gates on, and its Configure flow is a **real verification**: saving runs one unmetered probe embedding through core's `AiGateway` against the first usable embeddings provider and stores the fingerprint (`verified_hash` + `verified_at`, core's `KnowledgeBaseSettings` contract) that core re-checks on every read. Activation is refused until a verified config exists — the app's own rule, and the same "Configuration required" state the vendor's $59 plugin ships in. Providers and keys live only in core (Admin → AI Providers); embeddings are billed per 1k tokens through the shared AI wallet; storage stays in the app's own DB/storage (no external services). If the provider key is later replaced, core's provider screen re-proves this configuration automatically.

## Item 3 — AI Agents (ai_integration) — ✅ BUILT + LIVE (tenant access plan-gated off)

- **What:** Core carries the gates and surfaces — `AiAgentsAccess` (plan features `flows` + `ai_agents`), the whole `/ai-agents` screen set (its frontend types define the agent shape exactly: template, routing description, instructions, model, memory window, knowledge bases, channels, the Actions/Handover settings, HTTP actions, activity feed), the Messenger runtime contract, the mobile pause/resume actions and the dedicated `ai-agents` queue. The plugin supplies everything behind them: agent definitions + per-conversation state + turn audit (plugin tables), a runtime that binds over core's `NullAiAgentsRuntime`, the router, the tool-calling turn loop, the flow nodes (`AiAgentNodes`: catalogue entries, executors, validation, editor options), and the controllers the screens call (CRUD, HTTP-action CRUD + test, activity).
- **Behaviour:** a message no flow answered is dispatched to the `ai-agents` queue; the agent is sticky per conversation, or routed by description (feature `ai_agent_router`) when several are eligible; the turn runs on core's `AiGateway::turn()` (feature `ai_agent`) with tools built **strictly from the agent's Actions settings** — reply, knowledge search over its attached bases, handover, labels, tags, priority, contact fields, notes, resolve, transfer, and its own HTTP actions. When no agent is eligible, the runtime itself fires flows on the `inbound_unanswered` trigger. If an agent turn ends without any agent engaging, nothing is sent and nothing is charged beyond the gateway's own metering.
- **Safety gates (MCP-class, all battery-proven):** the AI never engages in group chats, never once a human is assigned, and stops the instant a human replies or is assigned (`humanTookOver`); pause/resume from the inbox/mobile is honoured before every turn; sends go only through core's `AutomatedMessageSender`, so plan routes and the **WhatsApp 24-hour window** are enforced by core and a refusal is recorded, never bypassed; label/tag/contact-field tools enforce their **id/key allow-lists** (an unlisted label was refused in the battery); HTTP actions marked "requires confirmation" refuse until the customer confirms, and their responses are filtered to the configured visible fields (a `secret` field in the test response never reached the model); **three consecutive failed turns hand the conversation to a human automatically**; there is no campaign tool at all — an agent cannot launch one; every turn is audited (outcome, actions taken, credits, latency, error).
- **No-key test strategy:** dev-only provider priced for both features (`ai_agent` 9, `ai_agent_router` 3) + `Http::fake()` at the provider wire returning scripted tool calls (reply / search / label / priority / HTTP / handover sequences, including the confirmation two-step). The send boundary is core's `AutomatedMessageSender` — the battery substitutes a recording double for it (its contract: null = queued, string = refusal) and separately relies on core's own refusal semantics; everything else — routing, turn loop, tools, state machine, flow nodes, charging — runs on the real code. The battery also caught and fixed real issues pre-production: the loop now stops after a successful reply instead of asking for a wrap-up round (an empty final round is a provider error in core's client), and label handling follows core's `ConversationLabel` model.
- **Dev battery: 45/45 PASS** — pre-install dark (catalogue clean, access closed); install → runtime binding swaps, tables created, both node types enter the catalogue, node validation + editor options work; a full reply turn (router 3 + turn 9 charged exactly, ledger-exact); plain-text and reply-tool paths both send; knowledge-grounded turn (search then answer, from Item 2's FAQ base); label allow-list enforced both ways; priority set; HTTP action executed with visible-fields filtering; confirmation-gated action completes only after the confirm step; handover sends the configured message, sets state, and the agent stays silent afterwards; router picks the sales agent for a buying message; pause blocks turns, resume restores, `present`/`presentMany`/`constrainHandling`/`settings` all behave; `unanswered()` dispatches the job onto the `ai-agents` queue; a channel no agent covers fires the `inbound_unanswered` flow; the flow step dry-runs with zero AI usage and really executes on a live run (branch `replied`); rollback rehearsed (deactivate → not owned; uninstall → tables dropped; reinstall works).
- **Production:** fresh backup first (status=OK, push=OK) → installed via `PluginManager::installFromZip` + activate — **active, v1.0.0**. Fresh-process verification: `AiAgentsRuntime` resolves to the plugin's runtime service, `installed()` + `installEnabled()` true, all 4 tables present, both node types in the runtime catalogue, `/ai-agents` routes registered (index/show/http-action test), site + /login 200, users still 1, **all 7 plans still `ai_agents=false`** (no tenant can use it until the owner's pricing decision — by design). Baked into `~/sendqon-build/src/app/Plugins/AiIntegrations/AiAgents/`.
- **Pending:** **PENDING-BYOK** — live agent turns need an AI provider (Admin → AI Providers, platform key or tenant BYOK on enabled plans) with prices for the `ai_agent` / `ai_agent_router` features, AND the owner's plan-flag decision (`ai_agents` per plan). First live conversation verifies end to end at that point; the identical machinery is proven in dev. One scope note: channel options in the agent editor are offered per channel (all connections); pinning an agent to specific connections is stored and honoured by the runtime's matcher, and the editor's connection-level picker can be deepened when the owner first uses it.
