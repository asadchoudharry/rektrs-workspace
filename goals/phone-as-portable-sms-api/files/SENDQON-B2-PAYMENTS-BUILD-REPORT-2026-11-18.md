## Item 1 — JazzCash (payment_gateway) — ✅ BUILT + LIVE (unconfigured)

- **What:** Hosted page-redirection checkout per JazzCash's public merchant guide. Signing = all `pp_*` fields except `pp_SecureHash`, sorted by field name (ASCII), values joined `&`, Integrity Salt prepended, HMAC-SHA256 with the salt as key (uppercase hex); `pp_Amount` in paisa. Merchant password is deliberately **not** sent in the redirect (SecureHash is the proof; a password in a URL leaks) — it stays server-side. Settlement converges from the browser return (`/payment/callback?gateway=jazzcash`) and the server-to-server IPN (`POST /api/payment-gateways/jazzcash/webhook`), both hash-verified, one idempotent settle path (Subscription + Transaction `createOrFirst`, user-row lock, activation after commit). Amount/currency mismatch → transaction flagged `needs_manual_refund`, plan NOT activated. `ppmpf_1..5` carry user/plan/kind/install-tag/purchase-ref. Supports monthly/yearly/lifetime (one charge per period), one-time purchases (credit packs/orders) via core's `OneTimePurchaseService`, and the setup-fee contract. No auto-renewal (JazzCash issues no reusable token on this flow). Config: Merchant ID, password (sensitive), Integrity Salt (sensitive), txn type, sandbox toggle + readonly IPN URL.
- **Dev battery: 30/30 PASS** — including the signing implementation matching **JazzCash's own published test vector byte-for-byte** (salt `3vv9wu3a18` example → `2C595361…B117`), checkout URL shape (sandbox host, paisa amount, no password in URL, hash self-verifies), valid simulated IPN → subscription ACTIVE + transaction completed + plan assigned, duplicate IPN → core `already_processed` with exactly 1 transaction/subscription, tampered IPN → 400 with zero state change, correctly-signed wrong-amount IPN → recorded + `needs_manual_refund` + no activation, one-time purchase IPN → completed, empty config → `isConfigured()` false + checkout throws, uninstall (after clearing battery subscriptions — core guards uninstalls with live subscriptions) → webhook 404, reinstall → active.
- **Production:** fresh backup first (status=OK, push=OK). Installed via `PluginManager::installFromZip` — **status=inactive, config empty** (activation is refused by the app until configured; owner activates after entering merchant credentials). Live-safe checks: site 200, /login 200, inactive-gateway webhook 404, all containers Up. Baked into host build tree `~/sendqon-build/src/app/Plugins/PaymentGateways/JazzCash/`.
- **Pending:** **PENDING-MERCHANT-ACCOUNT** — no JazzCash merchant account exists yet. Owner step: obtain JazzCash merchant credentials → Admin → Plugins → JazzCash → Configure (Merchant ID / Password / Integrity Salt) → set the IPN URL in the JazzCash portal → Activate → first live/sandbox charge verifies end-to-end.
- **Pushes:** source → Sendqon `plugin-jazzcash` (see hash line appended at push time below); this report → Sendqon `rebuild-tree` + rektrs-workspace `main`.

## Item 2 — EasyPaisa (payment_gateway) — ✅ BUILT + LIVE (unconfigured)

- **What:** Easypay hosted checkout (`Index.jsf`, GET redirect — a documented initiation pattern). Request hash per the Easypay merchant guide: all parameters as `key=value` joined `&` in alphabetical key order, AES-encrypted with the store Hash Key (ECB, PKCS padding), base64 → `merchantHashedReq`. Amounts PKR 2-decimals; order refs ≤20 alphanumeric. **Trust model:** Easypay's browser return (`status`/`desc`/`orderRefNumber`) is unsigned, so it is never trusted — the return (and the optional IPN) only triggers Easypay's documented **Inquire Transaction Status API** (`POST /inquire-transaction`, `{orderId, storeId, accountNum}`, base64 `Credentials` header). Settlement requires inquiry `transactionStatus=PAID` + exact amount; mismatch → `needs_manual_refund`, no activation; inquiry unreachable → nothing settles. Checkout creates the pending subscription/transaction up front keyed by the order ref (duplicates converge). Config: Store ID, Hash Key (sensitive, 16/24/32-byte AES), EWP Account Number, API username + password (sensitive), optional API base override, sandbox toggle + readonly IPN URL. Supports monthly/yearly/lifetime, one-time purchases, setup fee; no auto-renewal.
- **Dev battery: 26/26 PASS** — including `merchantHashedReq` matching an **independent OpenSSL CLI AES-128-ECB computation byte-for-byte**, pending records at checkout, verified return → ACTIVE, duplicate return idempotent, **forged "Success" return with FAILED inquiry → no settlement**, PAID-but-wrong-amount → manual-refund hold, IPN → same inquiry-verified settlement for a one-time purchase, empty config → checkout refuses, bad AES key length rejected by `validateConfig`, uninstall → webhook 404, reinstall → active. (Inquiry API faked at the HTTP layer with `Http::fake` — the verification logic is fully exercised; only the real endpoint/credentials are pending.)
- **Production:** fresh backup (status=OK, push=OK) → installed via PluginManager — **status=inactive, config empty**. Site + /login 200. Baked into `~/sendqon-build/src/app/Plugins/PaymentGateways/EasyPaisa/`.
- **Pending:** **PENDING-MERCHANT-ACCOUNT** — owner step: Easypaisa merchant onboarding → Configure (Store ID / Hash Key / EWP Account # / API credentials) → Activate → first sandbox charge. At onboarding, confirm with Easypaisa: the exact inquiry API base URL for the store (an override field is provided) and that the hosted flow's `autoRedirect` handshake matches the store's enabled integration type.
- **Pushes:** source → Sendqon `plugin-easypaisa`; report → Sendqon `rebuild-tree` + rektrs-workspace `main` (hashes in the lane's final summary).
