# Study — Evolution API (evolution-foundation/evolution-api)

**Date:** 2026-11-28 · **Studied for:** Sendqon WhatsApp provider options — should Evolution API become a Sendqon WhatsApp provider, and should it replace our own B8 Baileys bridge?
**Sources:** GitHub repo + releases + issues (checked 2026-11-28), repo `LICENSE` / `TRADEMARKS.md` / `.env.example` verbatim, Evolution Foundation licensing docs (docs.evolutionfoundation.com.br/licensing), project README, plus clearly-marked secondary sources (Swarmhit's 2026-11-24 repo read, Railway deploy-template notes, Codex Labs / RunXBuild comparisons). Every claim below traces to one of these; where the docs are silent, that is stated. READ-ONLY study — nothing was installed or deployed.

## What it is

A self-hosted, open-source REST API for WhatsApp: a TypeScript/Node.js 20+ server (Express + Prisma) that holds WhatsApp sessions open and exposes them as HTTP endpoints with webhooks. Each connected number is an **instance**. An instance picks one integration:

- **`WHATSAPP-BAILEYS`** — the number linked as a WhatsApp Web device via the Baileys library (QR code or pairing code). Free, unofficial.
- **`WHATSAPP-BUSINESS`** — Meta's official WhatsApp Cloud API (verified business, app, phone-number ID; Meta's per-message fees and template rules apply).
- **`EVOLUTION`** — a passive webhook-in channel (no WhatsApp connection of its own).

Repo stats at study time: **10,219 stars, 7,484 forks, 171 open issues**, 2,635 commits, 55 releases, created 2023-06-09, not archived (GitHub, 2026-11-28). Docker image: `evoapicloud/evolution-api`. The project began as a fork-lineage of CodeChat, itself a Baileys implementation (README acknowledgements). Alongside the API, the foundation maintains **Evolution Go** (a separate Go/whatsmeow engine, created March 2026, positioned as the high-performance option) and Evo CRM, which uses Evolution API as its WhatsApp provider.

## Licence — read this section carefully

The repo `LICENSE` file is the **Apache License 2.0 text with two additional conditions prepended**. GitHub's licence detection consequently reports the repo as **"Other (NOASSERTION)"**, not Apache-2.0. The two conditions, in the file's own words:

1. **LOGO and copyright preservation (frontend only).** "In the process of using Evolution API's frontend components, you may not remove or modify the LOGO or copyright information in the Evolution API console or applications. This restriction is inapplicable to uses of Evolution API that do not involve its frontend components."
2. **Usage Notification Requirement (applies to every use, including closed-source).** "If Evolution API is used as part of any project, including closed-source systems (e.g. proprietary software), the user is required to display a clear notification within the system that Evolution API is being utilized. This notification should be visible to system administrators and accessible from the system's documentation or settings page."

The sanction for missing either condition is the same sentence structure: should the conditions not be met, **"a commercial license must be obtained from the producer"** — i.e. non-compliance converts the deployment into one needing a paid commercial licence, at the producer's determination. **No commercial-licence price is published anywhere we could find — docs silent.** Licensing contact: suporte@evofoundation.com.br.

`TRADEMARKS.md` (v1.0, 2026-05-06) adds a brand-assets policy on top: "Evolution Foundation", "Evolution" and "Evolution API" are the foundation's trademarks. If you distribute or publicly host a UI carrying their brand assets, you may not remove/replace/modify **any** Protected Visual Identity Element (names, logo/wordmark, the © line, even the official colour palette and radius). If you modify the UI/branding, you must instead strip **all** Evolution marks and use a clearly distinct name. Nominative use ("based on Evolution API") is permitted if accurate and non-endorsing.

### The 2.4 line adds mandatory licence *activation* (separate from the licence text)

Release **2.4.0 (2026-05-06)** introduced a hard runtime gate, in its own release notes: "⚠️ BREAKING CHANGE — License activation is now required. Starting with v2.4.0, every Evolution API instance must be activated against the Evolution Foundation licensing server before serving API traffic." Until activation, business endpoints return `503 LICENSE_REQUIRED`; the gate uses a hardware-based instance ID and a **fire-and-forget heartbeat every 30 minutes**, with deactivation on shutdown. The foundation's licensing docs state the activation is **free** (tier `community`: no instance/message limits, no feature blocks, "no charge at any time"), and that activation collects the operator's **email and phone number**, product version and a locally generated instance UUID; heartbeats then send the version, **aggregate usage counters (e.g. total messages sent in the period)**, the enabled-features list, and the **server IP**. The docs are explicit that message content, contacts, numbers and credentials are **not** collected. The older **2.3.x line has no activation** (confirmed for 2.3.7/2.3.8), which is why current third-party deploy templates pin 2.3.8 and note "newer images need a license activation".

Two honesty notes: (a) the foundation's licensing page claims the code "continues Apache 2.0, **without additional clauses**" and calls activation a Manager-functionality requirement rather than a licence restriction — that contradicts the repo's own `LICENSE` file, which does carry the two additional conditions quoted above. The `LICENSE` file in the repo is the operative document; the web page is marketing-adjacent. (b) Telemetry also exists independently of activation: `.env.example` ships `TELEMETRY_ENABLED=true` (routes used, version — README describes it as anonymous, no personal data), so even a 2.3.x deployment phones home unless the operator turns it off.

### What this means for Rektrs / Sendqon white-label SaaS use

- **Backend-only use is the clean path.** If Evolution ran purely as an engine behind Sendqon's own panel (its Manager UI never exposed to tenants), condition 1 (logo) does not bite — it expressly applies only to uses involving the frontend components. Condition 2 still applies in full: Sendqon would have to show administrators a clear "Evolution API is utilized" notice (admin settings/docs page). That is a small, one-time compliance item — but it is the opposite of invisible white-labelling, and forgetting it technically puts the deployment in commercial-licence territory at the producer's discretion.
- **Exposing the Evolution Manager to tenants is effectively barred** under a Sendqon brand: the Manager is a frontend component, so its logo/copyright (and, per TRADEMARKS.md, its whole visual identity) must stay — tenants would see Evolution branding, not Sendqon's. Rebranding it requires stripping every mark, and the LICENSE's logo clause still only relaxes for non-frontend use, so a rebranded Manager fork sits in a grey zone we should not build a product on without written permission.
- **On the 2.4 line, every Sendqon host would register with the foundation** (operator email + phone per deployment) and heartbeat usage counters + server IP every 30 minutes. For a multi-tenant SaaS that is a standing third-party data flow about our aggregate traffic — disclosed by them, but ours to accept deliberately, not discover later.
- Standard Apache-2.0 duties (licence text, change notices, NOTICE attributions — the repo does ship a `NOTICE` file) apply underneath all of this.

## Architecture

- **Instance model.** One instance = one WhatsApp connection (one number on Baileys, or one phone-number ID on Cloud API), created via `POST /instance/create` with its own name and its own **instance token**. Instances are cheap to create and are the unit of everything: webhooks, integrations, tokens and chat data are all per-instance. The project publishes **no per-instance resource figure — docs silent**. Indirect evidence only: each Baileys instance holds a live WebSocket + in-memory state in the single Node process; a third-party capacity PRD (Logicfy, May 2026) plans "a single Evolution API instance [server] can reliably handle between 50–100 sessions", and issue #2752 reports memory growing ~90 MB/h until OOM with ~400 mostly-stuck instances (a leak report against 2.3.7, not a sizing guide). Plan on tens of numbers per modest server, not hundreds, and on horizontal sharding beyond that.
- **Storage.** PostgreSQL **or MySQL** via Prisma (provider-specific schemas/migrations). By default it persists a lot: `DATABASE_SAVE_DATA_*` defaults in `.env.example` save instances, new messages, message updates, contacts, chats, labels and history — i.e. a full mirror of every connected number's WhatsApp traffic lands in your database unless you turn the switches off. **Redis** is the cache/session layer (`CACHE_REDIS_ENABLED=true` in the example; session files also live under `/evolution/instances` in the Docker layout, so that volume must persist or every restart drops the pairings). Media goes to local disk or S3/MinIO, with automatic download from WhatsApp and optional OpenAI audio transcription.
- **Manager UI.** An embedded web manager at `/manager` (login = the global API key) for creating instances, scanning QR codes, and inspecting chats; v2.4.0 replaced it with a rebuilt "Manager v2" (its source repo is now private; a pre-built bundle ships in `manager/dist`).
- **Event transports.** The same event catalogue can be emitted over per-instance or global **webhooks**, **WebSocket (Socket.io)**, **RabbitMQ**, **Amazon SQS**, **Kafka**, **NATS** and **Pusher** — configurable globally and per instance. This is genuinely more delivery machinery than a hand-rolled bridge usually has.
- **Integrations.** Native per-instance chatbot/service integrations: **Chatwoot**, **Typebot**, OpenAI, Dify, Flowise, n8n, EvoAI, EvolutionBot. Proxy support (HTTP/SOCKS, global or per instance) exists for the WhatsApp connection.

### Chatwoot integration (the one they advertise hardest)

Chatwoot support is a first-class, per-instance integration, not a webhook hack: globally enabled via `CHATWOOT_ENABLED=true`, then configured per instance through the API/manager with the Chatwoot account details. Evolution creates/manages the Chatwoot inbox for the number and mirrors conversations both ways (WhatsApp → Chatwoot and agent replies → WhatsApp), including media, read/delete mirroring (`CHATWOOT_MESSAGE_READ`, `CHATWOOT_MESSAGE_DELETE`), a "bot contact" in Chatwoot that posts instance status/QR events, and an optional **history import that connects directly to Chatwoot's PostgreSQL** (`CHATWOOT_IMPORT_DATABASE_CONNECTION_URI`). The release history shows this integration is heavily used and heavily patched (a long tail of Chatwoot fixes in nearly every 2.3.x release). One security caveat, from a current deploy-template analysis of 2.3.8: Chatwoot's callback into Evolution (`/chatwoot/webhook/<instance>`) has **no API-key check** in 2.3.8 — the instance name effectively becomes a secret on that route.

## API surface (shape)

REST, JSON, everything namespaced by instance: `/{resource}/{action}/{instanceName}`, authenticated by an `apikey` header (global key or the instance's own token — see Security).

- **Instance:** create / connect (returns QR base64 or pairing code) / connectionState / fetchInstances / logout / delete / restart; per-instance settings (reject calls, groups-ignore, always-online, read messages/status, sync full history).
- **Send (`/message/…`):** text, media (image/video/document), WhatsApp audio (PTT), sticker, location, contact card, reaction, poll, list, buttons, status/story posts; 2.4.0 added interactive **carousel** and PIX payment buttons and hardened button/list rendering. Cloud-API instances additionally send **template messages** and (2.4.0) gained Meta template update/delete endpoints.
- **Chat (`/chat/…`):** fetch/find chats, contacts and messages (with filters), mark-as-read, mark audio as played (2.4.0), archive, delete, presence (`sendPresence` — composing/paused etc.), number existence check (`onWhatsApp`), profile picture fetch, privacy/profile updates.
- **Groups (`/group/…`):** create, invite/link management, participants add/remove/promote/demote, subject/description, settings — i.e. full group administration, which our own bridge does not expose as a product surface today.
- **Webhooks/events:** registered per instance (`POST /webhook/set/:instance`-style configuration) or globally via env (`WEBHOOK_GLOBAL_URL`, optionally `webhook_by_events` → one URL path per event). The catalogue (from the project's own env/event lists): `QRCODE_UPDATED`, `CONNECTION_UPDATE`, `MESSAGES_SET`, `MESSAGES_UPSERT` (received), `MESSAGES_EDITED`, `MESSAGES_UPDATE` (delivery/read status), `MESSAGES_DELETE`, `SEND_MESSAGE`, `SEND_MESSAGE_UPDATE`, `CONTACTS_SET/UPSERT/UPDATE`, `CHATS_SET/UPSERT/UPDATE/DELETE`, `GROUPS_UPSERT`, `GROUP_UPDATE`, `GROUP_PARTICIPANTS_UPDATE`, `PRESENCE_UPDATE`, `LABELS_EDIT`, `LABELS_ASSOCIATION`, `CALL`, `LOGOUT_INSTANCE`, `REMOVE_INSTANCE`, plus Typebot start/change-status and an errors event. Webhook delivery has configurable retry (`.env.example`: up to 10 attempts, exponential backoff from 5 s to a 300 s cap, jitter; 400/401/403/404/422 treated as non-retryable).
- **Docs drift warning (secondary source, Swarmhit, verified against source schemas):** parts of the published API reference still show the v1 request shape (e.g. a `textMessage` object for send-text) while the 2.x server validates `number` + `text` at top level — integrators must test against the running version, not just the reference.

## Ban risk — the honest section

**The Baileys mode is unofficial, and the project does not hide it — but it also does not shout it.** The README's own wording is mild: the Baileys method "relies on the web version of WhatsApp and may have limitations compared to official APIs." There is **no explicit ban warning in the project's docs** (Codex Labs' September 2026 comparison notes exactly this absence). The underlying library is blunter — Baileys' own README: "Use at your own discretion. Do not spam people with this. We discourage any stalkerware, bulk or automated messaging usage." And the rule being broken is Meta's: WhatsApp's Terms prohibit "bulk messaging, auto-messaging, auto-dialing" and non-personal use unless authorised, and reserve suspension for it.

**Community/issue signals are consistent with that:** open issue #2774 (2026-10-31, on v2.3.7) is titled "Adding participant to group getting number banned"; deploy guides and comparisons aimed at Evolution users repeat the same pattern — numbers are banned regularly in Baileys mode, fastest when messaging people who never wrote first, when a new number sends volume immediately, or on bulk/broadcast behaviour; reply-style, human-volume use on an established number is the low-risk end, but the risk never reaches zero and a ban is a permanent loss of the number, not downtime.

**Equivalence with our own B8 bridge — stated plainly:** our B8 bridge (sendqon-whatsapp-own, server id 5) is also a Baileys linked-device connection. **The ban-risk profile is the same protocol risk.** Evolution does not reduce it, and B8 does not have more of it. The risk lives in WhatsApp's detection of an unofficial web-protocol client plus sending behaviour, not in which REST wrapper sits on top. Differences are operational, not existential: Evolution's defaults (full-history sync, always-online presence, read-receipt automation, group-admin actions) can make a number *behave* more like a bot if enabled carelessly; conversely its per-instance proxy support can separate numbers by IP, which our bridge does not currently do. Neither changes the category.

**What the Cloud API mode changes:** everything about this section. A `WHATSAPP-BUSINESS` instance is Meta's sanctioned channel — no linked-device protocol, no ban-for-connecting risk; enforcement becomes the ordinary Business-platform kind (template/category policy, quality rating, per-message billing). If a number's traffic ever matters commercially, this mode — in Evolution or anywhere else — is the only low-risk route, and it is the same WABA path Sendqon already treats as a channel concept.

## Maintenance health

- **Two release lines, and the cadence story is the weak point.** The 2.3 line's last two stable releases are **2.3.7 (2025-12-05)** and **2.3.8 (2026-11-23)** — a **353-day gap** between stable releases on the line everyone deploys. 2.3.8 is a maintenance release whose headline fix is serious: instances that stayed "open" but silently stopped receiving (WhatsApp began sending `<status>` stanzas Baileys 7.0.0-rc.9 didn't ack, dropping connections ~every 50 minutes) — fixed via a `patch-package` patch to a **release-candidate** Baileys, applied at Docker build time. In other words, for most of 2026 the deployable stable line was one WhatsApp protocol change away from silent inbound failure, and the fix rides on an RC dependency.
- The **2.4 line** launched 2026-05-06 (licence activation, Manager v2, interactive messages) with 2.4.0-rc2 following on 2026-05-17 — and, oddly, the *later-published* 2.3.8 is what GitHub and the ecosystem treat as "latest stable" today; the 2.4 line has not displaced it. Only 4 releases total in the last 365 days (AwesomeRepos read, 2026-11-27). Commit history is long (2,635) and the repo was pushed as recently as 2026-11-23, but "active repo" and "timely stable releases" are different claims; the second is not currently true.
- **The org:** Evolution Foundation (Brazil; suporte@evofoundation.com.br), an ecosystem play — Evolution API + Evolution Go + Evo CRM + a hosted Cloud offer + professional support/managed services as the commercial model, plus a HostGator VPS partnership advertised in the README. This is a real, organised steward, not an abandoned repo — but its centre of gravity is its own ecosystem and cloud, and the trademark/licensing tightening in 2026 (TRADEMARKS.md dated 2026-05-06, activation in 2.4.0) shows the direction of travel: more brand control and more operator registration over time.
- **Issue signals (171 open):** current top items are the expected production long tail for a Baileys fleet — sessions that stop receiving while showing Connected (#2790, #2778 — the class 2.3.8 addresses), Chatwoot edge cases (#2795, #2782, #2755), the ban report (#2774), CPU saturation from unindexed lookups under concurrent number checks (#2753), and the ~400-instance memory growth (#2752). Nothing here is disqualifying; all of it says "you will operate this software, not just install it".

## Security

- **Key model.** Two tiers, both sent as a plain `apikey` header: a **global key** (`AUTHENTICATION_API_KEY`) that can create/delete/fetch **all** instances and is also the **Manager UI login**, and a **per-instance token** that controls only that number. There is no user/role system inside Evolution itself — anyone holding the global key owns every number on the server, so in a Sendqon deployment the global key must never leave our backend, and tenants must only ever see (at most) their own instance token.
- **Dangerous shipped defaults (from the repo's own `.env.example`, main branch):**
  - `AUTHENTICATION_API_KEY=<redacted>` — a **published, well-known default global key** sits in the example file (the same value is also the default `API_AUDIO_CONVERTER_KEY`). Any deployment that copies the example without changing it is fully compromised to anyone who can reach the port; this value is famous in the community precisely because so many installs kept it.
  - `AUTHENTICATION_EXPOSE_IN_FETCH_INSTANCES=true` — instance tokens are returned by the fetch-instances endpoint by default.
  - `CORS_ORIGIN=*` together with `CORS_CREDENTIALS=true`.
  - `WA_BUSINESS_TOKEN_WEBHOOK=evolution` — the Cloud API webhook verify token defaults to the literal string "evolution".
  - `TELEMETRY_ENABLED=true` (see Licence section).
  - Full message/contact/chat persistence on by default (privacy surface, see Architecture).
- **Unauthenticated edges:** a current third-party analysis of 2.3.8 (Railway Chatwoot template notes) flags that the Chatwoot callback route and the built-in EVOLUTION channel's inbound webhook route take **no API key** — on those routes the instance name is the only secret, so instance names should be unguessable and those routes firewalled where possible. (Flagged as third-party analysis; we did not run the server to test it.)
- **Track record:** the project's own changelog records a past **CRITICAL unauthenticated path-traversal in the `/assets` endpoint** (local file read), fixed in the 2.3.3 line, plus later websocket-host validation work — evidence both that serious issues have existed and that they do get fixed and disclosed in release notes. SECURITY.md routes reports to private disclosure (email/GitHub), which is the right shape.
- **2.4-line addition:** activation + 30-minute heartbeats to the foundation's licensing server (data items listed in the Licence section) — a deliberate, documented phone-home, but a network dependency and metadata flow a security review must accept explicitly.

## Fit vs Sendqon's current route

Sendqon today has three WhatsApp postures: the **vendor server** (Zender companion; the owner's +92 347 4162393 is live there), our **own B8 Baileys bridge** (server id 5, built and integrated, awaiting the owner's QR re-link cutover), and the **WABA/Cloud API channel concept**. Against those:

**What Evolution gives that B8 doesn't:**
- **Fleet management**: one server, many numbers, one API — instance CRUD, connection state, restart/logout, per-instance settings, tokens and webhooks, plus a ready Manager UI for operators. B8 is a single-purpose bridge built for our server-row model; multi-number tenancy on B8 is our own engineering to write.
- **Cloud API unification**: Baileys and official Business instances behind the *same* REST shape and event catalogue. Sendqon's WABA path could ride the same integration code as its Baileys path instead of two unrelated adapters.
- **Ecosystem integrations we would otherwise build**: Chatwoot two-way sync (a real support-desk story), Typebot/Dify/Flowise/n8n bot hooks, queue transports (RabbitMQ/SQS/Kafka) for high-volume event fan-out, S3 media handling, per-instance proxies, group administration endpoints.
- **Someone else's Baileys treadmill**: protocol breakage (like the Nov 2026 status-stanza failure) is patched upstream for a 10k-star user base, not by us alone.

**What it costs:**
- **Another full stack to run and answer for**: Node + PostgreSQL/MySQL + Redis + session volume, next to the existing Laravel/Zender stack on offbox-1 — plus its upgrade treadmill, which (see Maintenance) currently means choosing between a stale-but-unactivated 2.3.8 and an activated 2.4 line.
- **Licence/brand surface inside a white-label SaaS**: the admin-visible usage notice, the un-rebrandable Manager, the commercial-licence fallback at the producer's discretion, and (2.4) operator registration + heartbeats. None is fatal; together they are a permanent compliance tail our own bridge simply does not have.
- **Instance sprawl economics**: per-instance memory/state in one process, a full traffic mirror in its database by default, and sharding questions at fleet scale that B8's one-server-row-per-bridge model defers.
- **Support surface**: Sendqon tenants' WhatsApp problems become a three-party diagnosis (Sendqon ↔ Evolution ↔ Baileys/WhatsApp) instead of two.

**Migration shape, if the owner's number ever moved to it:** identical in kind to the B8 cutover — create a Baileys instance, generate a QR, the owner scans it from the phone (the number becomes a linked device of that instance; WhatsApp's linked-device limit means it may displace another session), re-point Sendqon's server row/webhooks at Evolution's endpoints, re-register the webhook URL and events. **Evolution does not remove the one step that has actually been blocking us — the owner's QR scan — and it adds a second migration (data/config into Evolution's instance model) on top of it.** Number history/contacts do not migrate; a full-history sync can be requested per instance but is a Baileys-side import, not a transfer from the vendor server or B8.

## Recommendation

### (a) As a Sendqon WhatsApp provider option — **WATCHLIST** (do not adopt now; named triggers to revisit)

Evolution API is the strongest off-the-shelf Baileys engine available — real fleet management, a unified Baileys+Cloud API surface, and integrations (Chatwoot above all) that would take us months to match. But adopting it today means picking a poison: pin the **2.3.8** line (no activation, but a 353-day stable gap, an RC-patched Baileys, and a line the foundation has already superseded once) or accept the **2.4** line's operator registration, 30-minute heartbeats, and the brand/notice conditions inside a product whose whole point is Sendqon branding. Our own B8 bridge already occupies the Baileys slot with the same protocol risk and zero third-party licence surface, and the vendor server still carries the owner's live number. There is no capability gap today that Evolution closes for a *current* Sendqon tenant.

**Revisit triggers (any one reopens this study):**
1. A tenant (or Sendqon itself) needs **many WhatsApp numbers under one account** — fleet scale is where Evolution's instance manager earns its stack.
2. Sendqon productises the **official Cloud API channel** and wants one engine/API for both Baileys and WABA numbers.
3. A **Chatwoot-based support desk** becomes a product requirement.
4. The 2.4 line demonstrates a restored stable cadence (two consecutive on-time stable releases) and the activation regime proves benign in the field.

If a trigger fires, adopt it **backend-only** (Manager never tenant-facing), on the 2.3.8 pin first, with the shipped defaults overridden (own global key, `AUTHENTICATION_EXPOSE_IN_FETCH_INSTANCES=false`, telemetry off, `DATABASE_SAVE_*` minimised, unguessable instance names, API behind our own gateway) and the admin usage notice placed in Sendqon's admin settings from day one.

### (b) As a replacement for our own B8 bridge — **NO-GO**

Same Baileys protocol, same ban-risk category, strictly more moving parts, plus a licence/brand tail B8 doesn't carry — in exchange for fleet features B8's current job (one bridge in Sendqon's server model, cutover already built) does not need. B8's blocker is an owner QR scan, and Evolution needs the identical scan. Replacing B8 with Evolution would spend a migration to stand still.

**One-line verdict: Evolution API is a credible engine we should keep on the watchlist for fleet/Cloud-API/Chatwoot triggers — it is not a safer WhatsApp route than what we already run, and it should not replace B8.**
