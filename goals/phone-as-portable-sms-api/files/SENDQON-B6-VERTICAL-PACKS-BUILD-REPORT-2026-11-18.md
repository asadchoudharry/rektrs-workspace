## Mechanism — verified against live core code BEFORE building

How the platform stores the things a pack is made of (all confirmed in the live 5.0.4 code on the dev copy):

- **Message templates** a workspace actually uses day-to-day are **canned responses** (`canned_responses`: user_id, created_by_user_id, shortcut, body — workspace-wide quick replies offered in the composer). WABA templates are a different store and go through Meta review per tenant WABA account, so packs do **not** create them (they cannot be made real without the tenant's Meta assets).
- **Flows** are `flows` rows whose graph lives in `flow_data` (canvas JSON: nodes `{id, type: triggerNode|sendNode|actionNode|controlNode, data:{type, label, config}}`, edges `{source, target, sourceHandle}`). The panel's own store derives `trigger_type` from the canvas (`FlowController::triggerTypeOf`), resolves channels via `ReceiveFrom::channelsForCanvas`, and runs `FlowValidator` over the result. Pack flows are created through exactly this model path and are left **switched off**, precisely like flows created from core's built-in template gallery (`resources/flow-templates/*.json`, instantiated via `FlowTemplates::canvas()`).
- **Drip campaigns** are `sequences` (steps `{uid, type: send|wait|wait_reply|condition|add_tag|add_to_group|notify, config}`), created through core's `SequenceService`, which compiles each sequence into a hidden flow. Pack sequences are created as **drafts**.
- **Tags** are `contact_tags` (user_id, name, color); **labels** are `conversation_labels` (user_id, name, color); **contact fields** are `contact_fields` (user_id, key, label, type incl. `date`, options) — the `trigger.date` flow trigger reads a date contact field by key, which is what makes the schools fee-reminder flow real.
- **Reports: the platform has no user-defined report-definition system.** Reporting is built into each object (campaign reports, sequence reports, flow run history, message logs). Packs therefore ship **no report definitions** — inventing a store core cannot render would be fake content. Everything a pack creates reports through the platform's built-in surfaces automatically. This is stated plainly rather than padded.

**The apply mechanism (per the plan card — "an import/apply action the tenant triggers"):** each pack is a self-contained `integration` plugin (runtime contract 1) with a tenant page (Blade, shipped in the plugin — the Booking/PTA-Mask precedent) listing every content item with its apply status. The workspace **owner** clicks *Apply*: the pack creates the records in that workspace (fields → tags → labels → templates → flows → sequences) and tracks each one in its own `<slug>_applied_items` table. Re-applying is idempotent (tracked records are skipped; a same-named pre-existing record is *adopted* into tracking, never duplicated). *Remove* deletes exactly the tracked records (sequences via `SequenceService::delete`, flows force-deleted, the rest via their models). **Nothing is ever seeded automatically, and the owner's production workspace was never applied to** — production installs end with 0 applied rows, verified per pack.

**Plan-card corrections recorded:**
1. Core's flow gallery template for lead capture writes `action.add_tag` with `tag_names`, but the runtime `AddTagExecutor` reads only numeric `tag_ids` (`ResolvesWorkspaceIds::pickedIds`) — names are resolved at editor-save time, a step direct model creation does not have. Pack canvases/steps therefore carry `__TAG__:Name` placeholders that `PackApplier` resolves to the workspace's real tag ids (of the pack tags applied moments earlier) before creating the flow/sequence.
2. There is **no core plan-feature key for packs** (unlike B5's dormant contracts), and adding one would need a core edit. Packs gate the platform's own way for content plugins: admin activates the plugin; the pack page 404s while inactive; apply/remove are owner-only. No plan features, prices or flags were changed, and **no core files were edited in B6** (no patch-register entries).
3. Soft-delete trap found by the battery: `withoutGlobalScopes()` also lifts the soft-delete scope, so the applier's adoption/existence checks exclude trashed flows/sequences explicitly — otherwise a removed pack's trashed sequences were "adopted" back on re-apply.
