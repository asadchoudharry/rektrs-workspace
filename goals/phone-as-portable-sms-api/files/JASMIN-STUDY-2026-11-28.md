# Study — Jasmin SMS Gateway (jookies/jasmin) as Sendqon's aggregator SMPP core

**Date:** 2026-11-28 · **Studied for:** Sendqon's aggregator future — the PTA CVAS track (feasibility 2026-11-18: SMS aggregator = CVAS **Registration**, Rs 10,000 one-time; path = resell → register → direct operator interconnect at ~200k–400k SMS/mo) and the SMPP core that will hold the operator binds when the interconnect day comes.
**Sources:** GitHub repo + API (checked live 2026-11-28), official documentation (docs.jasminsms.com / jasmin.readthedocs.io, "latest" = master line), repo `requirements.txt` and LICENSE on master, GitHub issues. Every claim below traces to one of these; where the docs are silent, that is stated. READ-ONLY study — nothing was installed or deployed.

## What it is

Jasmin is an open-source SMS gateway written in Python on the Twisted event-driven engine, designed — in its own words — "for performance, high traffic loads and full in-memory execution." It is simultaneously an **SMPP client** (binds out to SMSCs / operators), an **SMPP server** (downstream ESMEs bind into it, SMPP v3.4), and an **HTTP/REST submission endpoint**, with a rule-based MO/MT router, per-user billing quotas, and an AMQP store-and-forward core. Repo stats at study date: **1,221 stars, 611 forks, 25 contributors, created 2012-11**, not archived (GitHub API, 2026-11-28). Sendqon already runs a Jasmin companion (`sendqon-jasmin`, programme B9): our own SMPP server is registered in the panel and its machinery was proven to the route boundary — but it holds **0 routes and has never carried production traffic**, so our operational exposure so far is minimal (see "Our own B9 experience" under Maintenance).

## Architecture

Components (official Architecture overview + jCli docs):

- **jCli** — telnet management console (port 8990 by convention). *All* configuration — users, groups, filters, routes, connectors — is done here (or through the Perspective Broker API); there is no web admin and no SQL config store. Configuration objects live **in memory** in the brokers and are persisted to disk (pickled) every `persistence_timer_secs` (jasmin.cfg). Operational consequence: config backup = backing up Jasmin's state files; lose them and you rebuild routes/users by hand or from your own jCli transcripts.
- **RouterPB** (Twisted Perspective Broker) — holds users, groups, routes, filters, HTTP connectors; performs MO/MT routing and all billing.
- **SMPPClientManagerPB** — manages the SMPP **client connectors** (the outbound binds to SMSCs/operators): add/remove/start/stop per connector (`cid`).
- **AMQP core (RabbitMQ)** — every hop is a queue: HTTP/REST/SMPP-server submissions are published to the router, routed messages are published per-connector for delivery, `submit_sm_resp` events feed asynchronous billing, DLR/MO "throwers" publish out. This is the store-and-forward spine and the scaling joint: connectors and throwers can be restarted independently, and queues absorb operator-side stalls.
- **Redis** — DLR lookup store (message-id correlation while receipts are pending; `dlr_expiry` default 86,400 s) and general state support.
- **DLRThrower / DeliverSMThrower** — services that push delivery receipts and inbound (MO) messages out to third-party applications over HTTP callbacks, with acknowledgement-and-retry semantics (below).
- **HTTP API** (port 1401) and **RESTful API** (`/secure/send`, `/secure/sendbatch`, balance and rate-check endpoints) — submission surfaces for applications.
- **SMPP Server** (port 2775) — downstream ESMEs bind (transmitter/receiver/transceiver) with a Jasmin user account; supported PDUs: bind_*, submit_sm, deliver_sm, enquire_link.
- Monitoring: Prometheus metrics + a documented Grafana setup (official docs, "Monitoring using Grafana"), plus a jCli **stats manager** with per-connector counters.

### How operator SMPP connections are managed

Each upstream SMSC is one **SMPP client connector** with a full parameter set (jCli `smppccm`): `host`/`port`, optional TLS (`ssl`), `username`/`password`, `system_type`, **bind type** (transceiver default, or transmitter/receiver), timeouts (`bind_to` 30 s, `res_to` 60 s, `pdu_read_to` 10 s, `trx_to` 300 s inactivity), **automatic reconnect** on loss/failure with configurable delays (default 10 s, both on by default), `enquire_link` keepalive (default 30 s), `requeue_delay` (120 s) for rejected messages, and **`submit_throughput`** — a per-connector throttle in messages/second (default **1 msg/s**; 0 = unlimited). Multiple connectors can point at the same operator (parallel binds) and route types can spread traffic across them. One honest gap: **there is no user-facing SMPP window-size parameter** in the connector config — outstanding-PDU windowing is handled inside Jasmin's SMPP stack (`smpp.twisted3`) and is not tunable from jCli (docs silent on any knob). In practice the operator-agreed rate is enforced via `submit_throughput` + bind count, which is how Jasmin deployments normally do it, but an operator that insists on a strict small window gives us no documented dial.

### Routing model

Two ordered routing tables, **MO** and **MT**, evaluated top-down; a route = one or more **filters** (ANDed) + a connector (or connector set). Route types: **Static** (one connector), **RandomRoundrobin**, **Failover** (first *connected* connector wins — the peak-hour/link-failover mechanism the project advertises), and MT-side **LeastCost** routing among rated routes; a filterless **DefaultRoute** sits at the lowest order as fallback. Filters: Transparent, Connector (MO), User / Group (MT), SourceAddr, DestinationAddr (regex — this is where per-operator prefix routing, e.g. `03xx` ranges per PK operator, lives), ShortMessage (content regex), Date/Time interval, Tag, and **EvalPyFilter** — an arbitrary Python script as a filter. On top of routing sit **interceptors**: Python scripts that can inspect/modify/drop messages pre-route on both MO and MT sides (the mechanism for house rules like sender-ID enforcement, content policy, custom logging). Routing is reconfigurable at runtime through jCli without restarts (only host/port/credential-class connector changes need a connector restart).

### HTTP API for submitting messages

- **Plain HTTP API** — `GET/POST http://<host>:1401/send` with `username`, `password`, `to`, `content` (or `hex-content`), optional `from`, `coding` (full SMPP DCS range), `priority` 0–3, `sdt` (scheduled delivery, SMPP absolute/relative), `validity-period`, and the DLR triple `dlr=yes` + `dlr-url` + `dlr-level` (1 = SMSC, 2 = handset, 3 = both) + `dlr-method`. Returns `Success "<uuid>"` (the queued message id) or a typed `Error "…"` with distinct HTTP codes (400 validation, 403 auth/charge, **412 "No route found"**, 500 send failure). One destination per request.
- **RESTful API** — authenticated JSON API with single send, **batch send** (`/secure/sendbatch`), balance check and route/rate check; this is the surface a platform like Sendqon would normally integrate against (and the one Jasmin's own in-repo load tester drives).
- **SMPP server** — for customers who want to bind in as ESMEs (the aggregator-resale case): bind with system_id/password = Jasmin user, per-user `max_bindings` quota on the server side.

## DLR handling

Delivery receipts are a first-class flow, not an afterthought:

- Requested per message (`dlr`/`dlr-level` on HTTP, `registered_delivery` on SMPP). Pending correlations are held in Redis (`DLRLookup`); `dlr_expiry` defaults to 24 h, after which a late receipt is dropped (the FAQ's "Got a DLR for an unknown message id" entry is exactly this case).
- **Level 1** callbacks carry `id` (Jasmin UUID), `message_status` (ESME_* command status) and the connector used. **Level 2/3** add `id_smsc`, submit/done dates, `sub`/`dlvrd` counts and the final delivery state parsed from the receipt.
- The **DLRThrower** delivers callbacks by HTTP GET/POST to the subscriber's `dlr-url`; the receiver must answer 200 with body exactly `ACK/Jasmin`, otherwise the thrower **retries** up to `max_retries` with `retry_delay` — i.e. DLR delivery is at-least-once and consumers must dedupe on the message id.
- DLRs for SMPP-server customers are returned in-protocol as `deliver_sm`.
- Operator msg-id format mismatches are a known real-world pain and Jasmin has the specific knob: connector parameter **`dlr_msgid`** (0 = ids identical, 1 = submit resp hex / receipt decimal, 2 = the reverse).
- Known wart, on the record: **PR #1192 (opened 2024-04-25, still unmerged) fixes DLR handling on multipart messages**, and issue #1239 (2024-11) reports non-standard `deliver_sm` formatting — DLR edge cases are precisely where this codebase's maintenance lag shows (see Maintenance).

## Billing model — what it has, what an aggregator still must build

Jasmin's billing is **per-user, per-route, in Jasmin's own unitless "currency"**:

- Every MT route can carry a **rate**. A user sending through a rated route is charged per `submit_sm` PDU — so a 3-part concatenated message is charged 3× the rate. Routes are **unrated by default**; billing exists only where you set rates.
- Two quotas per user, either of which stops sending when exhausted, on **all channels identically** (HTTP + SMPP server): **balance** (prepaid credit decremented by route rates) and **sms_count** (a plain message counter). New users default to *unlimited* on both (postpaid assumption) until you set values.
- **Asynchronous billing**: with `early_decrement_balance_percent` set on a user, that percentage is charged at submit and the remainder only when `submit_sm_resp` acknowledges — a user cannot flood the queues on credit that never settles. The async leg rides the AMQP `billing` exchange back into RouterPB.
- Per-user **throughput quotas** (`http_throughput`, `smpps_throughput` in msg/s), SMPP-server `max_bindings`, plus an authorisation/value-filter layer per user (which parameters they may set, regex restrictions on source/destination/content — e.g. pinning a customer to their approved sender ID).
- Billing can be switched off per surface (`billing_feature=False` in jasmin.cfg) — relevant because Sendqon already meters its own tenants.
- **State caveat**: balances live **in memory** in RouterPB and are flushed to disk every `persistence_timer_secs`. A crash between flushes loses the most recent charges (the docs themselves warn against setting the timer high). There is no transactional ledger.

**Day-1 aggregator reality check.** Jasmin gives us: wholesale metering per directly-connected customer (ESME/HTTP user), prepaid cut-off, per-route cost rates, throughput caps. It does **not** give us: a CDR database or any reporting/invoicing (message records are **log files** — per-connector logs and HTTP access logs; the Developer FAQ's answer to "log messages in a third party database" is *write an interceptor*), multi-currency/tax handling (rates are unitless by design), customer-facing balance portals, reconciliation reports against operator invoices, or per-tenant (as opposed to per-Jasmin-user) accounting. For Sendqon this split is actually clean: **Sendqon stays the commercial system of record** (tenants, plans, credits, invoices — already built), and Jasmin is the network-facing pipe whose per-user quotas act as a wholesale safety net for any customer we ever let bind directly. Anyone buying Jasmin expecting a billing *platform* will be disappointed; as a *meter + cut-off* inside our own platform it is sufficient.

## Throughput & capacity evidence

- **No official benchmark exists.** Jookies publishes no msgs/sec figure; the docs say only "designed for performance / high traffic loads / full in-memory execution." Any vendor-style number attributed to Jasmin elsewhere on the web is unsourced — treat accordingly.
- **Community measurement (best available evidence):** GitHub issue #963 (2021, Jasmin ~0.9/0.10 era) — a user load-tested on AWS 4 vCPU / 16 GB and measured **~80–110 msg/s through the HTTP API** and **~60–70 msg/s through the REST batch API**, at ~20% CPU with ~40 ms network latency to the SMSC, asking how to reach 150 msg/s. Jasmin's own docs use `submit_throughput 110` in the canonical "first connector" example, consistent with that order of magnitude per connector.
- **Architecture-derived reasoning (labelled as such):** the path is Twisted async + AMQP queues + in-memory routing, so per-instance throughput is bounded by Python/Twisted event-loop throughput on the router/connector processes and by AMQP publish rates — realistically the **low hundreds of msg/s per instance** for SMPP-bound traffic, scaling horizontally (more connectors per SMSC, more Jasmin instances) rather than vertically. The in-repo load tester added on master (2026) drives the REST path at configurable target rates (examples at 50–100 msg/s).
- **Fit against our actual requirement:** the CVAS plan's direct-interconnect threshold is ~200k–400k SMS/**month** ≈ an average under 0.2 msg/s; even a 100:1 peak-to-average burst is ~20 msg/s, and aggressive growth to 1M SMS/mo with sharp peaks stays inside ~100 msg/s. **Capacity is not the deciding factor for Jasmin at PK interconnect scale** — the operator's agreed bind rate will bind us before Jasmin does. The honest risk is not throughput; it is correctness/maintenance (below).

## SMPP specifics for PK operators

- **TON/NPI**: fully configurable **per connector** — `src_ton`/`src_npi`, `dst_ton`/`dst_npi`, `bind_ton`/`bind_npi` (defaults src 2/1, dst 1/1). This is the first thing every PK operator interconnect specifies (national vs international format for 03xx numbers, alphanumeric sender TON=5 for masks), and Jasmin covers it without code changes.
- **Sender IDs / masks**: `src_addr` per connector or per message, with per-user value-filter regexes to restrict which sender a customer may use — maps onto the PTA mask regime (mask traffic only via approved routes), though the *approval workflow* itself is Sendqon-side (already built in B2), not Jasmin's.
- **Concatenated SMS**: supported both ways; splitting is configurable — **UDH** (default) or **SAR** TLVs — with `long_content_max_parts` (default 5) on the HTTP API. SAR-vs-UDH preference varies by operator SMSC; having both is what matters.
- **Urdu/Arabic (UCS-2)**: `coding=8` (UCS2) is a first-class connector/API default; the docs' own worked example is Arabic UCS-2 content (text and hex forms). Urdu rides the same UCS-2 path (70 chars/part, concatenated as above). No PK- or Urdu-specific defects were found in the docs; issue history shows generic multipart/DLR edge cases (above), not encoding failures. **Docs silent** — as expected — on individual PK operators' SMPP flavours (Jazz/Zong/Telenor/Ufone each have their own interconnect quirks, DLR text formats and mask rules); those are discovered in interconnect testing with any gateway, not a Jasmin-specific gap.
- **DLR msg-id formats**: the `dlr_msgid` hex/dec knob (above) exists precisely because SMSCs differ — expect to use it.
- SMPP version: **v3.4** on both client and server sides (no v5.0; no PK operator requires it).

## Maintenance risk — the honest section

Verified via GitHub API, 2026-11-28:

- **Releases**: last tagged release is **0.11.0, 2023-11-10** — three years ago. Before it, 0.10.12 (2022-09). There is no 0.12 release, no published release roadmap.
- **Commit activity tells a stop–start story**: master commits per year — **2023: 72 · 2024: 21 · 2025: 1 · 2026: 29**. The project effectively slept through 2025 (a single commit), then **revived in April 2026**: 29 commits, almost all by one contributor (Anshu S. / `sah-anshu`) working on a **`0.12rc`** line — Python 3.12+ warning cleanup, custom-TLV work, IP-binding for the SMPP server, an in-repo REST load tester — merged by the maintainer ("The Z" / Jookies). **Last push: 2026-04-26** — i.e. at study date the repo has again been quiet for ~7 months, with the 0.12 release candidate unshipped.
- **Issues/PRs**: 44 open issues+PRs combined (5 open PRs). Issue *discussion* is alive (several issues updated in Nov 2026), and some old bugs do get closed — but the open-PR queue shows the responsiveness problem plainly: PR #1192, a **DLR-on-multipart fix, has sat unmerged since 2024-04**; a "Durable Queues" PR has been open since 2025-05. A fix we needed would very likely have to be carried by us.
- **Dependencies**: master's `requirements.txt` is reasonably current (Twisted 23.10, celery 5.4, redis 5.1, cryptography 43, falcon 3.1) and master is being made Python-3.12-clean — but that currency exists **only on master / the unreleased 0.12rc**, not in the 0.11.0 release most deployments (including the stock Docker image) run. Small rot signals remain even on master (e.g. a requirements comment conceding the abandoned `lockfile` package is still in use).
- **Fork landscape**: 611 forks, **none maintained as a distribution** — the most-starred forks have ≤2 stars and are years stale; the only active fork is the current contributor's own working fork. There is no community successor to fall back on (contrast: projects where a fork takes over). Commercial support exists from Jookies (paid), which is an option but not a community.
- **What this means for us, plainly**: adopting Jasmin as the aggregator core means adopting a **self-maintained dependency**. We would pin a known commit, keep our own fork, apply security/DLR fixes ourselves (the multipart-DLR PR is the template of what that looks like), and budget a small but real annual maintenance effort in Python/Twisted skills we currently use only lightly. The cost of *not* doing that — running stock 0.11.0 unpatched into an operator interconnect — is that the first operator-side quirk or DLR bug becomes an outage with no upstream to escalate to.
- **Our own B9 experience**: the `sendqon-jasmin` companion installed and registered cleanly, its SMPP server surface answered, and Sendqon's plugin machinery proved the path **to the route boundary** — then it stopped there: 0 routes, no upstream bind, no live traffic, no DLR ever processed. So B9 proves *installability and surface compatibility*, nothing about behaviour under load, long-lived binds, or receipt storms. We should not let "we already run Jasmin" inflate confidence: **operationally, we have not run Jasmin yet.**

## Alternatives — one-paragraph anchor

The only other open-source SMPP core with comparable production history is **Kannel** (C, BSD-style licence): bearerbox/smsbox architecture, legendary stability at operators worldwide — but its last **stable release is 1.4.5 (2018-06-19)**, development continues only on an unreleased 1.5.0 line, its SMPP-server add-on (opensmppbox) has been effectively unmaintained since ~2014, and it has **no billing/quota model at all** (DLR storage to SQL exists; rating does not). Kannel is therefore *more* frozen than Jasmin at release level while offering *less* of what an aggregator needs — it survives as the fallback anchor, not the front-runner. Everything else in the open field is a library, not a gateway (Node `smpp`, Go `smpplib`, Python `pysmpp` — building blocks for a from-scratch core, a far bigger commitment), and the commercial cores (e.g. Melrose Labs, Restcomm/TCXC-style stacks) solve the maintenance problem with licence fees and vendor dependency instead. **No alternative dominates Jasmin for our position; the realistic choice is Jasmin-with-own-fork vs. paid commercial.**

## Fit with the CVAS track — where Jasmin sits, and the phased path

- **Phase 1 — Resell (now → registration):** traffic flows through a reseller's account (e.g. Veevo-class, Rs 3.15/SMS planning figure from the 2026-11-18 feasibility). Sendqon submits through its existing provider layer. **Jasmin is not needed** and should not be put in this path; the existing companion stays frozen and inert.
- **Phase 2 — Registered aggregator, still reselling upstream:** if a reseller/aggregator grants us an **SMPP bind** instead of HTTP, Jasmin earns its first real job: it holds that bind (one connector), Sendqon submits via Jasmin's REST/HTTP API, DLRs return via DLRThrower callbacks into Sendqon. Least-cost routing becomes relevant only when a *second* upstream account exists — Jasmin's rated routes handle it natively.
- **Phase 3 — Direct operator interconnect (~200k–400k SMS/mo):** Jasmin sits **between Sendqon and the operators**: `Sendqon → (REST/HTTP or SMPP) → Jasmin → SMPP client connectors → Jazz / Zong / Telenor / Ufone SMSCs`, one or more connectors per operator, DestinationAddr filters splitting prefixes, Failover routes per operator pair, per-operator `submit_throughput` set to the contracted rate, MO replies and DLRs flowing back through the throwers into Sendqon. Sendqon remains the tenant/commercial layer (plans, credits, mask approvals, invoices); Jasmin's per-user billing is used only if we ever sell raw SMPP binds to wholesale customers.
- **Before Phase 3 money is spent**, three cheap gates: (1) build Jasmin **from our own fork pinned to a master commit** (not the 0.11.0 image) and re-prove the B9 path end-to-end against an SMPP simulator (e.g. a local SMSC sim) including multipart + UCS-2 + DLR round-trips; (2) carry or rebase the multipart-DLR fix (PR #1192) in our fork and test it; (3) load-test one connector to the highest rate a PK operator is realistically going to grant us (≤200 msg/s) so the capacity question is closed with our own numbers, not a 2021 forum post.

## Verdict

### Aggregator-core role — **GO, conditional**

Jasmin is the right SMPP core for Sendqon's aggregator future: functionally it is the most complete open option (client + server SMPP, MO/MT routing with failover and least-cost, per-user prepaid quotas and throughput caps, DLR throwers with retry, UCS-2/concatenation/TON-NPI coverage for PK interconnects), its Apache-2.0 licence is clean for commercial SaaS, its measured capacity (~100 msg/s class per connector) is an order of magnitude above our interconnect-phase requirement, and every credible alternative is either more frozen (Kannel), not a gateway (SMPP libraries), or a paid vendor lock-in. The conditions are the maintenance facts, and they are not optional:

1. **Own fork, pinned build.** We run Jasmin built from a Rektrs fork pinned to a vetted master (0.12rc-line) commit — never the stock 0.11.0 release — with the multipart-DLR fix carried in-fork.
2. **Budgeted self-maintenance.** A named, small annual effort for dependency/security patching of the fork; if that budget ever goes to zero, the verdict reverts to WATCHLIST and a commercial core must be priced before interconnect.
3. **Proof before interconnect.** Simulator end-to-end (multipart, UCS-2 Urdu, DLR formats) + own load test, per the Phase-3 gates above, *before* any operator contract depends on it.
4. **Sendqon stays the system of record.** Tenant billing, CDRs, mask approvals and invoicing live in Sendqon; Jasmin is pipe + wholesale meter only, so a future core swap stays possible.

### Existing companion (`sendqon-jasmin`) — **KEEP, frozen**

Do not replace it (nothing better to replace it with, and it is already integrated and proven to the route boundary) and do not expand its duties during the reseller phase. When Phase 2/3 arrives, **rebuild the companion from our pinned fork** rather than promoting the current stock build, and treat that rebuild as the real Jasmin adoption moment.

*Watchlist triggers that would reopen this verdict: 0.12 actually shipping (upgrades confidence), the April-2026 contributor line going silent for a further 12 months with a critical CVE in the Twisted/SMPP stack (downgrades it), or a PK operator imposing a requirement Jasmin cannot meet (e.g. SMPP v5.0 or a mandated window behaviour) — any of these returns the question to this file.*
