# Chamilo Feature Study — the lighter LMS, read against the Moodle census

**Date:** 2026-11-28 · **Type:** STUDY-ONLY feature reference · **Subject:** Chamilo LMS (`chamilo/chamilo-lms`), the course platform that deliberately puts the teacher's daily tools in core and makes the **learning path** — not the activity list — the centre of a course. This study is the point-by-point counterpart to `MOODLE-FEATURE-STUDY-2026-11-28.md` in this folder.

> **⚠️ LICENCE NOTE — read first.** Chamilo is licensed **GPL-3.0**. This study is a *feature and workflow reference only*: it describes what Chamilo does, in our own words, so we can decide which **ideas** are worth building ourselves. **No Chamilo code, text, or assets have been copied into any Rektrs/IQRS tree, and none may be** — GPL-3.0 code reuse would contaminate our proprietary products. Anything adopted from this study must be implemented independently, the same discipline applied to the Moodle and Gibbon studies.

**Version note (read before quoting any single feature):** Chamilo's public documentation spans the long-lived 1.11.x teacher guide, the 2.x guides, and a master-branch README headed "Chamilo 3" whose quick-install still points at a 2.0.3 package. The *product model* described below is consistent across those sources, but exact feature availability is branch-dependent. Treat this as a design census, not a version-specific installation recommendation — any adoption decision must re-check the feature against one named branch.

**Our two systems, as mapped for comparison (same anchors as the Moodle study):**

## 1. What Chamilo is, in one paragraph

Chamilo is a course-centred LMS with a deliberately small conceptual vocabulary: a **course** (a container of tools, grouped on the course homepage into authoring, interaction and administration), a **session** (a time-bound run of one or more courses for a specific cohort, so the same course can be re-used without duplicating it), and inside the course a **learning path** that sequences documents, links, tests, assignments, forum threads and SCORM/AICC packages into a guided itinerary. Around that spine sit an exercises tool, an assignments tool, a weighted gradebook that also drives certificates and skills, an in-course attendance sheet, forums and a built-in social layer, and a plugin system used mainly for integrations (BigBlueButton, Zoom, OnlyOffice, xAPI) rather than for basic teaching functions. Where Moodle's centre of gravity is the *configurable platform*, Chamilo's is the *teacher finishing a course setup in one sitting*.

## 2. Chamilo's model, mined area by area (our own words)

**Course model and sessions.** A course is created once and filled with tools the teacher can show or hide. Courses sit in categories and a catalogue; they can be imported/exported, including a course importer from Moodle. The distinctive unit is the **session**: a dated edition of courses assigned to a group of learners, with its own coaches and enrolment window. One course, many runs — the LMS analogue of "same syllabus, new term/class" — without cloning content. Groups exist at course level and globally, separate from the platform-wide social groups.

**Learning paths — the signature.** A path is an ordered sequence of learning objects and activities. It can be merely *suggestive* (a visible table of contents the learner may browse freely) or *prescriptive* (the order is enforced). Any item can carry a **prerequisite**: a previous item completed, or — for a test — a minimum score reached. Prerequisites can be applied to all steps or cleared from the whole path in one action. The player tracks progress, time and scores per item; paths import AICC and SCORM (SCORM 1.2 fully, SCORM 2004 partially per the project README), and a path's final step can surface the learner's certificate. This is sequencing as a first-class, teacher-operated object — not a side-effect of dates and visibility settings.

**Exercises (quizzes).** One tool serves exams, formative exercises, unlimited-attempt drills and answer-routed "scenarios", distinguished by configuration: feedback timing (immediate, end-of-test, withheld), questions on one page or one per page, shuffled questions/answers, attempt limits, start/end windows and time limits, negative marking (zeroed or carried), review-before-submit, and a pass percentage. Question types documented include single- and multiple-answer multiple choice, true/false combinations (including "don't know" variants scored zero), fill-in-the-blanks (cloze-style passages), matching/ordering, open questions (teacher-marked), oral expression (recorded audio answers), image hotspots, and exact-combination scoring. Questions carry **categories and difficulty levels**, feed a per-course questions database, and can be **recycled** into a new test as copies (editing the copy does not alter the original). Imports include Aiken, Excel, HotPotatoes and selected QTI 2. The project README claims 20+ question types, random selection by category and adaptive tests on the current line.

**Assignments.** Teachers collect file or online-text submissions with a soft deadline (late flagged, still accepted) and a hard close, can target specific learners, and work through submissions with score, feedback comments and an uploaded corrected file. Bulk handling is practical: download all submissions as one ZIP, upload a ZIP of corrections, list non-submitters, export a PDF list. A submission's visibility to peers can be controlled. With a maximum score set and "add to gradebook" ticked, the assignment joins the course assessment with a weight. Current guides also describe peer review support and optional AI-assisted grading suggestions; neither is a phased peer-assessment workflow of the Moodle Workshop kind.

**Gradebook ("Assessments").** A weighted aggregation over linked activities — tests, assignments, learning-path completion, attendance sheets, graded forum threads, surveys, plus manually entered classroom activities. Weights are expected to total 100; sub-categories group related items (e.g. five homeworks inside a 30% Homework category, each weighted within it). Each linked activity can carry a **minimum score**: fail a key activity's floor and the learner cannot achieve the course objective even if the weighted total passes. A separate minimum certification score gates the certificate. Grades export to spreadsheet. What the public documentation does **not** evidence is a formula language, multiple aggregation methods per category, drop-the-lowest, extra credit, or a scales/letters/outcomes engine of Moodle's depth — the maths is deliberately "weights, floors, threshold".

**Attendance in course.** An attendance sheet holds dated sessions (repeatable, group-scoped, with durations). Learners default to present; the teacher marks exceptions. Extended status types (late, justified absence) are a platform configuration. Sheets show per-learner percentages with colour coding — the 1.11 guide documents orange above 10% absence and red above 25% (fixed thresholds there). Signatures on a teacher-held tablet, per-student comments and PDF reports exist, and — the distinctive move — **a sheet can be linked into the gradebook** so presence counts as assessed evidence. This is course-session presence, not a school register: Chamilo has no SIS attendance machinery behind it.

**Certificates and skills.** Certificates are template-based (HTML templates with placeholder tags for learner, course, score, date and a QR/verification link), generated when the gradebook threshold and per-activity minimums are met, downloadable by the learner or batch-generated by the teacher as PDFs; one default template per course in the 1.11 model, richer templating via a plugin. **Skills** are a hierarchical catalogue (nestable skills with codes, criteria text and icons), importable in bulk from CSV/XML, measured against named **level profiles** (ordered scales such as Bronze/Silver/Gold). A skill is validated automatically when a linked gradebook category threshold is met or a linked course is completed, or manually by a teacher/admin where enabled; validated skills accumulate on the learner's profile, can be displayed as badges (Open Badges 2.0 is documented), and are visualised as a zoomable **Skills Wheel** that can also search users against a required skill profile. Skills can additionally be peer-evaluated (described as 360° evaluation). Compared with Moodle's competencies + learning plans, this is the same territory with the paperwork removed: tree, levels, automatic validation, a picture — but no per-student plan/evidence workflow in the documented model.

**Social and peer features.** A built-in social network (admin can disable it): a wall with posts, likes and comments; connections ("friends") with a safeguarding-relevant asymmetry documented in the 2.x guide — learners can only connect with other learners, while teachers may search for and connect with learners; internal messaging with multi-recipient replies and tags; and platform-wide social groups distinct from course groups. Inside courses, forums support categories/threads and can be scored, feeding the gradebook. This is a *community layer*, not a structured peer-assessment engine.

**Administration, hosting weight, and the "simplicity" claim — verified against requirements docs.** The current README's minimum server is **2 vCPU, 4 GB free disk, PHP 8.3–8.5, MariaDB 10+ or MySQL 5.7+**, and it notes Chamilo 3.0 was tested working on a 2 vCPU / **2 GB RAM** VM (4 GB recommended to build the dev environment). Moodle's own release requirements are likewise modest on paper (its 4.5 release page pins PHP/database minimums; Moodle's install documentation has long quoted small RAM/disk minimums). **So the requirements documents do not prove Chamilo runs on a smaller box.** What they do prove is a narrower *operational* surface: one database family (MariaDB/MySQL only, vs Moodle's five), the daily teaching tools in core rather than chosen from a plugin directory, course tools toggled from one homepage, and platform settings managed in the web UI with `.env`/Symfony YAML reserved for the technical layer. "Lighter" is an administration and decision-load claim, not a guaranteed VPS-size claim — and the flip side is real: a smaller plugin ecosystem (see below) and documentation spread across three version lines is its own admin cost.

**Accessibility emphasis — what is concrete.** Accessibility is a stated project value, and the concrete, checkable items are: an admin-enabled **font-resizing** option and **larger icons** option (project accessibility article); icons designed to read across languages, each with a hover description, and a persistent contextual-help control on most pages (teacher guide's usability page); oral-expression answers as an alternative response mode; and historical self-reported checks — the project's 2018 accessibility article reports running AChecker against its 1.11 test portal with 0 issues at WCAG AA and AAA levels, and the 1.9.10 release (2015) was described as the first Chamilo version to comply with WAI WCAG Level AAA. These are **historical, project-reported** results, not a current independent conformance report or VPAT for the present branch — the honest borrow is the *features and the habit of testing*, not the AAA headline.

**Multi-language, RTL, Urdu.** The README claims **60+ fully translated interface languages including RTL support**; language packs ship with the platform, can be enabled/disabled per language, set as platform default, and chosen per user; **sub-languages** allow an organisation to override terminology (its own terms for "course", "learner", etc.) without forking a pack; course content pages can be authored per-language with fallback to the default. **Urdu specifically could not be verified**: no official Chamilo source found in this study names an Urdu interface pack or its completion state (Urdu appears only in an OnlyOffice connector's document-template list, which is not the Chamilo UI). RTL as a capability is claimed; a production Urdu pack for our schools remains an open verification item, exactly as it would be for any LMS we adopt.

**Plugins and extension shape.** Plugins live in `public/plugin/`, ship bundled for the major integrations (BigBlueButton, Zoom, OnlyOffice, xAPI), and are discovered automatically. The documented architecture gives a plugin: metadata + install/uninstall scripts, admin-managed settings stored per access-URL (the multi-tenant unit), optional course-tool registration (an icon on the course homepage, per-course settings), admin/mail plugin flags, injection into **18 named display regions** of the frontend, Symfony event subscribers, and auto-discovered Doctrine entities/repositories with prefixed table names. It is a tidy *integration-and-regions* plugin model. It is not a marketplace: nothing in the official material suggests an ecosystem anywhere near Moodle's plugin directory scale, so niche needs (proctoring brands, publisher content, local SIS quirks) are more likely to be commissioned than installed.

**Standards and reporting (for the table).** SCORM 1.2 (partial 2004), AICC import into paths, LTI, xAPI/cmi5, QTI/Aiken exercise imports, REST-style web services with JWT API auth, course import from Moodle. Reporting is operational tracking — per-learner/course/session progress, time spent, scores, completion, participation, averages, exports — surfaced in tracking views; the public docs do not evidence a predictive analytics engine, a configurable report builder, or event-triggered intervention rules of the Moodle kind.

## 4. Question 1 — Where Moodle is overkill for K-12, and where Chamilo's lightness becomes the ceiling

**Where Moodle is genuinely overkill for our customer (a K-12 school, one campus, teachers who are not LMS specialists):**

1. **Grading-policy machinery.** Eight aggregation methods, formula entry, drop-lowest/extra-credit and outcomes reporting answer institutional policies that a school expresses once a term in its *examination* system — not per online course. A weighted-to-100 course gradebook with per-activity floors (Chamilo's shape) covers classroom reality.
2. **Assessment-integrity depth.** Certainty-based marking, adaptive behaviours with penalty ladders, per-user overrides and exam-browser lockdown serve high-stakes, accommodated, proctored testing. Our schools' board-pattern assessment is on paper; online quizzes are formative and low-stakes.
3. **Predictive analytics.** At-risk models need years of clean engagement data and staff who act on insights. A school first needs trustworthy progress/time/score tracking — Chamilo's layer — and human follow-up.
4. **Workshop-grade peer assessment** for most ages: phased allocation plus grading-the-grading is a powerful secondary-school instrument and an unreasonable default for primary/middle years.
5. **Plugin curation as an operating cost.** Moodle's ecosystem is an asset only if someone curates it; for a school without an LMS admin, "everything is a plugin decision" is itself the burden Chamilo removes by shipping the daily tools in core.

**Where Chamilo's lightness becomes a ceiling:**

1. **Question banking.** A per-course pool with categories/difficulty and copy-recycling cannot govern a shared departmental bank: no evidenced versioning (pin a quiz to question v3 while v4 is drafted), no draft/ready lifecycle, no cross-course/site scoping, no usage statistics. The day two teachers share a subject bank — or a SaaS serves many schools — this is the first wall.
2. **Gradebook maths.** Weights + floors + one threshold cannot express drop-the-lowest, best-of-N, extra credit, mixed scales/letters, or formula policies; and there is no evidenced grade-change audit trail of Moodle's kind. Fine inside a course; insufficient as the school's marks engine (which, in both our systems, rightly lives in Examinations, not the LMS).
3. **Analytics and reporting.** Tracking views and exports, but no item analysis to catch broken questions, no configurable report builder, no event monitoring, no predictive layer. Insight stops at "look at the table".
4. **Ecosystem and version risk.** A small plugin/integration ecosystem means commissioned work for niche needs; and the 1.11 / 2.x / 3 documentation-and-branch spread means "which Chamilo?" is a real diligence question in a way "which Moodle LTS?" is not.
5. **Mobile/offline.** No official offline-capable mobile app was evidenced; Moodle's app (and our own published apps) set a bar Chamilo's web-first model does not meet for low-connectivity learners.

## 5. Question 2 — ⭐ The Chamilo borrow-list for OUR LMS design

Tags: **[NEW]** = not on the Moodle study's shortlist · **[REFINES]** = overlaps a Moodle shortlist item (marked, not re-flagged as new) · **[CAUTION]** = borrow the pattern, not the feature as-is. Effort is indicative for our platforms: *surface* = UI/flow over existing data · *model* = data-model work needed.

1. **[NEW] Path-first course home — "next up" as the primary object.** The course opens on the learning path: an ordered itinerary with progress, where the learner's next item is obvious; sections/catalogue are secondary navigation. Suggestive vs prescriptive is a per-path teacher choice. *Effort: surface + a path/item model (ERP LMS and the IQRS add-on both have lessons/courses but no path object).* This is the single biggest lesson in this study: Moodle taught us gating machinery; Chamilo teaches us to present the route itself.
2. **[REFINES Moodle §4.3] Prerequisites in one gesture.** Per-item prerequisite = "previous item completed" or "test ≥ X%", with apply-to-all and clear-all actions and a teacher preview as the learner. Borrow the *interaction*, which is far simpler than a general condition builder; keep Moodle-style date/group conditions as an advanced layer only if ever needed. *Effort: model (completion state) + surface.*
3. **[NEW] The K-12 default course template.** A new course starts with exactly the daily tools on — documents, path, one exercise, assignments, attendance, gradebook — grouped as authoring / interaction / administration, everything else one toggle away. Teacher-first means the first screen is a checklist, not a toolbox explosion. *Effort: surface.*
4. **[NEW] Sessions as course re-runs (LMS layer only).** One course, many dated runs bound to class cohorts with their own tracking and certificates — the LMS mirror of a school term. In our architecture the SIS/ERP stays the source of classes and enrolment; the LMS borrows only the *run* presentation so teachers stop cloning courses every term. *Effort: model (course-run binding).*
5. **[NEW] Exception-only attendance marking, inside the course.** Default everyone present; mark the exceptions; colour the learner's row as absence crosses thresholds; optionally let the sheet count toward the course grade. Our school attendance register already exists and stays authoritative — borrow this UX for *course-session* presence and for how little work marking should be. *Effort: surface over existing attendance data.*
6. **[REFINES Moodle §4.6] Skills as a picture, not a plan.** A skill tree with level profiles (Bronze/Silver/Gold-style), bulk import from the curriculum, automatic validation when a gradebook threshold or course completion is met, and a **wheel** view a child and parent can read at a glance. Defer Moodle's per-student learning plans/evidence workflow; add it only for senior students if a real advising process appears. *Effort: model (skill tree + levels + validation links) + surface.*
7. **[REFINES Moodle §4.3/§4.9] Certificate as the path's final step.** When the weighted total and per-activity floors pass, the certificate surfaces *inside the path finale* and in the gradebook, with batch PDF generation for the teacher. The trigger composition (total **and** floors) is the detail worth copying. *Effort: surface over existing certificate modules in both systems.*
8. **[REFINES Moodle §4.2] A two-stage question bank: drawer first, vault later.** Stage 1 (Chamilo-weight): a per-course question pool where every authored question lands automatically, tagged with category + difficulty, recyclable into new tests **as a copy**. Stage 2 (Moodle-weight, later): scoped sharing, versioning, lifecycle. Chamilo proves stage 1 delivers most classroom value; it does not disprove stage 2's need at SaaS scale. *Effort: model, staged.*
9. **[NEW] Named test presets instead of a settings wall.** "Exam", "Practice exercise", "Drill (unlimited)", "Scenario" as starting presets that set feedback timing, attempts, shuffle and pass %; advanced settings unfold only on demand. Directly aimed at teachers who currently face raw quiz configuration in both our systems. *Effort: surface.*
10. **[NEW] In-context help as a product feature.** A persistent help control on teacher tools explaining *this* tool in plain words, icons with text descriptions, and admin-editable terminology (sub-language style) so the UI can say "class" and "term" the way the school does. Teacher-first simplicity is documentation placed at the point of confusion. *Effort: surface.*
11. **[CAUTION] A moderated class wall, not a social network.** Borrow: a per-class wall/groups space inside the course, teacher-visible, with the documented asymmetry that learners connect only within their supervised circle. Do **not** borrow open friending or platform-wide social groups for minors. *Effort: surface + small model, inside the LMS only.*
12. **[NEW] Core-before-plugins as a packaging rule.** Decide the daily teaching tools into the core LMS; reserve plugins for integrations (video, documents, xAPI) exposed as course tools or page regions with per-tenant settings — Chamilo's `public/plugin` shape (install/uninstall, per-access-URL settings, region injection) is a clean template for that rule in our own plugin terms. *Effort: architecture policy, not a feature.*

**Explicitly not borrowed:** Chamilo's social network as-is (safeguarding), its historical WCAG AAA headline (unverified for current branches — borrow the font/icon affordances and the testing habit instead), and its per-course question pool as the *final* answer to banking (see item 8's stage 2).

## 6. Verdict — does Chamilo change any Moodle-study conclusion?

**The Moodle study's core conclusion stands:** Moodle remains the deeper reference for the connected learning loop — governed question bank, configurable gradebook, item analysis, peer assessment, H5P, analytics, ecosystem. Chamilo does not out-feature Moodle anywhere except sequencing-as-a-product and teacher-first packaging. **But Chamilo corrects the Moodle census in five places where it overshot K-12 needs:**

1. **Sequencing priority (order-of-build correction).** The Moodle shortlist led with gradebook/bank machinery and treated completion + restrict-access as items 3/15. Chamilo shows the *path* should be built and presented first — it is the surface teachers and children actually live in — with gating implemented as its prerequisite feature, not as a separate conditions subsystem.
2. **Gradebook scope (size correction).** "Configurable aggregation engine" (§4.1 of the Moodle study) should be read as a **two-tier** requirement: Chamilo-weight weights/floors/threshold for *course* grades now; Moodle-weight aggregation only where it already belongs — the examination/report-card engine. Building Moodle's full engine inside the LMS is overshoot.
3. **Question bank (phasing correction).** The shared, versioned bank stays the destination (SaaS scale demands it), but Chamilo's per-course pool with categories/difficulty and copy-recycling is the correct **first** increment — the Moodle study presented the bank as one item; it is two.
4. **Peer assessment (ambition correction).** Workshop (§4.5 of the Moodle study) should be demoted from the adoption shortlist to a **secondary-school pilot candidate**. Chamilo-weight peer feedback (visible submissions, scored forum participation, peer-evaluated skills) is the K-12-appropriate first form.
5. **Competencies (form correction).** Lead with Chamilo's skill tree + levels + wheel + automatic validation; Moodle's learning plans with evidence are an advisor workflow our schools do not run. The Moodle item survives only in its framework half.
6. **Analytics (expectation correction, minor).** Neither study should let "analytics" imply prediction for our schools in the near term: Chamilo's honest tracking layer (progress, time, scores, absence colours) is the deliverable; Moodle's predictive insights stay a PARTIAL-to-watch, not a target.

**And one correction in the other direction:** the Moodle study did not overshoot on **item analysis** (quiz statistics) or **H5P** — Chamilo offers no equivalent for either, which confirms both as genuine Moodle-side borrows rather than category-standard features we could have sourced from the lighter system.

**Bottom line:** If Moodle is the reference for *how deep an LMS can go*, Chamilo is the reference for *how little of that depth a school day actually touches* — a path to follow, a weighted gradebook with floors, a skill picture, a certificate at the end, and tooling a teacher can set up between two classes. Our LMS design should be sequenced Chamilo-first (path, presets, template, skills picture) and deepened Moodle-ward (bank governance, item analysis, H5P, report-card-grade aggregation) only where school reality proves the need.
