## Preamble

### Scope

This register converts the 2026-11-07 audit of the IQRS web system into a single, owned, testable backlog. Sources covered in full:

- `WEB-APP-AUDIT-AND-DESIGN.md` — §1 verdict and security facts, the 18-row workflow table in §2 (multi-defect rows split into separate flaws), the §2.1 cross-cutting fragility register, the §3.1 design-debt list, §4 roadmap items 1–38 (each item implies one or more flaws, all captured), §5 and §6 (treated as below).
- `hidden_files/audit-lane-a-workflows.md` — code audit detail with file/function evidence.
- `hidden_files/audit-live-walk.md` — live production observations, 2026-11-07 09:35–09:49 PKT, read-only.
- `files/DESIGN-DIRECTIONS-SUPPLEMENT.md` — skimmed for additional recorded defects and for the two governed borrowings adopted into Direction A (journey discipline from D; Worklist pattern from E), which imply fix work and are registered as DESIGN flaws.

**Feature proposals are NOT flaws.** §5 of the audit (online payment as a product launch, real push, chat product, admissions CRM, analytics/early-warning, safeguarding log, document management, bilingual programme, API-as-feature, gamification layer G, copilot layer H) is tracked separately as a feature backlog and is excluded here except where the *underlying defect* is a flaw in its own right — e.g. the missing device-token endpoint (FL-062), the unexposed chat model (FL-061) and the missing change-password endpoint (FL-024) are defects in the current system, while building the full chat/push products on top of them is feature work.

**Unverified items are NOT flaws.** §6 items that could not be established from local evidence appear as `type=VERIFY` rows in Wave 0. They must be proven true or false on staging / by inspection before any fix is scheduled.

### Severity scale

| Severity | Definition |
|---|---|
| **Critical** | Exploitable trust, credential, money-truth or child-data failure, or a core school function is impossible as deployed. Fix before anything that depends on it. |
| **High** | Materially wrong output, silent data corruption/miscount, a whole workflow or audience blocked, or a defect that will cause incidents at scale. |
| **Medium** | Works in the happy path but fragile, misleading, inefficient or confusing in normal use; operator/parent friction or latent incident risk. |
| **Low** | Cosmetic, wording, dead-code or minor friction debt that signals unmaintained quality and erodes trust cumulatively. |

### Type scale

`SECURITY` · `WORKFLOW-BUG` · `DATA` · `CONFIG` · `DESIGN` · `PRINT` · `VERIFY`

### Owning workstreams

- **Security Engineering** — identity, authorisation, tokens, uploads, SQL, error handling, audit trail.
- **Core Workflows Engineering** — fees, exams, attendance, homework, timetable, HR, library, transport, portal and API behaviour.
- **Print Systems** — receipts, marksheets, admit cards, certificates, ID cards, print headers/footers, PDF/Excel and message templates.
- **Design Implementation** — Calm Campus Web token layer, components, navigation, forms, dashboards, portal and public site.
- **Data Cleanup Tooling** — tooling and governed clean-up for subjects, exams, fee groups, HR and student records.
- **Platform & Staging Engineering** — staging foundation, logging, backup/recovery regime, operations runbook, standards hardening.
- **Product & Content** — public website content, wording/spelling, notices discipline, session/gateway decisions with the school.
