# TAO Assessment Study — what a dedicated computer-based testing platform teaches our school exam design

**Date:** 2026-11-28 · **Type:** STUDY-ONLY design reference · **Subject:** TAO, the computer-based assessment platform by Open Assessment Technologies (OAT SA) — github.com/oat-sa (legacy platform) and github.com/tao-ce (current Community Edition), taotesting.com, userguide.taotesting.com. TAO is the platform class our systems do **not** belong to: a specialist assessment engine (authoring, delivery, scoring, results) with no school administration of its own. This study mines its *design* for our future online/CB testing, and settles the QTI question for our item bank.

## 1. What TAO is, in one paragraph

TAO is a full assessment *cycle* engine — **Rostering → Authoring → Delivery → Results** — built around one idea: assessment content is a managed asset, separate from any single test event. Questions ("items") are authored once in a bank, assembled into tests, published as deliveries, sat by candidates in tracked sessions, scored by a pipeline that mixes machine and human scoring, and stored as structured results data that reporting and item-quality statistics feed on. It is the reference implementation of "computer-based testing" as a category, which is why this study maps the assessment layer only — TAO has no fees, admissions, transport or HR machinery; programmes pair it with student-information systems, exactly as schools pair Moodle with an SIS.

## 2. TAO's model, in our own words

**QTI items and tests — the content standard.** Everything TAO authors is QTI (1EdTech's Question & Test Interoperability standard): items and tests are stored and exchanged as QTI packages, with import/export supporting **QTI 2.2 and QTI 3.0**. An item is a self-contained unit: the question body, one or more *interactions* (choice, text entry, extended text/essay, file upload, hotspot and other standard types), its correct-response declaration and its scoring rules travel together. Truly custom interaction types are possible through Portable Custom Interactions (PCI) — pluggable interaction code that still rides inside the QTI package. What QTI buys, concretely: (a) **portability** — an item bank is not trapped in one vendor's database; content can move between authoring tools, banks, LMSs and delivery engines; (b) **standard interactions** — a fixed, well-specified vocabulary of question types means an item means the same thing in every conformant system, including how it is scored; (c) **results interoperability** — outcomes are defined in the same standard's terms. The cost side is in §5.

**Item banking workflow.** Items, media assets and tests live in a content bank as managed resources, each carrying **metadata properties** (subject classifications and other key–value properties) that make the bank searchable and classifiable rather than a pile of questions. Items carry a lifecycle **state**; TAO's own assembly guidance is that only items in the **"final" (reviewed/approved) state** should be used in real tests — drafting, review and approval are bank workflow, not test-day improvisation. (In the current CE, per-item *statistics and usage data* are among the features held back for Enterprise — see §4 — which matters because bank quality control is exactly where statistics belong.)

**Test assembly.** A test is a hierarchy — **test → test parts → sections → items** — and behaviour is set as *properties at each of the four levels*, with higher levels overriding lower ones: time limits (including what happens on late submission), navigation policy (linear, must-answer-in-order vs free revisit), which tools a candidate may use, item **weights**, the scoring method, and **outcome declarations** — an explicit statement of which result variables the test will produce. Assembly can search the bank filtered by metadata and item state, so a test is built as a selection from governed bank content, not by typing questions into the test.

**Delivery and sessions.** Publishing a test creates a **delivery**; assigning a group of candidates and a time window creates a session; each candidate's run is a **delivery execution** with an explicit state machine (begun → interacting → closed, with closed splitting into fully-scored vs awaiting-human-scoring states). Live proctoring (in TAO Portal) shows sessions in status tabs — not started / awaiting authorization / in progress / paused / finished — and gives proctors a fixed action vocabulary: **authorize, pause, resume, extend time, reset, terminate, reopen, report**. Most actions demand a reason code plus a free-text explanation, and every action is written to a proctoring audit log with actor, action, reasons, IP and user agent. **Lockdown is opt-in, not default:** the TAO Secure Browser (a full-screen locked environment with breach detection/logging and optional pause-on-breach) must first be enabled for the organisation by the vendor's account management, then switched on per session ("Secure Browser Required"). AI-based *remote* proctoring is a separate commercial layer (paid add-on at mid tiers, included at top tiers), not part of the open platform's core.

**Scoring — two pipelines, one result.** Machine-scorable interactions are scored automatically by response processing at submission. Anything human-scored routes to **TAO Grader**: scoring is organised as *projects*; a response can carry **multiple trait outcomes** (several score boxes per answer — e.g. content, language, method scored separately); rubrics/criteria guide markers; marking is asynchronous and can be split across a team; there is batch scoring, the ability to reopen a scored response, anonymised marking, and a (beta) **read-behind** flow — a two-step score-then-review pattern for second-marker quality control. The design point: automatic and human scores land in the *same* outcome model, so a test mixing MCQs and essays produces one coherent result, not two systems glued together.

**Results and reporting.** A result/outcome store keeps, per candidate per item: the response given, the raw outcomes, the interpreted score/correctness, and timing (start, end, duration), plus session and LTI context. Session results export as CSV in a fixed schema (total score, max score, score ratio, then per-item fields). Above the raw store sit dashboards and custom reports (TAO Insights: visual dashboards, custom report building, exports, and APIs for programmatic result access). The principle worth stealing: **results are stored as data first and rendered as reports second** — the report card is a view, never the record.

**LTI integration with LMSs.** TAO plugs into LMSs (Canvas, Moodle, any LTI 1.3 platform) as an external tool: teachers deep-link published deliveries into LMS assignments; students launch the test from the LMS; proctors can launch the monitoring view via LTI; scorers can launch the grader via LTI (with custom claims selecting which deliveries/executions and which scoring category to mark); and final scores flow back into the LMS gradebook through **AGS** (Assignment and Grade Services), with roster lookups via NRPS in proctoring contexts. Registration is an administrator ceremony (OIDC/JWKS exchange) done once per LMS. The pattern: the LMS owns the course and the gradebook; the assessment engine owns the test; LTI + AGS is the seam.

**Users and roles.** TAO Portal administers users, groups and organisational hierarchies. Roles come in two scopes: **global roles** (Global Admin, Content Developer, Group Creator, Public Sessions Manager, Battery Manager, Support, System Manager, plus a Data Explorer bulk-edit capability) and **group roles** that apply only inside one group (Test-taker, Group Manager, Scorer, Score Reviewer, Proctor, Booklet Publisher, Scan Uploader, Group Viewer). The same person can be a scorer in one group and a manager in another. The legacy platform had the same shape in older clothes (Global Manager, Item Author, Test Author, Test Center Administrator, Proctor, test-taker, plus data-access controls on bank content).

## 3. Where TAO is actually used at scale — verified evidence

- **PISA 2025 (the strongest evidence available).** The OECD's own *PISA 2025 Results (Volume I)* publication names **Open Assessment Technologies as the Core 1 subcontractor for the PISA 2025 platform** (lead contractor ACER). OAT/ACER's award report (June 2026) states PISA 2025 ran on this platform across **91 countries and economies, 900,000+ assessment sessions, in 54 languages**, and won Best International Implementation at the 2026 e-Assessment Awards. PISA is the world's flagship international student assessment — this is national/international-scale proof, not a vendor brochure claim.
- **Japan — national CBT standard.** Japan's MEXT chose TAO as the platform for its national computer-based testing programme (first model pilot 2016, 2,000 first-year high-school students; delivered with Uchida Yoko/Infosign), i.e. a ministry standardising a whole country's CBT direction on it.
- **Lithuania — national examinations agency.** The National Agency for Education piloted on TAO Community Edition, then moved to a customised Enterprise solution; it delivered remote national testing to **15,000 grade 4 and 8 students in fall 2021**.
- **Ceneval (Mexico).** The national evaluation centre integrated a TAO item bank from 2011, reported at **over 3,000,000 test takers per year** (2014 case study).
- **Vendor-stated figures (labelled as such):** OAT's user guide claims 100M+ tests delivered and concurrency up to 200k+ parallel test takers. Treat these as marketing numbers; the PISA/Japan/Lithuania/Ceneval items above are the independently anchored ones. For calibration at the other end, TAO CE's own installation guide reports its tested envelope honestly: **500 concurrent test-takers** (all submitted; login slowdowns of 1–2 minutes at 500, ~7 s worst case at 200) — a useful reminder that the *open* build's proven envelope is school/district scale, and the 200k figure belongs to the vendor's hosted, tuned deployments.

## 4. The recorded complaint, verified — CE vs commercial

**The complaint on record:** the Community Edition lags the commercial edition — thin result analysis, slow feature development, unclear scaling guidance, and real support only behind payment. **Verdict: substantially TRUE, but narrower and more specific than the complaint suggests — and the gap is named by the vendor's own staff.**

What is actually held back (OAT staff post, TAO Community Forum, "Differences between versions?", April 2026 — the vendor's own current gap list of Enterprise vs CE):

- **Built-in reporting** (CE's reporting story is the raw result store + exports, not the finished reporting layer)
- **AI Labs** features
- **Custom data access control on the item bank**
- **Item statistics and item usage data**, and **import of item statistics** — the bank quality-control layer
- **Remote lists management**
- **Public sessions / anonymous tests**
- **Email notifications for test takers**
- **SSO / MFA**
- **Newer features introduced since the 2025.10 release line** (CE trails the commercial release train)

Nuances the same post adds: some features exist in the CE codebase but are **not enabled by default** (test batteries, custom rebranding, Data Explorer beta); some gaps are bugs, not policy (text-to-speech was broken, listed among CE 2025.10's known issues alongside a non-working item Usage tab and item Statistics tab); and some differences are architectural — Enterprise runs on cloud services, CE must substitute open-source equivalents. On **pace**: CE releases separately and visibly lags (forum users noted the January build still being "the latest" months later and asked where CE releases are even tracked); the later **CE 1.1 RC3 (LTS)** bundled commercial-cycle improvements spanning Nov 2025–May 2026 and added a documented build-from-source path — the January release still referenced private repositories, with a complete from-source open build targeted for August 2026. On **support**: CE support is the community forum + user guide; the commercial cloud tiers (checked 2026-11-28) run Starter free (1 author, 3,000 AI credits/mo, **50 learner attempts/month**), Author $149/mo (up to 5 authors, shared item bank, still 50 attempts/mo), Ignite from $990/mo (5 included/25 max authors, 1,250 attempts/mo, branded URL, dedicated account management; Data API and AI proctoring are paid add-ons), Elevate custom (10 included/50 max authors, 5,000 attempts/mo, AI + Data APIs included, AI remote proctoring included), Enterprise custom (custom capacity/connectors, private cloud, 24/7 support tiers).

**What this means if adoption were ever evaluated** (we are studying design, not adopting): the held-back set is not random — reporting, item statistics, bank access control and SSO/MFA are precisely the features a *school vendor* cannot ship without. A CE-based product would therefore face the AGPL/commercial fork almost immediately: comply with AGPL-3.0 across a SaaS offering, or buy the commercial licence whose entry tiers cap attempts at volumes a single school term would exhaust. The complaint is real; its practical consequence is that TAO-the-product is a national-programme procurement, not a small vendor's building block. TAO-the-*design*, however, costs nothing to learn from — which is the point of §5.

## 5. Question 1 — what our school-scale online testing should borrow

School scale is not national scale shrunk; it is a different problem. A class test is 30–40 students, one teacher, low-to-medium stakes, on school hardware and school Wi-Fi; an entrance test is a few hundred candidates, higher stakes, one day. Nothing in our near future needs 200k concurrency, parallel test forms for equating, or AI remote proctoring. What TAO teaches that *does* transfer:

**Borrow (design list, in build order):**

1. **The item bank as a first-class library, separate from any test.** Items live in a bank organised by metadata (subject → chapter/topic, difficulty, marks, curriculum outcome), never inside a single exam. This is the ERP's named gap (no standalone question-bank module) and the IQRS bank's next step (today it is bound to the online-exam module). One bank feeds class tests, entrance tests and LMS quizzes alike.
2. **Item lifecycle states with an approval gate.** Draft → reviewed → approved/final → retired, with only *approved* items eligible for real tests, and item versioning so an edit never silently rewrites a question already sat. This is governance our exam module already understands in another dress (the Exam Release Gate pattern) — apply the same discipline to items.
3. **Assembly as its own layer, blueprint-first.** Test → sections → items, with properties (time limit, navigation policy, weights, scoring method, declared outcomes) set per level. For schools, the killer form is the **blueprint**: "10 items from Chapter 4, difficulty mix 4 easy/4 medium/2 hard, 20 marks" resolved against the bank at assembly time — teachers think in blueprints, not in item IDs.
4. **Delivery/execution separation with an explicit state machine.** Published test → scheduled delivery (class/section + window) → one execution per student with states not-started → in-progress → submitted → auto-scored → awaiting-human-scoring → closed/released. Every later feature (invigilation, rescoring, result release) hangs off these states; inventing them later is the expensive path.
5. **The two-pipeline scoring model.** Objective items auto-score at submission; subjective items enter a **human-scoring queue** with rubrics, optional multi-trait scores (content/language/method as separate boxes), anonymised marking, and reopen/rescore. School scale simplifies the cast (the class teacher marks; a second marker only for entrance/board-pattern tests — TAO's read-behind, kept as an option, not a default) but the *pipeline shape* should be TAO's from day one, because our exams already mix objective and subjective questions on one paper.
6. **Results stored as data, rendered as reports.** Per-item responses, raw outcomes, interpreted scores and per-item timing in a result store; report cards, class analysis and CSV export as views over it. Plus **item statistics** (facility = how easy, discrimination = how well it separates strong from weak students) computed from stored results — notably, this is a feature TAO itself holds back from its CE; for us it is a read-side computation over data we will already have, and it is what turns a question bank from a drawer into an improving asset.
7. **Invigilation-lite with an audit log.** A teacher's live session screen (who has started, who is in progress, who submitted) with the proctor action vocabulary — authorize, pause, extend time, terminate, reopen — where every action requires a reason and is written to an audit log. No lockdown browser by default at school scale; a locked/kiosk mode is an opt-in reserved for entrance tests. (The reason-logged action log is the same accountability pattern as our Exam Recheck Register.)
8. **Two-scope roles.** Global roles (bank author, test author, admin) vs group-scoped roles (this class's invigilator, this test's scorer/reviewer). Our RBAC already scopes by module; the borrow is scoping *assessment roles by group/test*, so a teacher can be scorer for their own class's test and nothing else.

**Do not borrow:** test batteries and randomised parallel forms (equating machinery for national programmes); the Secure Browser as a default; AI remote proctoring; PCI custom interactions; multi-level organisational hierarchy trees; IRT calibration pipelines. Each solves a scale or stakes problem we do not have, and each would tax a small team's build and support budget. If a future board-scale customer appears, that is a new study, not a retrofit.

## 6. Question 2 — the QTI verdict

**The honest pros.** QTI is the only mature, vendor-neutral standard for assessment content: 25 years old, maintained by 1EdTech, with QTI 3.0 current and certification programmes for authoring/import/export/delivery. Adopting it buys: (a) an **item model that has already solved the hard modelling questions** (interactions, response declarations, scoring rules, outcomes) — designing against it avoids a decade of edge cases; (b) **portability/insurance** — our bank can leave any system, including our own future rewrites; (c) **future content supply** — international publishers and assessment vendors speak QTI; (d) **credibility** with any future institutional/international customer, for whom "QTI import/export" is a checklist line.

**The honest cons, for a small vendor.** (a) **No local payoff today:** we found **no evidence that any Pakistani public item-bank or board system publishes or consumes QTI**. Punjab's Punjab Examination Commission runs an online Item Bank System (reported 2022: a standardised bank of ~300 questions per subject generating school-specific 25-question papers with keys and rubrics) — a bank, but with no QTI interchange in evidence; the IBCC Model Assessment Framework pushes central item banks and psychometrics (CTT/IRT) without a QTI requirement in anything we found. If boards move, they have not moved yet. (b) **Full QTI is heavy:** the complete runtime — all interaction types, response-processing templates, adaptive items, PCI — is a platform-sized build; TAO itself is what full QTI costs. (c) **Tooling cost is real even for a subset:** XML package parsing/serialisation, media handling, and round-trip testing against other systems' dialects (QTI in the wild is a family of near-dialects; conformance is a spectrum, and 1EdTech certification itself requires membership). (d) **Over-engineering risk:** a class test needs five interaction types, not twenty-five.

**Verdict — PARTIAL adoption: GO.** Specifically:

- **Adopt the QTI item *model* internally** (item = body + interactions + response declaration + scoring rule + metadata + lifecycle state) as the design grammar for our bank, in our own database schema. This costs nothing extra — it is §5 item 1–2 designed with QTI's vocabulary.
- **Build QTI import/export for the common subset** — choice (single/multiple), text entry, extended text, matching, hotspot; QTI 2.2 first (widest tool support), 3.0 export when a consumer demands it. Position it as an interchange layer over our model, never as our storage or runtime format.
- **Do NOT build a QTI-native engine** (full response-processing, PCI, adaptive) — **NO-GO** at our scale.
- **WATCHLIST triggers for upgrading to fuller adoption:** a Pakistani board/PEC publishing or accepting QTI content; a publisher offering a QTI bank worth licensing; an international/SaaS customer making QTI a requirement. Any one trigger converts the subset into a funded lane; until then, partial adoption keeps the door open at subset cost.

## 7. Final verdicts

- **TAO as a product: NO-GO** (and not proposed — study only). Licence (GPL-2.0 legacy / AGPL-3.0 dual-licensed CE), the CE-vs-Enterprise hold-backs (reporting, item statistics, bank access control, SSO/MFA), and attempt-capped commercial tiers all point the same way: it is a platform for national programmes and funded institutions, not a component for a proprietary school SaaS.
- **TAO as a design teacher: GO.** The borrow list in §5 — bank-first content governance, lifecycle states, blueprint assembly, delivery/execution states, two-pipeline scoring, results-as-data with item statistics, reason-logged invigilation, two-scope roles — is the checklist our online-testing design should be written against, in both the IQRS overhaul's online-exam line and the ERP's PARTIAL online-exams/question-bank row.
- **QTI: GO on partial adoption** (model alignment + subset import/export), **NO-GO on a full QTI-native engine**, **WATCHLIST** on the three triggers in §6.
