# IQRS as a Multi-School SaaS — Phase S Architecture Paper

**Programme:** IQRS Web System Overhaul — international standard, then SaaS (goal_477711825d07)
**Role:** SaaS Architect lane · **Date:** 2026-11-07 · **Status:** Paper only — no SaaS build authorised
**Scope:** What Phase S (after Waves 0–6) should be, and — the decision this paper exists to force — which choices in Waves 0–6 must be made *now* so Phase S remains possible without a rewrite.
**Owner / commercial entity:** Assad, REKTRS PRIVATE LIMITED.

**Evidence base and confidence.** This paper is grounded in: the local API application, byte-identical to production (`~/workspace/iqrs-api/production/api/` — `config/`, `controllers/Webservice.php` + `Auth.php`, `models/Setting_model.php`, `models/Auth_model.php`, `libraries/SaasValidation.php`); the additive staff extension (`~/workspace/iqrs-api/staff-ext/`); and the audit (`WEB-APP-AUDIT-AND-DESIGN.md` §1–§2, scorecard #11 API maturity and #12 SaaS operations).

> **Confidence limit — read first.** The web admin application's own source is **not** in the local copies; only the API app is. Everything below about the API, settings model, auth and uploads is code-proven. Everything about the web admin (its views, its session handling, how an install is provisioned, how print templates and the theme system are stored) is inferred from the API's shared database/settings and the live walk in the audit. Phase S therefore *starts* with a discovery step (S0, §5) that obtains and audits the full web-app source before any tenancy commitment is treated as final. No tenancy recommendation in this paper requires rewriting the web admin blind.

**One-line recommendation.** Start Phase S as **deploy-per-tenant** (Option i) wrapped by a thin, separately built **platform layer** (Option iv's control plane, without its full ambition) — i.e. *Option i operated the way Option iv describes*. Do not attempt shared-database tenancy (Option iii) on this vendor codebase. Revisit only on the triggers in §2.3.

## 1. Where we start — tenancy-relevant properties of the current install

IQRS today is not "almost multi-tenant". It is a textbook single-tenant install in every layer that matters. The properties below are the starting facts Phase S must change — or deliberately replicate per school.

| # | Property | Evidence in the current system | SaaS consequence |
|---|---|---|---|
| 1.1 | **One install, one domain, one codebase copy** | `config.php` hard-codes `$config['base_url'] = 'https://iqrs.edu.pk/api/'`. One Hostinger shared-hosting account, one document root. Staging is a second copy of the same shape (`staging.iqrs.edu.pk`, DB `u238632175_test123`). | There is no routing concept of "which school is this request for?" anywhere. Tenancy must be introduced at the deployment/routing layer, or retrofitted into every query. |
| 1.2 | **One database** | `database.php` defines a single `default` group (production DB `u238632175_KliTy`). No tenant column, no tenant discriminator, no per-tenant connection selection exists in any model examined. | Every table is implicitly "the school's table". A shared-DB model would require touching effectively all of them (§2). |
| 1.3 | **One settings universe — the single-row `sch_settings` pattern** | `Setting_model::get()` returns `$result[0]`; `getCurrentSchoolName()`, `getCurrentSession()`, `getCurrency()`, `getStartMonth()` all read row 0. That one row holds school name, DISE code, address, timezone, currency, current session, start month, theme, logo images, `folder_path`, `cron_secret_key`, and — significantly — `mobile_api_url`, `app_primary_color_code`, `app_secondary_color_code`, `app_logo`, `saas_key`. | This is simultaneously the biggest obstacle and the biggest asset. Obstacle: "the school" is a global singleton assumed by hundreds of call sites. In any shared model, file isolation would need a new per-tenant prefix enforced everywhere; in a replicated model, isolation is free. Predictable/non-randomised filenames (audit §2.17g) are a cross-tenant disclosure risk in any shared-file design. |
| 1.5 | **One identity & session model spanning web + API + mobile** | Three surfaces share one database and one notion of user: web admin/portal (staff via `staff`, families via `users`), the vendor API (`Auth_model` → `users_authentication` tokens), and IQRS's own staff extension (`api_staff_sessions`, keyed by `staff.id`, deliberately separate because staff have no `users` row). In a multi-school world this secret distinguishes nothing: any school's app build can address any school's API. Scoped, per-tenant keys (Wave 6) are therefore not polish — they are the tenancy boundary for the API (§4, item D6). |
| 1.7 | **No audit trail, no backup code, logging off** | Audit §2.16/§2.18: no `audit` anywhere in the API data layer; `log_threshold = 0`; no backup/restore/export code in the API evidence (Backup/Restore exist only as web-panel permissions, unverifiable from source). Today we could not answer "who changed this record" for our own school. Audit and backup are overhaul work (Waves 1/6) whose *shape* decides SaaS viability (§4, items D2/D8). |
| 1.8 | **A vendor "SaaS" skeleton exists — disabled and empty** | `Webservice::__construct()` loads `SaasValidation` and `media_storage` on every request. `saas-config.php` sets `saas_enabled = false`. Two implications: (a) quota/plan enforcement has *named seams* to attach to later — worth not deleting in the overhaul; (b) the existence of a vendor SaaS concept makes the licensing question in §1.9 sharper, not softer. |

CodeCanyon-style licences commonly license *one end product / one domain per licence* and commonly distinguish "users can be charged for the end product" (extended) from running a multi-customer service — but this paper does not interpret the licence and no Phase S commercial step should rely on an assumption here. | **Gate G0 (§5): no pilot school is onboarded commercially, and no marketing commitment is made, until licence clarity is documented.** Possible outcomes include: one licence per tenant install (which deploy-per-tenant in §2 accommodates naturally — each school's install carries its own licence, purchased by us or by the school), a vendor SaaS/partner agreement, or a finding that SaaS resale is not permitted on this product at all — in which case Phase S becomes "operate IQRS's *own* additive layer + services around properly licensed per-school installs", or stops. This is the single item that can invalidate the whole phase, which is why it is sequenced first, in parallel with the overhaul, not discovered at the end. |
| 1.10 | **The additive-extension precedent** | `staff-ext/` proves, on this exact stack, that new platform capability can be added *without editing vendor tables*: own tables (`api_staff_sessions`, `api_sync_log`), own controllers (`Staffapi`, `Staffauth`, `Staffsync`), CSPRNG-grade tokens, session-derived identity, ownership scoping, idempotency keys, staged-then-production rollout with backups and rollback files. | This is the architectural pattern Phase S should generalise: **platform capability lives in additive, owned code around the vendor core — never as edits inside vendor tables/controllers that the next vendor update would erase.** It is also the pattern the overhaul already uses, so §4's decisions extend an existing discipline rather than inventing one. |

## 2. Tenancy model options for *this* CodeIgniter 3 codebase

Judged against this codebase specifically — a CI3 monolith we licence rather than own, whose web-admin source we do not even hold locally — not against tenancy theory.

| | (i) Deploy-per-tenant — one install per school *(current shape, replicated)* | (ii) One codebase, database-per-tenant | (iii) Shared database, `tenant_id` scoping | (iv) Platform layer around per-school installs *(extracted control plane)* |
|---|---|---|---|---|
| **Shape** | Each school = own subdomain/folder, own copy (or symlinked copy) of the code, own DB (`…_KliTy`-pattern), own `uploads/`, own `sch_settings` row. Provisioning = scripted clone of the IQRS install recipe. | One code tree; a resolver (subdomain → config) selects the DB connection per request; uploads still need per-tenant folders. | One DB; `school_id` added to every tenant-owned table; every query scoped; `sch_settings` becomes keyed by school. | Schools run as in (i); a **separate, owned** platform app (registry, provisioning, billing, health, support access) manages the fleet. School installs stay vanilla-plus-additive-extensions. |
| **Isolation strength** | **Strongest available here.** Separate DB + files + secrets per school; a breach, corruption or runaway query in one school cannot read or lock another's data. Backup/restore/deletion per school is a file/DB operation, not surgery. | Strong at data layer (separate DBs), weaker at code layer: one bad deploy hits all schools at once; shared file/session space needs care. | **Weakest.** Isolation is a `WHERE` clause repeated correctly thousands of times — in a codebase the audit shows *already* has universal IDOR with no ownership checks (§2.17c). One missed scope = cross-school child-data disclosure. | Same data isolation as (i), plus a new high-value target: the platform itself. Contained by keeping the platform *out* of the request path for school data (it provisions and observes; it does not proxy daily traffic). |
| **Upgrade / ops cost** | Highest per-tenant marginal cost: N installs to patch, migrate, back up. Mitigable — and only mitigable — by automation: one golden image/recipe, scripted rollout in rings (staging → IQRS → pilot → fleet), per-install version registry. On shared hosting this is manual and slow; on a VPS it becomes routine (§6). | Lowest deploy cost (deploy once), but every schema migration must run N times against N DBs with per-DB failure handling — the hard part of (i) remains, the easy part is saved. | Lowest nominal ops cost; highest engineering cost by an order of magnitude (below). | (i)'s cost, paid down progressively: the platform automates exactly the repetitive parts (provision, upgrade, backup-check, health) as they start to hurt. Cost is sequenced, not upfront. |
| **Fit with vendor code we may not freely rewrite** | **Best.** The vendor product is used exactly as licensed and shipped — one install per school is its native shape (and maps cleanly onto per-install licensing, §1.9). Our changes stay in the additive-extension pattern (§1.10). Vendor updates apply per install as they do today. | Poor–moderate. CI3's single `default` DB group and code that assumes one connection everywhere (models, the API constructor loading settings before routing) must be re-plumbed; `sch_settings`-as-singleton (`$result[0]`) fights per-request DB switching; each vendor update risks clobbering the resolver. | **Unacceptable.** Requires editing essentially every model/query in a licensed codebase — including the web admin, whose source we do not hold — plus adding a column across the schema and re-proving every workflow. It destroys vendor upgradability, maximises licence-modification exposure, and must be re-done on every vendor release. Rejected outright. | **Best alongside (i).** The vendor core is untouched; everything SaaS-specific is ours, in our own app and additive tables — the same legal/technical posture as `staff-ext/`. |
| **Fit with the existing mobile apps** | **Native.** The apps already point at a *per-install* API URL — `sch_settings` itself carries `mobile_api_url`, `app_primary_color_code`, `app_secondary_color_code`, `app_logo`. A second school = a second API URL + its branding values; the app's school-selection/config step is a small, known change. | Moderate. Apps still address one host; the API must resolve tenant from subdomain — workable if each school keeps its own subdomain/API URL, at which point the app-visible shape is identical to (i) anyway. | Poor. One API URL for all schools forces tenant selection *inside* the app/login flow (school code entry, cross-school parent identity) — a redesign of both apps' auth before any school #2 exists. | Same as (i) for the apps, plus the platform can issue each school its API URL/branding bundle as one provisioning output the apps consume. |
| **Time to first paying school** | **Fastest.** The recipe is "do again, scripted, what was done once for IQRS" — gated by licence clarity (G0) and hosting shape, not by engineering. Weeks, once Waves 0–6 have made the single install worth selling. | Months. The connection-resolver + settings-singleton rework must be built and re-verified against the full workflow suite first. | Quarters, with the overhaul effectively restarted inside a forked vendor codebase. Not a Phase S plan; a different programme. | MVP platform (registry + provisioning scripts + health) adds a small increment over (i); full platform (billing automation, self-serve onboarding) is deliberately *after* the pilot (§5). |
| **Verdict** | ✅ **Phase S starting model** | Deferred — becomes attractive only at a fleet size where deploy-once genuinely dominates, and only if the resolver can be built additively | ❌ **Rejected** for this codebase | ✅ **Adopt as the operating wrapper around (i)**, built incrementally (§3, §5) |

### 2.1 Recommendation

**Adopt (i) + (iv-as-wrapper): per-school installs, run as a fleet by a thin owned platform layer.** Concretely: every school gets its own install, database, uploads tree, domain and licence; everything that makes those installs *a product rather than a pile of copies* — registry, provisioning, branding/config issuance, subscription state, health, backup verification, audited support access — lives in platform code **we** own, built additively in the `staff-ext/` pattern and never by forking vendor tables or controllers.

Why this wins for *this* situation, in order: (1) it is the only model that respects both hard constraints at once — a licensed vendor core we should not fork, and a child-data isolation duty where "separate database" is the strongest sentence we can say to a school; (2) it matches how the mobile apps and `sch_settings` already work, so school #2 needs configuration, not architecture; (3) its known weakness (N installs to operate) is an *automation* problem that arrives gradually and can be paid down in Phase S order (§5), whereas (iii)'s weakness is a *correctness* problem that arrives on day one and can never be fully re-verified; (4) if the licence answer (§1.9) is "one licence per install", this model is already compliant in shape.

### 2.2 What this model deliberately does *not* promise

No cross-school features in Phase S (no parent with children in two schools in one login, no cross-school reporting, no shared staff identity). Those are platform-layer features of a later phase, added at the platform layer where identities can be *linked* across installs — not by merging school databases.

### 2.3 Triggers to revisit the model

Reopen this decision if any of the following becomes true — and not before:

- **Fleet size:** sustained > ~25–30 schools on per-tenant installs where upgrade/backup labour is measurably the binding constraint *despite* the §3.7 automation — the point where (ii)'s deploy-once economics deserve a fresh costing.
- **Licence/vendor change:** QDOCS offers a genuine SaaS licence/edition (the §1.8 hooks suggest one exists upstream) on terms that beat per-install licensing — adopting the *vendor's* multi-tenancy would supersede building our own.
- **Product demand:** paying schools require cross-school-group features (a trust/chain running several schools under one administration is the realistic case) — that argues for (iv) growing *group* tenancy at the platform layer first, still not for (iii).
- **Platform rewrite decision:** if the vendor core is ever replaced by a system we own outright, tenancy is re-decided for that codebase on its merits; this paper's rejection of (iii) is specific to forking *this* licensed CI3 monolith.

## 3. The platform layer — needed regardless of tenancy model

Everything in this section is ours to build, outside the vendor core. Even under the recommended model, none of it exists today; scorecard #12 ("Reliability, SLA, support & SaaS operations — Falls short") is precisely this section's absence.

### 3.1 Tenant registry & lifecycle
A single platform-owned registry: one record per school — legal name, subdomain/domain, install location, DB identifier, licence reference, plan, subscription state (§3.4), version/build of the install, primary contact, data-residency/hosting node. Lifecycle states mirror the discipline the owner's other venture already uses for tenants (`requested → approved → provisioning → active → suspended → …`): a school is *provisioned* only when registry, install, admin account, branding and backup check all pass — not when the files are copied.

### 3.2 Provisioning & onboarding
Scripted, idempotent, re-runnable — the install recipe extracted from how IQRS itself (and staging) were stood up: create hosting space/VPS tenant slot → create DB + user → deploy golden build → run additive-extension SQL (`api_staff_sessions`, `api_sync_log`, successors) → seed a *blank* `sch_settings` (never a copy of IQRS's row: no IQRS students, fee groups or HR debris may ever be cloned into a customer) → seed the agreed starter catalogue (subjects, exam structure, fee-group skeleton — the overhaul's Wave 4 tooling, §4 D7, is what makes this a data pack rather than manual clicking) → create the school's first Super Admin with a forced first-login password set → verify (smoke login, API health, backup run, TLS) → hand over with a written admin pack. Onboarding also includes data migration *in* (students/staff from the school's spreadsheets/previous system) using the same tenant-agnostic import tooling.

### 3.3 Branding & per-school configuration
Per-school config already has a home: the school's own `sch_settings` row (name, logos, timezone, currency, session, `mobile_api_url`, app colours/logo). **Calm Campus Web is designed to be per-school-themeable on top of this:** the design system is a *token layer* (CSS variables for colour, radii, density, type) with IQRS navy `#10204D` / gold `#D4AB42` / ivory `#FAF7EF` as **IQRS's token values, not as constants in components**. A new school = a new token set (its primary/accent, its crest as a fixed-size circular badge with ring, its name/motto) issued from its settings at provisioning; components, layouts, print templates and dark mode ("night navy" derived from the same tokens) are shared and unchanged. The rule that makes this true is a Wave 5 decision (§4, D3): **no school-specific colour, name, logo path or motto may be hard-coded in a view, stylesheet, print template or mobile screen — every such value resolves from settings/tokens, or the build fails review.**

### 3.4 Identity — three planes, kept separate
- **School plane (exists):** staff, students, parents inside one install, exactly as today (plus the overhaul's hashed passwords, ownership checks and scoped tokens). School Super Admin administers *their* school only.
- **Platform plane (new, ours):** platform operators authenticate to the *platform*, never by holding school passwords. Roles are exactly-scoped, in the maker/checker spirit the owner already enforces elsewhere: e.g. `platform-provisioner` (create/suspend installs), `platform-billing` (plans/invoices), `platform-support` (read-only health + break-glass, §3.8), `platform-admin` (registry config) — **one role per operator login, no universal super-user**, every action audit-logged at the platform layer.
- **No backdoor plane:** there is no shared master password, no reuse of the vendor's static `Auth-Key` as a platform credential, and no platform SSO into a school's staff accounts except through §3.8's audited break-glass.

### 3.5 Billing hooks — two money flows that must never mix
- **School's money (inside the install):** fees collected from parents — the overhaul's fee work (discount ledger, gateways such as JazzCash/Stripe *as evaluated for fee collection*) belongs to the school; REKTRS never holds or reconciles it beyond providing the software.
- **Platform's money (in the platform layer):** each school's subscription to *us* — plan, price, billing period, trial, paid/unpaid/suspended state — recorded in the registry and enforced at the platform layer (suspend = platform state change + install-level lock screen/`maintenance_mode`-style gate, executed by our additive code reading subscription state — **not** by editing vendor fee logic, and never by touching the school's fee data). Stripe (cards/international) and a Pakistan rail (JazzCash/Easypaisa or bank transfer with manual verification) are the candidate *SaaS-billing* rails; evaluating them for SaaS billing is a separate decision from the fee-gateway evaluation, with separate merchant accounts, webhooks and reconciliation. Plan *prices* are the owner's commercial decision (§5, Gate G3) — this paper defines only the hooks: plan catalogue, per-school subscription record, dunning/suspension policy points, invoice generation from the platform layer.

### 3.6 Domains & TLS
Each school gets `school-slug.<platform-domain>` by default (fast, one wildcard certificate, zero school-side DNS work) and may attach a custom domain (`system.theirschool.edu.pk`) as a plan feature: DNS verification, per-domain TLS issuance/renewal automation, and `base_url`/API URL re-issuance as one provisioning step — remembering that today `base_url` is a hard-coded string in `config.php` (§1.1), so domain assignment must be a *generated config*, not an edit. The mobile apps consume the resulting API URL from the school's config bundle (§3.3).

### 3.7 Data isolation, backup & restore — per tenant, provable
Under deploy-per-tenant this is finally simple, and Phase S must keep it that way: per-school DB dump + `uploads/` archive, on an automated schedule, copied off-host, with retention — i.e. the overhaul's Wave 6 backup regime (§4, D8) written as a **per-install script parameterised by install path/DB/domain**, so the platform runs the identical script N times and records per-school success/failure in the registry. Restore is per-school and rehearsed (a restore drill per school at onboarding, then sampled drills across the fleet); a school leaving the service gets a complete export (DB + files + printable records) and a certified deletion — data-portability as a feature, answering scorecard #6 properly at fleet level.

### 3.8 Observability & support access discipline
- **Per-tenant health:** the platform polls each install (web login page, API health/smoke endpoint — the overhaul's Wave 6 API work, §4 D6, should expose a minimal authenticated health/status surface), DB reachability, disk/uploads growth, last-backup timestamp, certificate expiry, install version. One fleet dashboard; alerting on any school red. The Wave 6 runbook/SLA-imitation (uptime log, incident notes, restore drill record) is the *seed document* of real SaaS operations — written so it can be re-pointed at N installs without restructuring.
- **Support access = break-glass, audited:** routine support is done *with* the school (their admin shares/exports, or grants a named, time-boxed support account in their install). Platform operators have **no standing login** to a school's data. Exceptional access uses a break-glass flow: named operator + reason + school notified + time-boxed credential created by our additive support endpoint + every action written to both the platform audit log and a row the school's own Super Admin can see in their install. If we cannot explain an access from logs, it did not have permission to happen. Child data makes this a trust feature, not bureaucracy — it is what we will say to every school board that asks.

## 4. DECISIONS TO MAKE NOW — in Waves 0–6, before Phase S exists

**This is the paper's operative section.** Each item is cheap or free at overhaul time and expensive-to-impossible to retrofit after N schools — or after IQRS's own patterns have hardened — depend on the wrong shape. Programme rule proposed: **no wave is signed off until its rows below are explicitly answered in that wave's design notes.**

| # | Wave | Decision to make NOW | SaaS cost if ignored |
|---|---|---|---|
| D1 | **0 — Staging foundation** | Make the install **reproducible**: every config difference between installs (base URL, DB credentials, upload path, environment) is *generated from a per-install config file outside the vendor tree*, and staging↔production differ only by that file. Capture the full install recipe (hosting, DB, additive SQL, settings seed) as a script/runbook as staging is rebuilt — not from memory later. Also: obtain and archive the **complete web-admin source** matching production (closes §0's confidence gap). | Provisioning school #2 becomes archaeology: hand-edited configs, unknown deltas, a recipe nobody can re-run. Every later automation (§3.2) is built on sand — and the licence/source question (§1.9) stays unanswerable for the web half of the product. |
| D2 | **1 — Security** | Design the **audit log with a school/install context column from day one** (actor, role, install identifier, entity, before/after, timestamp, IP) even though only one school exists; apply the same context field to the staff extension's `api_sync_log` successors. Password hashing, token redesign and session fixes must contain **no single-school assumptions**: no global singleton user, no hard-coded school ID/name in token claims, token/session tables keyed so a platform layer can reason about them per install. | Retrofitting context into an audit trail is impossible for historical rows — the fleet's early history is permanently unattributable, exactly when a new SaaS most needs to prove who touched child data. Auth rebuilt around IQRS-specific shortcuts must be rebuilt *again* per the platform identity model (§3.4), this time under paying customers. |
| D3 | **1 & 5 — Security / Calm Campus Web** | **Scoped, per-install API keys replace the static shared `Auth-Key`** as the design target (the Wave 1 stop-gap may rotate the secret, but the Wave 6/versioning design in D6 must land on per-install, revocable, scoped keys). In parallel: **all branding is settings/token-driven** (§3.3) — IQRS navy/gold, crest, name, motto, currency, timezone, date format are *values*, never literals, in web views, print, email/SMS templates and both mobile apps. | A shared published secret across a fleet means one leaked app build compromises every school's API gate — the tenancy boundary simply does not exist at the API. Hard-coded IQRS identity turns every new school's branding into a code fork; the token system — the overhaul's flagship asset — becomes single-use. |
| D4 | **2 — Workflow bugs** | Fix workflows **generically, not IQRS-specifically**: the fee-discount fix is a real **discount ledger** (amounts on the fee, status from *paid only*, policy — who may grant, caps, approval — as *settings*, not code embodying IQRS's practice); attendance-type logic stops assuming `attendence_type_id != 4` means present (types are per-school data); fine logic is unified into **one** implementation with per-school parameters, not four copies tuned to IQRS. Any rule a reasonable school could set differently is a setting with IQRS's value as the default. | Each IQRS-shaped hard-coding is a future fork: school #2 with a different discount policy, attendance-type order or fine rule forces either a code branch per school (fleet divergence, unmaintainable) or telling a paying customer their policy is wrong. The discount-ledger defect — already the audit's most consequential data flaw — gets *standardised* instead of fixed. |
| D5 | **3 — Print unification** | Build the unified print system as **templates + tokens + per-school header/footer/logo config**: one print engine, school identity injected from `sch_settings` (crest badge, name, address, session), fee receipts showing Paid/Discount/Balance from the D4 ledger. No IQRS text, phone, address or colour inside any template body. Print templates must be *data the install carries*, exportable/importable per school. | Print is the surface parents physically hold — and the easiest place for the previous school's identity to leak into a customer's documents (a reputational, trust-destroying error class). Hard-coded templates mean per-school print forks and re-doing Wave 3 per tenant. |
| D6 | **6 — Standards hardening (start design in 1)** | Treat the **API as the SaaS integration surface**: versioned routes (`/v1/…` alongside legacy), per-install scoped keys (D3), a documented contract (OpenAPI or equivalent), a health/status endpoint (§3.8), and idempotency/audit conventions generalised from `api_sync_log`. Keep the vendor's `SaasValidation` hook points intact and named in our docs (quota/storage seams, §1.8) even while disabled. The mobile apps' per-school API-URL configuration becomes a *formal config bundle* (API URL + branding + school display name) the platform issues. | Without versioning + scoped keys, every fleet-wide API change is a flag-day across all schools' apps, and no school can be revoked, rate-limited or audited individually. Deleting/ignoring the vendor quota seams removes the natural attachment point for plan enforcement (§3.5) if the vendor SaaS path is ever licensed. |
| D7 | **4 — Data-cleanup tooling** | Write **every cleanup/migration tool tenant-agnostically**: parameterised by target install/DB, dry-run + report first, no IQRS student/staff/fee IDs, names or policies baked in (the ~951 legacy fee groups, duplicate staff, placeholder phones are *patterns* to detect, not constants to delete). The starter-catalogue builders (subjects, subject groups, exam structure, fee-group skeleton) output a **reusable seed pack**. | Wave 4 is secretly the onboarding department: the same tools that clean IQRS are what migrate school #2's data in and set it up (§3.2). IQRS-specific scripts must be rewritten under onboarding deadline pressure, with a new school's real data as the test case — the worst possible conditions. |
| D8 | **6 — Standards hardening** | Build the **backup/restore/observability regime per-install and scriptable**: one backup script (DB + uploads + config manifest incl. install version), parameterised per install, emitting a machine-checkable success record; restore drill documented and timed (RTO/RPO stated, even if modest); logging on with per-install log locations; the runbook written fleet-shaped (per-install sections generated from a registry-like list, even while the list has one entry). | A backup regime that is a manual hosting-panel habit cannot be evidenced to a school, cannot be monitored by the platform (§3.7/§3.8), and fails silently at exactly fleet scale. "We back up your children's records" must be a *report*, not an assurance. |
| D9 | **All waves** | Preserve the **additive-extension discipline** (§1.10) as a programme rule: new capability goes in owned controllers/tables/config *around* the vendor core; any unavoidable vendor-file touch is logged in a single patch register (file, reason, reapply-on-vendor-update instructions). Vendor updates are rehearsed on staging per install shape, not improvised. | Undisciplined vendor edits make the fleet diverge invisibly and turn every vendor security update into per-school manual surgery — or, worse, updates stop being applied and the SaaS sells known-vulnerable software to schools. The patch register *is* the upgrade runbook at N installs. |
| D10 | **5 — Calm Campus Web** | Keep **web and mobile on one token/config system** (same token names, same settings keys) and keep the apps' school-config step inside the existing per-install API-URL pattern — no new hard-coded IQRS endpoints, domains or asset URLs anywhere in either app; all assets (crest, logos) load from the install's config bundle. | Two design systems or IQRS-baked apps force per-school app builds and store submissions — an operational cliff that appears precisely at school #2 and blocks every subsequent one. |

## 5. Phase S outline — staged path

Phase S begins only when the overhaul's exit gate is met: Waves 0–6 proven on staging, rolled to production with the owner's approval under the standing staging-first rule, and IQRS operating at the new standard. Sequencing below is deliberately conservative: **sell nothing until the thing being sold is the overhauled system, running twice.**

| Stage | Content | Exit gate |
|---|---|---|
| **S0 — Discovery & legal clarity** *(starts in parallel with late overhaul waves; no build)* | Obtain/audit full web-admin source (D1); document the true install recipe from Wave 0's runbook; **licence review (§1.9)** — licence text, QDOCS written clarification if needed, counsel if still ambiguous; hosting-shape decision (§6: shared hosting cannot operate a fleet — VPS shape costed); draft data-processing terms, school-facing privacy notice and support model. | **G0 — Licence clarity documented** (per-install licensing, vendor SaaS terms, or a stop/pivot decision). **G1 — Full-source confidence:** web-admin tenancy-relevant facts verified, this paper's inferences confirmed or corrected. No commercial commitments before G0. |
| **S1 — Pilot: second school, deploy-per-tenant** | One friendly school (known to the owner, tolerant, preferably small). Provisioned **by the §3.2 script**, on its own subdomain/DB/licence, with its own token set/branding, seed pack from D7 tooling, data migrated with D7 import tools. Run one full term's critical cycles (admissions → attendance → fees → exams) with heightened support. Instrument: provisioning time, defect list, support hours — the real unit economics. | **G2 — Pilot proof:** a full fee cycle and exam cycle completed on the pilot install; provisioning re-run demonstrated (a third throwaway install stood up from the script alone); per-school backup restore demonstrated *for the pilot's data*; pilot school's written willingness to pay / reference. |
| **S2 — Platform layer MVP** | Build only what operating two schools proved necessary: tenant registry + lifecycle (§3.1), provisioning automation hardening, fleet health dashboard + backup verification (§3.7/§3.8), platform operator logins with exactly-scoped roles (§3.4), break-glass support flow with dual audit, subscription record + manual invoicing (billing automation follows real volume, not hope). Custom-domain support (§3.6) if pilot demand exists. | Platform operates IQRS + pilot (+ further schools) with no per-school manual server rituals; every operator action auditable; a new school can be provisioned end-to-end from the platform + script. |
| **S3 — Commercial readiness** | Pricing and plans **decided by the owner** (input, not this paper's output — note the owner's other venture already operates a decided SaaS pricing model with per-country/currency plans, trials and an approver flow; Phase S should reuse that *discipline* — published plans, trial policy, tax treatment — with school-market numbers set by the owner); SaaS billing rails live (§3.5, separate from fee rails); school contract + DPA + SLA-shaped support offer (response targets we can actually meet, status communication, maintenance windows); onboarding pack and admin training materials productised from the pilot; marketing claims limited to what the pilot proved. | **G3 — Owner pricing/plan decision recorded.** **G4 — Commercial gate:** licence (G0) + contract/DPA + billing + support model all in place *before* the first non-pilot school signs. |

Cross-school-group features, if demanded, designed at the platform layer (§2.2). | Ongoing. The §2.3 triggers — not enthusiasm — decide any move toward (ii) or a vendor SaaS edition. |

## 6. Risks & unknowns

| # | Risk / unknown | Severity | Mitigation / where decided |
|---|---|---|---|
| R1 | **Vendor licence does not permit SaaS operation** (or only on terms that break the economics — e.g. full-price licence + vendor SaaS fee per school). | **Existential** | G0 before any commercial step (§1.9, §5 S0). Deploy-per-tenant keeps the per-install-licence path open as the most likely compliant shape. This paper gives no legal advice; the owner obtains the licence text, vendor clarification and, if needed, counsel. |
| R2 | **Shared-hosting ceiling.** One Hostinger shared account cannot operate a fleet: no automation, no per-tenant isolation of resources, no credible backup/health regime, performance contention, one account compromise = all schools. | High | Phase S assumes a hosting-shape change (VPS-class, per the pattern the owner's ERP already runs on) costed in S0; the overhaul itself correctly stays on the current shape for the single school. Fleet size on shared hosting is capped at the pilot, if even that. |
| R3 | **PHP / CodeIgniter 3 ageing.** CI3 is end-of-life-line technology; the vendor's pace of PHP-version support bounds how long installs can stay patched on modern hosting. Every year of fleet growth increases the eventual migration surface. | High (slow-burning) | D9 discipline (additive, patch register) keeps *our* surface portable; S0 records the vendor's current PHP/CI support statement; the §2.3 rewrite trigger exists precisely so this is a planned decision, not a crisis. Do not deepen the fork (another reason (iii) is rejected). |
| R4 | **Data-protection duties multiply per tenant.** As operator for many schools we hold many schools' child data: breach notification, retention/deletion, parent data-subject requests, and per-school DPAs become *our* operational duties, under Pakistan's evolving data-protection landscape and each school's expectations. One school's breach handled badly is every school's headline. | High | §3.7/§3.8 (isolation, provable backup, break-glass audit) are the technical half; S0/S3 produce the contractual half (DPA, retention schedule, incident playbook grown from the Wave 6 runbook). Scorecard #2's gaps (consent, retention, subject rights) become fleet requirements, prioritised in S2 backlog. |
| R5 | **Support burden scales faster than revenue.** Schools need hand-holding at admissions, fee season and results day — simultaneously, across all tenants, on the same academic calendar. A two-person operation can drown in September. | High | Pilot measures support hours honestly (S1); onboarding pack + admin training (S3) deflect the repeatable; support *hours/SLA* are part of the owner's pricing decision (G3), not an unlimited free good. Consider per-plan support tiers at the platform layer. |
| R6 | **Web-admin unknowns.** Print storage, theme seams, session handling, provisioning quirks and any additional single-school assumptions in the web half are currently inferred, not proven (§0). A hostile surprise there (e.g. licence checks phone home per domain) could move costs between options. | Medium–High | S0/G1 closes this before commitments; §2's recommendation was chosen to be robust to plausible surprises (it depends least on web-admin internals). |
| R7 | **Vendor viability / update cadence.** QDOCS could change licensing, pricing or discontinue the line; a fleet amplifies dependence we already have for one school. | Medium | Per-install licensing documentation per school (§3.1 registry); D9 keeps our additive layer inventoried so the *replaceable* parts are known; exit/export duty (§3.7) is owed to schools regardless. |
| R8 | **Fee-season and exam-season load correlation.** All tenants peak together (same national calendar); per-tenant installs on undersized hosting fail together. | Medium | Per-tenant resource sizing from IQRS's own peak measurements during the overhaul; fleet health (§3.8) watches the peaks; hosting shape (R2) must allow per-tenant scaling. |
| R9 | **Scope seduction.** Cross-school dashboards, a marketplace, AI features (audit scorecard #10) will be requested before the basics are fleet-proven. | Medium | §2.2/§5 sequencing is the defence: platform MVP is defined by what two schools *needed*, and new platform features enter via S4's revisit discipline, not via the first persuasive request. |
