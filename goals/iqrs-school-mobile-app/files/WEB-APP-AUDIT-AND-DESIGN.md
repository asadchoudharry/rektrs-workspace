# IQRS Web App — Audit, Benchmark & Design Renewal

**System:** iqrs.edu.pk — Smart School 7.2 (QDOCS) on Hostinger shared hosting: staff admin panel, student/parent portal, vendor mobile API, and the public website.
**Date:** 2026-11-07 · **Audit type:** read-only. No production data, settings or code were changed for this report.
**Evidence base:** (A) code/workflow audit of the vendor backend source, verified byte-identical to the production API copy (`Webservice.php` md5 `4e742290…` in both trees — every code finding below is therefore a finding about production); (B) a 12-dimension international benchmark against PowerSchool / Infinite Campus / Blackbaud-class expectations; (C) design research from Behance/Dribbble-class references; (D) a read-only walk of the live production admin and public site on 2026-11-07, 09:35–09:49 PKT.
**Marking convention:** findings are tagged **LIVE-OBSERVED** (seen on the running production system) or **CODE-DERIVED** (proven from the byte-identical source).

## 1. Executive verdict

**Short answer: No.** As deployed, this software does **not** meet international standards for a school management system in 2026. It is a competent single-school record-keeping and fee-collection tool wrapped in a 2015 interaction model — and it has security defects serious enough that the trust question fails on its own, before design, features or benchmarks are even considered.

Three facts decide the trust answer by themselves:

1. **Student and parent passwords are stored and compared in plaintext.** Login is a direct `WHERE password = ?` string comparison (`Auth_model::checkLogin()`, `User_model::checkLogin()/checkLoginParent()`). The bcrypt machinery exists in the same codebase and is used for *staff* — the largest, least supervised account population (families) is the one left in the clear. **CODE-DERIVED**
2. **The password is returned in ordinary API payloads.** `Student_model::get()` SELECTs `users.password`, and that row is returned wholesale by the profile endpoint and embedded in others (e.g. transport returns the entire student record). Anyone holding any valid login can read credential material. **CODE-DERIVED**
3. **There is no ownership check on `student_id` anywhere in the API (universal IDOR).** Authentication proves only that *someone* logged in; every endpoint then trusts the `student_id` in the request body. Any parent or student token can read any other student's profile, fees, attendance, results and documents by changing one number. Combined with findings 1–2, any logged-in user can harvest other students' passwords by iterating IDs. **CODE-DERIVED**

Around those sit further trust failures: database errors are rendered as full HTML pages (SQL text and table names) in production because of a one-character typo — `'db_debug' => (ENVIRONMENT !== 'prodcution')` in `database.php:18`; API tokens are 10 characters generated with the non-cryptographic `rand()`, valid for a rolling **one year** and renewed for another year on every call; the offline-payment endpoint accepts file uploads with **no validation at all**, storing them under the client-supplied filename; and application logging is switched off (`log_threshold = 0`), so incidents leave no app-side trace. **CODE-DERIVED**

The second verdict is about *use*, not code: **the academic core of the school is unconfigured.** On the live system, all 8 exam groups contain **0 exams** (no schedule, marks entry or report card can be produced for 2025-26), only **2 subjects exist system-wide** (Computer and Computer Practical — no English, Urdu, Maths or Science), and no class timetable is scheduled. Because homework, syllabus status, lesson plans and subject-wise views all INNER-JOIN the `subject_group_*` tables, and no subject groups are configured, those features are **starved by construction** — they return empty lists that are indistinguishable from "nothing was set". **LIVE-OBSERVED + CODE-DERIVED**

The third verdict is about *money honesty*: the fee model stores discounts **inside** the payment record (`amount_detail` JSON), and status is derived from *paid + discount* — so a fee with a Rs 700 discount and **Rs 0 paid** is labelled "Partial", indistinguishable from a real part-payment. This was confirmed live (Tuition Rs 2,400, Paid 0.00, status "Partial"). A display-layer patch shipped 2026-11-07 separates Paid / Discount / Balance on screen, but the stored model — and therefore the API status string every consumer receives — still cannot tell "discounted, nothing paid" from "partly paid". **LIVE-OBSERVED + CODE-DERIVED**

**What is genuinely good:** the breadth of single-school operations is real (fees, exams, HR, transport, library, inventory, front office in one system); the fee *deposit* write is properly transactional; exam results are correctly gated on publication; the notice board enforces publish dates in the model; the web product ships 77 languages including Urdu with a true RTL mode; and IQRS's own additive staff API (built for the mobile programme) demonstrates — on the same framework and database — CSPRNG tokens, session-derived identity, ownership scoping, idempotency keys and an audit log. Every major vendor defect in this report was avoidable within the vendor's own stack.

## 3. Design: why it looks old, and what should replace it

### 3.1 What exactly makes the current design dated

IQRS does not have an old *colour scheme* — it has a 2015 *interaction and component model*, and recolouring it would change nothing that matters. The layers, each evidenced:

- **The stack itself is the tell.** Bootstrap **3.3.5 / 3.3.7** (2013–2016) with the **AdminLTE** skin system (`skin-blue`, fixed left sidebar + top bar, "pick a skin" recolouring), **jQuery 2.2.3** with SlimScroll/FastClick plumbing, and **three icon fonts at once** (Font Awesome, Glyphicons Halflings, Ionicons) where the industry moved to stroke SVG icon sets years ago. Roboto is shipped as a separate `@font-face` family per weight (`.eot/.woff/.ttf/.svg`) — pre-variable-font technique, with no display face, no type scale, and no tabular-numeral discipline for fees/marks. **CODE-DERIVED (local source)**
- **Boxy panels everywhere.** Every module is a bordered rectangle with a coloured header strip, 3px corner radii and hard drop shadows. Modern systems use 12–24px radii, hairline borders and tonal surfaces instead of shadows.
- **Dense small-type tables as the universal answer.** ~35 modules in a dark-blue sidebar; almost every workflow lands on the same full-width DataTable at 12–13px with tiny icon actions (live: icon-only actions with no visible labels), export buttons crowded on top, no density modes, no saved views, no status language a parent can parse. **LIVE-OBSERVED + CODE-DERIVED**
- **Stock 2014 palette, not the school's.** AdminLTE `#3c8dbc` blue, `#008d4c`, `#d73925`, `#e08e0b`, `#00acd6` — unrelated to IQRS navy/gold. The school's identity is applied, if at all, as a logo swap on someone else's product. The live login pages confirm it: a bare form beside a navy branding panel with a small, hard-to-read logo. **CODE-DERIVED + LIVE-OBSERVED**
- **One navigation model for everyone.** A fixed left sidebar serves the Super Admin (300+ functions) and a parent who needs five things, as an undifferentiated tree of system-language module names — no role-shaping, no grouping by job, no command search. Live, it also **buries the two working areas** (student records, fee collection) under dozens of unused add-ons (Hostel, CBSE Examination, Gmeet/Zoom Live Classes, Online Course, Lesson Plan). **LIVE-OBSERVED + CODE-DERIVED**
- **Filter-first friction everywhere.** Three clicks to reach a student list; four steps to an attendance grid; four chained dropdowns before homework can be added; section dropdowns that clear after searching; two "Search" buttons on one page (Income/Expenses); two "Save" buttons on one page (Payment Methods); a destructive Delete button beside Post on the Notice Board; a compose form with no Cancel. **LIVE-OBSERVED**
- **Dated charts.** Heavy gridlines, legend boxes, saturated categorical colours, no direct labelling, no number-first presentation — while the live Dashboard's Income/Expense panels render blank white and its fees chart sits near-flat because the underlying data is empty. **CODE-DERIVED + LIVE-OBSERVED**
- **No dark mode — not even the tokens that would allow one.** Colours are hard-coded hex in component CSS; there is no token layer to invert. In 2026 dark mode is an expectation, and the mobile app already defines a "night navy" theme — web and app diverge the moment a user enables dark mode on their phone.
- **Weak mobile responsiveness where it matters most.** Parents arrive on phones; a responsive-*ish* Bootstrap 3 table that horizontally scrolls a 9-column fees statement is technically responsive and practically unusable. The portal was designed desktop-first and squeezed.
- **Forms that look like database tables.** Label-left/field-right rows exposing the schema, no grouping, no progressive disclosure, no plain-language help, validation as a red banner at the top. This is the single biggest daily-friction item for office staff.
- **Print inherits the chrome.** Marksheets, admit cards, fee receipts and certificates are configured inside the same system and inherit its typography — so the dated look leaves the building on paper, in parents' hands. (The live fees screen even parks a strip of ~28 classmate photos on the page — noise in exactly the wrong place.) **LIVE-OBSERVED**
- **Localisation and spelling debt as a visible quality signal.** "Chasis Number", a section named "Victer (Boys)", designation "Gard", a staff record named "Daily Expence", "COMPLAIN" on the public site, UPI offered in Pakistan. Individually trivial; together they tell parents the system is unmaintained. **LIVE-OBSERVED**

### 3.3 Recommendation — Direction A, executed as "Calm Campus Web"

Adopt **Direction A as the single web design system**, with two governed borrowings: **from C, for the portal only** (greeting-led home, child switcher, week strip, task cards, fee split-bar, attendance ring — all already specified in the approved mobile design system; reuse the specs, don't reinvent them); and **from B, as a mode and a moment only** (the token-derived "night navy" dark theme, and a principal/owner analytics view with B's chart confidence — inside A's components, no glass dependency).

Why A wins, in order of weight:

1. **One system, both audiences, both platforms.** A is the only direction covering data-dense staff work *and* parent simplicity, and it is literally the web extension of the school's already-approved mobile design language ("Calm Campus": navy `#10204D`, gold `#D4AB42`, ivory `#FAF7EF` / warm paper, crest only as a fixed-size circular badge with a gold ring, aspect-locked and never cropped). Anything else re-opens a settled mobile decision and leaves IQRS maintaining three visual languages.
2. **It fixes the actual disease** — the 2015 component/interaction model (tokens, role-shaped navigation, density modes, number-first dashboards, modern tables/forms) — while B mostly re-skins it darker and C mostly avoids the hard screens.
3. **Evidence weight.** The closest functional twins found (whole-school ERP dashboards, 2025–26) and the highest-appreciated Behance school dashboards are A-pattern light SaaS systems. B's anchors are course-admin showcases, not ERPs with fee ledgers and 51 reports.
4. **Trust with money.** Fees are IQRS's most sensitive workflow, including the known discount-display problem: the renewal must present **Paid / Discount / Balance separately** (as the mobile fix already does). Calm, light, bank-like navy/white presentation is the right register; dark glass and playful warmth both undermine it.
5. **Print coherence.** A plus the editorial layer below gives marksheets, receipts and certificates a dignified paper design matching the screens. B would force a second, unrelated print design.

**Identity rules carried into the web system** (consistent with the approved mobile language):

- **Tokens:** navy `#10204D` primary (`#081731` for dark surfaces), gold `#D4AB42` as a *precious* accent (~5% of any screen: crest ring, money CTA, key numerals), ivory `#FAF7EF` editorial/print ground and warm-paper web canvas. The live site's orange `#F58001` is **not** carried forward as a UI colour.
- **Crest:** only as a fixed-size circular badge — white ground, 2px gold ring, aspect-locked, never cropped, stretched or recoloured — at sign-in, headers (small), receipts/certificates and About. Scarcity is what makes it premium. (This is the construction that fixed the mobile crest-clipping bug; the web adopts the same rule, not a looser one.)
- **Type:** Plus Jakarta Sans (headings, display numerals) + Inter (body and all tabular data, with tabular numerals for every fee/marks figure). **Georgia serif is reserved for editorial/print moments** — public-site headlines, portal welcome, certificates, marksheets, report titles — and never appears in tables, forms, buttons or admin headings, where it would cost legibility. This is exactly the reconciliation the approved mobile system already made.
- **Status language:** status always as a labelled tinted chip (text + colour), never a bare dot or a raw system word; gold is an accent, never body text on white; WCAG 2.2 AA contrast is a gate, not an aspiration; ≥48px touch targets in the portal; the token/type system must not hard-code LTR-only assumptions (Urdu/RTL readiness).

### 3.4 What a redesign touches

A credible renewal is not "a new admin theme". In implementation order:

**Phase 0 — Foundation (invisible; everything depends on it).** A design-token layer as CSS variables (colour, radii, shadows, density) mapped 1:1 to the mobile tokens, with the night-navy dark theme derived from the same tokens. A web component library on top of the existing CodeIgniter views: pill buttons, bento cards/tiles, chips, tables (compact/comfortable density, sticky header, summary row, labelled status), forms (label-above, grouped sections, inline help and at-field validation), sidebar (rail/expanded, role-shaped groups — *Today, Students, Money, Teaching, Operations, Reports, Settings* — not the raw module tree), top bar (global search, session switcher, user menu), modals/sheets, toasts, skeleton/empty states, and **one** SVG icon set (Lucide or Phosphor) replacing all three icon fonts. One chart theme (brand + semantic palette, direct labels, minimal grid) applied to the dashboard widgets and report charts.

**Phase 1 — Highest-visibility surfaces.** Both **login screens** (staff `/gauthenticate/login`, student/parent `/site/userlogin`): split layout — navy panel with crest badge and motto (Georgia, ivory) beside a clean form panel; forgot-password included; any 2FA screens restyled to match. This is the school's handshake and should be finished — and photographed — first. The **admin dashboard** rebuilt as bento: Today strip (students/staff present), Money tile (collected today / due, with Paid/Discount/Balance honesty), restyled fees-vs-expense chart, enquiries, library, notices — one datum + context + drill-through per tile, role-filtered as the widgets already are by permission. The **portal home + Fees + Attendance**: greeting and child switcher, attendance ring, week strip, fee split-bar card, notices feed.

**Phase 2 — Working surfaces.** The admin theme applied module by module: Students, **Fees Collection first** (highest daily value), Attendance, Examinations, HR/Payroll, Front Office, Communicate, Library/Inventory/Transport — lists and forms. The legacy "skin" picker is retired in favour of Light / Night Navy / density. The **reports centre**: all 51 reports get the modern table + filter + export pattern and a consistent report header. The **public website / Front CMS**: Georgia editorial headlines, ivory ground, navy/gold — related to the operational apps but distinct (editorial ≠ dashboard), and, per §2, it first needs *content*.

**Phase 3 — Paper and messages (do not skip; parents judge the school here).** Printed outputs: fee receipt (crest-badge header, tabular-numeral money table, Paid/Discount/Balance separated), marksheet and admit-card templates (Georgia titles, calm tables, gold rule), certificates (full editorial treatment), ID cards, and all Print Header/Footer configurations migrated. Email templates (notice, fee reminder, login credentials, results) rebuilt on the token palette with plain-language subjects; SMS templates reviewed in the same pass; PDF/Excel exports inherit report typography so a downloaded statement doesn't revert to 2015.

**Guardrails.** No framework rewrite in the renewal's first release — the CodeIgniter views stay; the win is tokens + components + priority surfaces, and tokens survive a future rebuild. No WebView-style shortcuts or pasting mobile screens into web (or vice versa): shared *system*, native *layouts* per platform. Theme overrides must live in the codebase's custom/override locations wherever it allows, with a documented list of touched core views — otherwise the next vendor update erases the renewal; the override seams should be confirmed against the code before build estimates are promised.

## 4. Improvement roadmap

Every item is tied to a finding in §1–§2. Order within each band is priority order. Nothing in the Quick wins band requires new procurement; the security items in it are configuration/one-line-class fixes whose *risk reduction* is out of all proportion to their size.

### 4.1 Quick wins (days)

**Security & trust first:**

1. **Fix the `prodcution` typo** and force `db_debug = FALSE` in production; put a JSON error envelope in front of the API so failures return clean JSON, never HTML error pages. *(§1, §2.17d)*
2. **Stop returning the password.** Remove `users.password` from the SELECT lists in `Student_model::get()` and `Course_model`'s student query. One change; ends a standing credential disclosure in profile/transport payloads. *(§1, §2.17b)*
3. **Validate the offline-payment upload** through the existing guarded upload path (`handle_upload_file_compulsory`) and store files under randomised names; apply the same randomisation to student documents. *(§2.17g)*
4. **Turn on application logging** (`log_threshold`) so incidents and 500s leave a trace. *(§2.18)*
5. **Remove or neutralise the leftover debug endpoint** (`geeee()`) and the filesystem-path `die()` in document upload. *(§2.17j–k)*
6. **Stop exposing the server path on General Settings** — the full filesystem path and Base Url should not render on a settings page any admin can open. *(§2.1 register, LIVE-OBSERVED)*
7. **Add login throttling** at the application or hosting layer — credential guessing is currently unthrottled against plaintext-compared passwords. *(§2.17f)* Interim mitigation until item 10 lands.

**Data cleanups (operational, no code):**

8. **Create the subject catalogue and subject groups.** Enter the real subjects (English, Urdu, Maths, Science, Islamiat, etc.), build Subject Groups, and map them to every class-section. This single act un-starves homework, syllabus status, lesson plans, My Subjects, subject-wise timetable and subject attendance — eight surfaces at once. *(§2.7, §2.8)*
9. **Configure the examination structure for 2025-26:** create the term exams inside the 8 existing exam groups (dates, subjects, max marks) so schedules, marks entry and report cards become possible at all. *(§2.6)*
10. **Clean the fee-group mess:** consolidate the ~951 per-student "AFM Legacy Arrears" groups into a small, named set of legacy-arrears groups, so fee reporting and the group picker become usable. *(§2.4)* — Do this **before** relying on any fee report.
11. **Clean the HR records:** de-duplicate staff (the doubled Qari Abu Baker / Muhammad Wazir records), replace placeholder phones ("3123456789", sequential numbers) with real ones, remove the expense items recorded as staff ("Daily Expence", "Building Rent" designations), correct roles/designations (guards are not Teachers; "Gard"), and complete the sampled profile gaps (bank details, contract type, work shift) for payroll-critical staff. *(§2.9)*
12. **Backfill student record essentials** — DOB, guardian mobile, category — starting with the classes where they are blank at scale, and resolve duplicate-name ambiguity by always pairing keyword search with class/section in office procedure until item 18 lands. *(§2.2)*
13. **Fix the visible wording debt:** "Chasis Number", "Victer (Boys)", "Gard", "Daily Expence", "COMPLAIN" on the public site, and remove UPI from the payment-mode list for a Pakistani school. Rename the mislabelled Dashboard tile ("Fees Awaiting Payment") or correct its count (2,594 awaiting, not 25). *(§2.4, §3.1)*
14. **Decide the December session-start question** — confirm it is intentional; if not, correct it before the next session rollover. *(§2.1 register)*
15. **Give the public website minimum viable content:** about/admissions/contact pages, real footer links, and the school's actual information — the current "home page" placeholder is the school's public face. *(§2.15)*
16. **Post a first notice and fix the Notice Board layout hazard** — move/confirm-guard the "Delete Notice Board" button away from "Post New Message", and add a Cancel to the compose form. *(§2.13)*

### 4.2 Medium (weeks)

**Security hardening (code, scoped):**

17. **Hash student/parent passwords.** Migrate `users.password` to `password_hash` with verify-on-login and transparent rehash-on-next-login (the `Enc_lib` machinery already exists and staff already use it). Until this lands, items 2 and 7 are mitigations, not fixes. *(§1, §2.17a)*
18. **Enforce ownership in the API.** Derive the permitted student set from the token (student ⇒ self; parent ⇒ own children from `parent_childs`) and reject foreign `student_id`s on every student-scoped endpoint. This closes the universal IDOR. *(§1, §2.17c)*
19. **Replace the token scheme:** `random_bytes`-generated tokens (IQRS's staff extension already uses 256-bit tokens on this stack), a sane idle/absolute expiry instead of the self-renewing one-year window, and a revocation path. *(§2.17e)*
20. **Null-guard the `Student_model::get()` callers** (or return a typed empty object) so a missing `default_login`/session row degrades to a clean 404 JSON instead of an HTTP 500 — keeping the 2026-11-07 data fix but removing the fragility that made 1,680 students break the API. *(§2.3 register)*
21. **Parameterise the raw-SQL hot spots** (fees, chat search, subject list) and remove/neutralise the dead `teacher_subjects` methods before a future route reaches them. *(§2.17h, §2.6)*
22. **Fix the Search Due Fees filter bug** — the report must honour the Class/Section it was given; a school-wide answer to a class question is worse than no report. *(§2.4, LIVE-OBSERVED)*
23. **Fix the homework double-filter** and convert the homework/syllabus/lesson-plan INNER joins to LEFT-JOIN fallbacks, so ungrouped subjects still surface (defence in depth alongside item 8). *(§2.8, §2.7)*
24. **Fix the attendance grid**: remove the 3 unlabelled radio buttons, correct string sorting to numeric, stop the Section dropdown resetting after search, and reconsider the default-all-Absent behaviour (default to unmarked, with an explicit "mark all absent" action). *(§2.3, LIVE-OBSERVED)*
25. **Enforce the profile-edit policy** — have `editprofile()` actually call the existing `checkProfileUpdate()/profileUpdateFields()` gates. *(§2.14)*
26. **Add the change-password endpoint** (current password verified, new password hashed per item 17) and expose it in the apps. Small build, high trust return; specified fully in §5. *(§2.14)*
27. **Give writes idempotency + an audit row**: an actor-stamped audit log for money and record edits, and idempotency keys on insert-first writes (leave, offline payments, visitors, ratings) — the pattern IQRS's staff extension already proves on this database. Also fix the decorative `Leave_model` transactions. *(§2.16, §2.9)*
28. **Rationalise the sidebar**: hide or disable the unused add-on modules (Hostel, CBSE, Live Classes, Online Course, Lesson Plan until configured) so the two working areas stop being buried; label icon-only actions. *(§2.13/§3.1, LIVE-OBSERVED)*
29. **Enable MFA for staff/admin** — the 2FA module exists as an add-on; activating it is the cheapest large security step available after items 17–19. *(Scorecard #4)*

**Design renewal, Phase 0 + Phase 1** (§3.4): token layer + component CSS, both login screens, admin dashboard bento, portal home/fees/attendance. *(§3)*

### 4.3 Structural (months)

30. **Separate discounts from payments in the fee model.** A real discount ledger with amounts, applied against the *fee* (not the collection event), with status derived from *paid only* and discount shown as its own component everywhere — completing at the data layer what the 2026-11-07 display patch started at the screen layer. This is the single most consequential data-model fix in the system: it makes discount reporting, defaulter lists and reminders truthful. *(§1, §2.4)*
31. **Payroll/HR data rebuild, then verification:** after the item-11 cleanup, reconcile staff records against physical files (contracts, bank accounts, CNICs) so payroll rests on verified data; the current records cannot support trustworthy payroll or statutory reporting. *(§2.9)*
32. **A documented backup & recovery regime:** automated daily off-site backups with stated retention, a dated restore drill, and documented RTO/RPO — replacing the current position (no backup code in evidence, no proof a backup has run). *(§2.18, Scorecard #6)*
33. **Design renewal, Phases 2–3** (§3.4): module-by-module admin theme, reports centre, public site rebuild, and the full print/message template family. *(§3)*
34. **An operations runbook that imitates an SLA** (since none exists contractually): uptime monitoring with alerts, patch cadence for the PHP stack, certificate/backup ownership, incident contacts, and a named owner. *(Scorecard #12)*
35. **Privacy programme basics:** a plain-language privacy notice (English + Urdu), per-child photo/consent recording, retention rules that actually delete leavers' data on schedule, and a one-click export/delete path for a departing family. *(Scorecard #2)*
36. **Accessibility remediation:** a WCAG 2.2 AA pass over the portal and login flows first (contrast, keyboard operability, target sizes, accessible authentication), then the admin; publish an accessibility statement. *(Scorecard #3)*
37. **A real API contract:** documented, versioned endpoints with per-integration scoped keys and a contract test between apps and backend — ending the pattern where the vendor's own app calls endpoints that do not exist. *(Scorecard #11)*
38. **Timetable & academic data build-out:** with subjects/groups in place (item 8), build the actual class timetables and lesson-plan data so the academic surfaces have something true to show. *(§2.7)*

**Sequencing logic, stated plainly:** the security fixes (1–7, then 17–19) come before everything else because they protect data the school already holds; the data cleanups (8–11) come before any reliance on reports, payroll or the academic modules because those outputs are currently untrustworthy or empty; the fee-model separation (30) is structural precisely because it must be done once, carefully, with the display patch holding the line meanwhile; and the design renewal rides on top — valuable, visible, and correctly *last* among the trust-critical work.

## 6. Honest limits — what was NOT verified

This report is deliberately explicit about its edges. The following were **not** established by any of the four evidence streams, and no conclusion above depends on them:

- **Load / concurrency performance.** No load testing was performed. Page loads during the live walk were generally quick and search tables took 1–2 s, but peak behaviour (result day, fee deadline, whole-school attendance at 09:00) on shared hosting is unknown. The N+1 patterns found in code (§2.3) are a *risk indicator*, not a measured result.
- **No penetration test.** The security findings are code-proven defects (plaintext comparison, IDOR-by-construction, debug-typo, unvalidated upload path) — they do not require a pentest to be true — but no attempt was made to exploit them against the live system, and the full vulnerability surface (hosting panel, PHP configuration, TLS, other subdomains) is out of scope.
- **Parent panel interior.** The student/parent portal was **not signed into** during the live walk — only its login page was observed. Parent-portal findings are therefore CODE-DERIVED from the byte-identical API/backend source, not LIVE-OBSERVED inside the panel. (The mobile apps exercise the same API and corroborate the functional picture, but the web portal's interior screens were not walked.)
- **Payroll math was not deep-checked.** HR/payroll has no API surface to audit, the web-panel payroll controllers are not in the local source, and the live walk observed records, not computations. The report's payroll conclusion is about **data trustworthiness** (duplicates, placeholders, missing bank/contract fields) — it makes no claim about whether the salary arithmetic itself is correct.
- **Web-panel-only code.** The local evidence contains the mobile/API backend, not the web admin application's own controllers. Workflows that live only in the web panel (admissions processing, payroll screens, the 51 reports' internals, backup/restore) are rated on what the evidence can prove and are marked accordingly; where the inventory lists a function, its *existence* is credited but its *correctness* is unverified.
- **Modules seen but not opened in the live walk:** Hostel, Reports (as a section), Lesson Plan, Online Examinations and QR Code Attendance appeared in the menu but were outside the requested walk; their live state is described only where code or inventory evidence covers them.
- **Backups in practice.** The report states there is no backup code in evidence and no proof a backup has run. Whether the hosting provider's own facilities (e.g. host-level snapshots) are configured was not in scope and is not claimed either way.
- **Benchmark "no evidence" findings** (accessibility artefacts, SSO, retention, OneRoster/LTI/Ed-Fi, AI, RTO/RPO, SLA) are statements about the inventory, vendor documentation and source available on 2026-11-07. If a capability exists in the live installation but is undocumented and undiscoverable, that is itself recorded as a finding for procurement purposes.
- **Benchmark frame.** FERPA/COPPA/GDPR and Ed-Fi/OneRoster do not bind IQRS directly and have no Pakistani state mandate; they are used as the international benchmark the audit was asked to apply — the shape of parent, regulator and partner expectations converging globally — not as claims of local legal obligation.
