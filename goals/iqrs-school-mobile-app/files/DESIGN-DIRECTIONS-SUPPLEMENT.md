# IQRS Web App Renewal — Design Directions Supplement: Five More Directions (D–H)

**Date:** 2026-11-07 · **Companion to:** `WEB-APP-AUDIT-AND-DESIGN.md` §3 (directions A–C, recommendation) and `hidden_files/audit-lane-c-design.md`
**Question answered:** the owner asked for more choice — five *further* design directions beyond the three already researched, each genuinely different in paradigm, not a re-skin.

> **How these five differ from A–C.** A ("Calm SaaS Bento") is a visual/component system. B ("Dark Glass Analytics") is an atmosphere. C ("Warm Human Portal") is an audience posture. The five below each change something more fundamental: **D changes the form philosophy** (one task, one page), **E changes the navigation architecture** (launchpad + floorplans instead of sidebar + dashboard), **F changes the medium the design is modelled on** (the printed document, not the app), **G changes the motivational model** (game mechanics, not information), and **H changes the primary interface itself** (asking, not navigating).
>
> **Identity is non-negotiable in all five:** navy `#10204D`, gold `#D4AB42`, ivory `#FAF7EF`; Georgia serif headlines; the crest only as a fixed-size circular badge with a gold ring, aspect-locked, never cropped or recoloured. Where a direction *wants* to break one of these, the break is stated explicitly, not smuggled in.
>
> **Honesty note on links.** Every primary link below was opened and read during this research (gallery text gives titles, owners, dates and the designers' own descriptions; it does not give every pixel). One secondary item is labelled *search evidence* — seen in search results, not opened. No URL was invented or reconstructed.

## Direction D — "One Thing at a Time" (Public-Service Plain)

**The one-line idea:** Stop designing screens; design *journeys* — every task becomes a short sequence of pages that each ask exactly one plain-language question, end with a check-your-answers page, and confirm with a reference number.

**Reference — what it actually is:**
- **GOV.UK Design System** (UK Government Digital Service) — https://design-system.service.gov.uk/components/checkboxes/ (opened). What the page itself demonstrates is the whole philosophy: the component guidance is written as *rules for not confusing people* — the fieldset legend **is** the question ("Which types of waste do you transport?"), a one-line hint ("Select all that apply"), options ordered alphabetically, nothing pre-selected "because pre-selection makes users submit the wrong answer," and a standing instruction to *start by asking one question per page*. The system's wider pattern library (referenced from that page and from GDS pattern summaries retrieved in search) adds: progressive disclosure (ask the minimum, reveal follow-ups only when needed), an error *summary* that links to each problem field, a check-answers page before any consequential submit, and a confirmation page with a reference number. Visually it is deliberately close to un-designed: one sans (GDS Transport), very large type (19px body is the norm), black text on white, a single green action button per page, thick black-and-yellow focus states, almost no cards, no shadows, no decoration. The DWP Accessibility Manual's interaction-design guidance (retrieved in search: https://accessibility-manual.dwp.gov.uk/guidance-for-your-job-role/interaction-designer) states the rationale plainly: one thing per page "is less disorientating for users and reduces the cognitive load," and is the default *starting* point for every form.
- This is not a gallery concept — it is the most heavily user-researched design system in the world, tested on millions of low-confidence users, and copied by the US, Australian and other governments.

**Translation to the IQRS admin:** The big fee/admission/staff schema-forms (the audit's "forms that look like database tables — the single biggest daily-friction item") are rebuilt as journeys: *Admit a student* becomes ~6 short pages (name → class → guardian → contact → check → done, admission number issued). Fee collection becomes: find student → amount & method on one page → check page showing Paid / Discount / Balance separately → confirmation with receipt number. Attendance is the honest exception (see risk): a 35-name grid is one *task*, so the grid stays — GOV.UK's own service-manual tradition accepts that repeat, rapid, caseworker-style work may group more per page.
**Flex to portal + public site:** This is where D shines brightest. A parent paying or checking fees, a parent submitting an application or a leave request, gets one question per screen, in plain words, with a check page before money moves — the pattern least likely to produce a wrong submission or a support call. The public site's admission enquiry becomes a calm step-by-step form instead of a database grid.
**Identity fit:** Workable but austere. Navy replaces GOV.UK black for headings and the header band; gold is reduced to the crest ring and the focus/confirmation accents; ivory becomes the page ground. Georgia appears only where D allows a display moment — the portal welcome and the confirmation pages. The result is dignified but intentionally plain: the school looks *trustworthy and official* rather than *designed*.
**Effort / risk:** Component layer is the cheapest of all eight directions (fewer components than A). The cost is in the *views*: Smart School's forms are single-page posts, so splitting priority journeys (admission, fees, leave, staff entry) into multi-step flows is real view/controller work — phased, journey by journey, it is theme-plus, not a rebuild. **Usability risk is inverted vs. the others:** for parents and occasional users it is the *safest* direction that exists; for expert office staff doing repetitive entry (a queue of parents at the fee counter) one-thing-per-page can feel slow, and bulk operations (attendance grid, marks entry for a class) must be explicitly exempted or staff will route around the system. Urdu/RTL: excellent — the pattern library is language-agnostic and its plain-language discipline transfers directly.

## Direction E — "The Role Launchpad" (Enterprise Floorplans)

**The one-line idea:** Abolish the universal sidebar-and-dashboard entirely — each role lands on a *launchpad* of live tiles for its own jobs, and every job is executed in one of a handful of standard page types ("floorplans") that repeat across all ~35 modules.

**Reference — what it actually is:**
- **SAP Fiori design system — Layouts, Floorplans and Frameworks** (SAP, opened): https://www.sap.com/design-system/fiori-design-web/v1-84/page-types/floorplan-overview. SAP describes the model exactly: *"the SAP Fiori launchpad is the main entry point. All the apps available to a user are presented as tiles in the app finder, while the home page shows a personalized view of tiles the user has selected"* beneath a persistent shell bar with enterprise search. The floorplan table is the discipline: **List Report** (find and act on a large set of items), **Worklist** ("a collection of items that a user needs to process… the user has to either complete a work item or delegate it"), **Object Page** (display/create/edit one object — *"now the recommended floorplan"*), **Overview Page** (one role's whole domain on a page of cards), **Analytical List Page** (chart + table drill-down), **Initial Page** (a single search field that takes you straight to one object), and **Wizard** (a long or unfamiliar task divided into guided steps). Tiles are not icons — they carry live data (a count, a KPI), and visibility is role-driven by catalogue.
- This is the operating model of the world's largest school-adjacent ERPs (SAP runs universities and ministries); it is a *discipline*, not a theme.

**Translation to the IQRS admin:** The fit to Smart School's actual structure is surprisingly direct, because Smart School is already permission-driven (30 role groups, 234 functions). The Accountant's launchpad shows live tiles — *Collect Fees (today: Rs —)*, *Fees Due (1,643)*, *Approve Offline Payments (7 waiting)* — and nothing else. The 35-module tree disappears into an App Finder. Then the floorplans do the consistency work A has to invent component-by-component: every list in the system is a List Report (same filter bar, same table behaviour), every student/staff/record is an Object Page (header + sections + timeline), every approval queue is a Worklist, admission is a Wizard, and "find a student" is an Initial Page with one search field — killing the audit's "three clicks and two dropdowns before any list appears" complaint *structurally*, not cosmetically. Attendance is a specialised Worklist (process the class, item by item, until the list is empty).
**Flex to portal + public site:** Parents get a *small* launchpad (5–7 tiles: Fees Due with the amount on the tile, Attendance, Homework, Notices, Timetable, Results) — tile-as-answer is even better for a parent than a dashboard, because the number is on the door, not behind it. The public site does not use the launchpad (it stays editorial), but its admission enquiry hands off into a Wizard.
**Identity fit:** Natural. Tiles are the easiest surface in this entire document to brand: navy tile field, ivory cards, gold reserved for the one number that matters (money due, items waiting), crest badge in the shell bar. Georgia stays in its editorial layer (portal welcome, print). The risk to identity is the opposite of F's: Fiori can look *corporate-generic* — the defence is the same token discipline as A.
**Effort / risk:** The largest information-architecture change of the eight short of a rebuild: the navigation shell (launchpad + app finder + shell bar) is new, and 35 modules must be mapped to floorplans and re-templated group by group. It can be phased (launchpad home + Object Pages for students first) and it stays inside CodeIgniter views — but it is a *programme*, not a theme. **Low-literacy risk: low-to-moderate, and interesting** — tiles labelled in job language ("Collect Fees", not "Fees Master") with live counts are *easier* for office staff than a module tree; the risk is the opposite end — power users losing their memorised sidebar paths, and the discipline collapsing if late modules are bolted on as one-off pages. Fiori's own ecosystem warns this only works if the floorplan rules are enforced without exceptions.

## Direction F — "The Ledger" (Editorial Broadsheet, print-born)

**The one-line idea:** Design the system as if it were the school's printed register, report and receipt book — set beautifully: Georgia-led typography, rules and columns instead of cards and chrome, ivory paper, and screens that read like documents a parent would keep.

**References — what they actually are:**
- **Collej.AI — Transforming College Readiness** (Craxinno Technologies, Behance, 2026; opened): https://www.behance.net/gallery/248395849/CollejAI-Transforming-College-Readiness. Stated honestly: this is a pitch-deck and visual-identity system for an EdTech platform, *not* an admin UI. Its relevant, documented design pillar is **"Editorial Typography as Storytelling — oversized, decisive typography carries the narrative arc… each section reads like a chapter, not a slide,"** with a modern sans system set at *editorial scale contrast* and card modules reserved for stats. It is evidence for the identity layer of this direction (public site, reports, portal reading surfaces), not for data-entry screens — the admin translation below is this supplement's extrapolation, labelled as such.
- The second anchor is **IQRS's own paper**: per the audit, marksheets, admit cards, fee receipts and certificates are generated inside this same system and are the artefacts parents actually hold, judge and keep. No other direction treats those as the *source* of the design rather than its last phase.

**Translation to the IQRS admin:** Deliberately restrained. Lists become *registers*: a fees ledger set as a ledger — date and name in text columns, money in tabular figures, hairline rules instead of zebra striping and boxes, totals ruled off with a double rule, the way a printed bahi-khata closes a page. Student and staff records become *dossiers*: a Georgia name heading, a fact table, a timeline written as entries. Dashboards become a *front page*: today's headline numbers set large in serif, a "notices" column, a "today at the school" column. Data entry stays sans and functional (see the divergence note) — the Ledger governs presentation surfaces (dashboards, records, reports, statements), not keystroke surfaces.
**Flex to portal + public site:** The strongest public face of all eight directions. The public website becomes a genuine school prospectus — ivory ground, Georgia headlines, gold rules, the crest badge like a seal — indistinguishable in register from the printed prospectus, which for a school whose motto is "Knowledge. Faith. Excellence." is a real asset. The parent portal's fees statement becomes a document a parent can download, print and file — and it *matches the receipt they already hold*, ending the current screen/paper mismatch the audit flagged.
**Identity fit:** The most natural of all eight — navy/gold/ivory *is* a print palette, and Georgia is already the identity's serif. **But this direction contains the supplement's one explicit divergence, stated plainly:** the approved Calm Campus mobile system *retired Georgia from product UI* (it survives there only in the crest artwork and editorial moments), precisely because serif costs legibility in dense operational screens. Direction F, taken whole, reverses that decision on web — Georgia display type inside dashboards and records. The two products would then embody two different answers to the same question, and a parent moving between the Family app and the portal would feel it. F is coherent only if the school *wants* web = heritage/document face and mobile = operational face, as a deliberate split.
**Effort / risk:** Theme-level and cheap for the surfaces it governs (typography, rules, print templates — much of it is the audit's Phase 3 done first and done properly). The risks are legibility and numbers: Georgia has no tabular-figure discipline for money columns, so fee/marks figures must stay in a tabular sans even inside F (a rule the direction must accept or fail at the fees table), and serif display type at small sizes on budget-phone screens is the first thing low-vision parents will struggle with. **Low-literacy risk: low for reading surfaces** (documents are familiar), **moderate if it leaks into forms**. Longevity: the best of all eight — print registers do not go out of fashion.

## Direction G — "Progress Arcade" (Gamified Dual-Interface)

**The one-line idea:** Make progress *visible and rewarding* — streaks, badges, ranks and subject zones for students; radical at-a-glance transparency for parents; and a deliberately sober toolkit for staff, all as one governed system: motivation is the design material.

**Reference — what it actually is:**
- **NAP Master EdTech Platform — UX/UI Case Study** (Behance, 2026; opened): https://www.behance.net/gallery/248921273/NAP-Master-EdTech-Platform-UXUI-Case-Study-. An Australian NAPLAN-prep platform redesigned around an explicit **"Dual-Interface Philosophy: design for two distinct cognitive levels simultaneously — student view: playful, rewarding, simple; parent insight: data-rich, transparent, actionable."** The documented mechanics: a personalised welcome card; overall progress as a **circular chart** ("the circular badges feel more like achievements" — a direct user-testing quote that changed the design); four colour-coded **subject cards** carrying completion badges ("87%") and a one-click Continue; a **7-day streak tracker with a fire icon**; a badges section; **leaderboard access from the sidebar**; an attendance calendar; and a single-metric performance graph "deliberately kept simple to avoid overwhelm." Its visual system is documented too: dark navy sidebar `#0A1628`, white content, subject-mapped accents, Inter with a 14px minimum, 12px radii, WCAG AA 4.5:1 contrast. Its reported outcomes (designer's figures, unverified by us): sessions/week 2.3 → 5.7, support tickets −73%, parent NPS 34 → 71 — cited here as the *genre's* promise, not as a guarantee for IQRS.

**Translation to the IQRS admin:** It doesn't — and that refusal is the direction. Staff surfaces stay plain working tools (in practice, A's components or D's journeys). What the *admin* gains is the other end of the mechanics: teachers and office staff get the *management* screens for the game layer — which class has the longest attendance streak, homework-completion leagues, badge issuance for behaviour/achievement (the system already has a behaviour-records addon concept). If the owner wants one visual system with no exceptions, G is disqualified by its own logic; it is a *layered* direction — arcade in front of students, instruments in front of staff.
**Flex to portal + public site:** The student-facing portal is where G lives: attendance streaks ("present 12 days in a row"), homework completion rings per subject, term badges, class ranks handled carefully (ranks among *classes* motivate; public ranks among *children* can shame — the reference uses personal progress and opt-in leaderboards, and IQRS should copy that restraint). For parents the same data renders soberly: one circular progress, one streak, one "needs attention" subject — which is also exactly what the reference's parent research demanded ("I never know if my child is actually improving or just busy"). The public site borrows only the energy: achievement showcases, top-of-term celebrations — not game chrome.
**Identity fit:** Surprisingly good
...[truncated 13571 chars] at the base and dangerous at the decoration layer. The reference itself runs a dark-navy sidebar and white content — IQRS navy/gold drops straight in, and gold turns out to be the *perfect* reward colour (medals, badges, the attendance ring the mobile app already draws in gold). The danger is the subject-accent rainbow: G encourages colour-per-subject energy that, unchecked, dissolves the navy/gold discipline into a generic kids-app palette — the pastel-tile drift Lane C already warned dates fastest. Governed (navy structure, gold rewards, subject tints muted and secondary), it fits; ungoverned, it eats the identity.
**Effort / risk:** This is a **feature programme wearing a design direction's clothes**. Smart School holds the raw data (attendance, homework, marks) but has no streak engine, no badge model, no rank computation — those are data builds on top of whatever visual system is chosen, so G's true cost is *A-or-D's cost plus a mechanics layer*, phased over terms. **Low-literacy risk: the lowest of all eight for students and parents** — a ring and a flame need no literacy at all — with two human risks instead: public comparison can shame weaker students (mitigate: personal-best framing, class-level leagues, opt-in), and reward inflation (if everything earns a badge, nothing does). For office staff it changes nothing, which is either its honesty or its irrelevance, depending on what problem the owner most wants solved.

## Direction H — "Ask First" (Copilot Cockpit)

**The one-line idea:** The primary interface stops being navigation and becomes a question — a page-aware assistant panel on every screen that answers from the school's real data in plain language (Urdu included) and *proposes* actions as approval cards, while the classic screens remain underneath for those who want them.

**References — what they actually are:**
- **BidderOps Copilot** (product documentation, updated Oct 2026; opened): https://docs.bidderops.com/features/chat-assistant. A *shipped* B2B product's pattern, documented plainly: the assistant "lives in a side panel on every page of the app" (top-bar button or Ctrl/Cmd+J), "knows which page you are on — ask *'what's overdue here?'*", answers "from your real data" using tools, keeps conversations saved server-side and resumes them across sessions, and — the governance detail that matters — **write actions are never executed directly: "each proposed action appears as a card in the chat with the exact values it wants to write, and nothing happens until you approve it,"** restricted to editor roles. This is the 2026 enterprise-consensus shape of AI in serious software: not a chatbot page, but a supervised copilot layer.
- *Search evidence (not opened):* a screen-recorded Dribbble concept, "Xelio — AI Dashboard," shows the same pattern from the dashboard side — greeting header, KPI row, an "Explore with AI" template gallery (Latency, Cost Optimisation…), and a copilot panel answering "Which workflow has the highest error rate in the last 7 days?" with a sourced, chart-backed reply. Cited only to show the pattern's presence in current dashboard design culture.

**Translation to the IQRS admin:** The panel sits over A's (or D's) screens — H is a *layer*, and it still needs a designed system beneath it. Its killer uses in a school office are real: "Which students in Class 6 still owe October fees?" → a list, with a proposed action card *"Send fee reminder SMS to these 14 parents"* awaiting approval; "Show today's absentees whose parents haven't been informed" → list + notify card; a teacher asks "Who hasn't submitted the maths homework?" instead of learning the homework module's four-dropdown ritual. The audit's deepest admin complaint — 35 modules of system language between staff and answers — is the exact problem this pattern exists to dissolve.
**Flex to portal + public site:** For parents this is potentially the most humane interface of all eight: "Meri beti ki is month attendance kya hai?" typed (or spoken) in Roman Urdu/Urdu, answered with the attendance ring and one line of text, beats teaching a low-literacy parent *any* navigation model — including C's. On the public site it becomes an admissions assistant answering fee/timing/transport questions at 9 pm. Both uses are also where the risk concentrates (below).
**Identity fit:** The *surface* fits trivially — the panel is a navy sheet with the crest badge as the assistant's avatar, gold confined to the approval action; visually it can be pure Calm Campus. The *divergence is interactional, stated explicitly:* the approved mobile apps have no such layer, so web would lead and mobile would follow later, or the products diverge in capability. Unlike F, this divergence is additive (a layer on top of the same tokens), not contradictory.
**Effort / risk:** **Rebuild-tier — the only direction here that is not achievable as design work on Smart School 7.2.** It requires an AI service, a permission-respecting data-access layer, and an actions framework with audit trails. Three hard gates, all from this audit's own findings: (1) **Security first, non-negotiably** — an assistant querying a database whose API currently leaks passwords and checks no record ownership (Lane A) would industrialise that leak; H is unsafe until the audit's §2 security fixes are done and verified. (2) **Money truth** — a language model that misstates a fee balance destroys trust faster than no app at all; every figure must come from deterministic queries with the answer's source shown, and writes only ever via approval cards. (3) **Cost & language** — per-query cost at 1,668-student scale, and Urdu/Roman-Urdu quality varies by model; both need a pilot, not a promise. **Low-literacy potential: the highest ceiling of all eight, and the highest floor if it hallucinates.** Verdict inside the direction: a Phase-3 ambition to design *towards* (the token system and approval-card pattern can be reserved now), not a renewal candidate today.

## Closing note — does any of the five beat Direction A for *this* school?

**Plainly: no. Direction A ("Calm Campus Web") still stands as the system to build**, and researching five more paradigms strengthened rather than weakened the reasons in audit §3.3: IQRS needs *one* design language across admin, portal and the already-approved mobile apps; it must be buildable on CodeIgniter views without a framework rewrite; and it must keep money looking like money. None of D–H satisfies all three — D is a philosophy without a component system, E is an architecture that still needs A's components inside its floorplans, F governs only presentation surfaces, G is a feature programme, and H is a layer that must sit on top of a system like A (and is unsafe until the security fixes land).

What the five *do* change is the borrowing list. Lane C already had A borrowing C's portal patterns and B's dark mode. This supplement recommends **two more governed borrowings, adopted into A now**:

1. **From D — journey discipline for every parent-facing and money-moving flow.** One thing per page, plain-language questions, error summaries, a check-answers page before any fee is confirmed, and a confirmation with a reference number. This is a direct, evidence-backed attack on the audit's worst form findings, and it costs little inside A's forms work.
2. **From E — the Worklist as a named pattern in the admin.** "Items waiting for you" queues (unmarked registers, offline payments to approve, enquiries to follow up) as first-class home-screen citizens with live counts — the launchpad's single best idea, adoptable as tiles on A's bento dashboard without buying the whole Fiori programme.

And two are recorded as **future layers, not current candidates**: G's mechanics as an engagement programme for the student portal once the base renewal is live (its data layer can be specced independently), and H's copilot as a Phase-3 ambition, gated on the audit's security fixes, with its approval-card pattern reserved in the component library from day one. F, finally, needs no separate adoption: its entire value — Georgia, ivory, the ruled and dignified document — is *already* A's editorial/print layer; choosing F wholesale would add only the one thing A deliberately refused, serif inside operational UI, at a real legibility price.

If the owner's instinct pulls toward any single one of D–H as *the* direction, the honest costs are in the table above — but the recommendation of record remains A, now better-armed.
