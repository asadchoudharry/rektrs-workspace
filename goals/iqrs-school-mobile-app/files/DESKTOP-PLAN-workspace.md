# IQRS Workspace Desktop — Detailed Implementation Plan

**Product:** IQRS Workspace Desktop — an offline-first desktop application for the teachers, staff and admin of IQRA REHMANIA TUL ATFAL HIGH SCHOOL, mirroring the delivered Workspace Android app's design and behaviour, with full offline access: all online data available offline in a local database, and offline changes syncing back to iqrs.edu.pk.

**Owner decision:** approved by Assad, 2026-11-10 — *"tafseeli plan banao, Workspace Desktop pehle"* (detailed plan; Workspace Desktop first, Connect Desktop later).

**Status of this document:** PLAN ONLY. No code has been written, no server contacted for this plan, nothing deployed. Every factual claim below is grounded in the planning team's evidence files (27 lanes: source censuses of the Android app and the server API, a toolchain proof executed in this VM, the production schema read from actual DDL dumps, and per-domain design work). Lane files live in `hidden_files/desktop-plan/wave-a|wave-b|wave-c/` beside the goal's `files/` folder; section references like *(census C §6)* point there.

**Production scale (the design point):** 1,682 students · 110 staff · session 2025-26 · Smart School 7.2 (PHP/CodeIgniter + MySQL/MariaDB) on Hostinger **shared** hosting — no VPS, no daemons; all sync is plain HTTPS REST.

## 1. Executive summary + scope

### 1.1 What we are building

A Windows desktop app (JavaFX 17, same Java stack as the Android apps) that a teacher or office user installs once, signs into with their existing staff login, and then **keeps working with no internet**: student master, class registers, homework, notices, fees, marks — read from and written to an encrypted local SQLite database on the PC. Whenever a connection exists, the app pulls what changed on the server and pushes what was done offline, using the sync machinery the Android app already proves in production (the outbox + `Staffsync` idempotent endpoints), extended with one new server family (`Staffpull`) for delta downloads.

The Android Workspace app is already offline-*tolerant* (a raw-JSON read cache + a proper write outbox). The desktop is offline-*first*: a real queryable local database, a full student-master sync (which the phone deliberately never does), offline search, offline fee collection with a money-safe overlay, offline marks entry with persistent drafts, and local printing — none of which the phone has today.

### 1.2 Why this shape (the three findings that decided the design)

1. **The push side already exists.** `Staffsync.php` carries **34 idempotent write endpoints** (not the ~16 remembered from Wave 1A — it grew through Waves 2A/2C-A), each keyed by a client-minted `client_txn_id` with a proven claim/duplicate contract in `api_sync_log`. Every write the desktop v1 needs maps to an existing endpoint (§6.2). The server build is therefore concentrated on the **pull** side, which does not exist at all today (0 of 118 Staffapi endpoints accepts a `since` parameter).
2. **Delta pull is cheap because the database already maintains cursors.** From the actual production DDL (phpMyAdmin dumps, staging ≡ production): ~50 in-scope tables carry `created_at` + `updated_at … ON UPDATE current_timestamp`, so a generic `(updated_at, id)` cursor engine works almost everywhere. The proven exceptions are narrow: **marks** (`exam_group_exam_results.updated_at` has no `ON UPDATE`), `feetype`, `staff_designation`, `expenses`, and **hard deletes** anywhere (handled by tombstones + id-set reconciliation, §6.1).
3. **The toolchain is proven, with one physical dependency.** JDK 17 + JavaFX + SQLite + jpackage all compile/run/package in this VM today (§2). The single hard external dependency is a **designated Windows machine**: `.msi` installers, DPAPI, and real-printer verification can only be proven on Windows, and that machine does not exist yet (§11, §12).

### 1.3 Scope — Workspace Desktop v1

**In scope (58 screens in D1+D2 of the 71-row inventory, §7):**
- Shell: sign-in, app lock (PIN), home/dashboard, module catalogue, profile, Waiting/Conflicts.
- Students: full-master browse + **offline search**, detail/family view, edit (online via a new version-checked sync twin).
- Attendance: full register (all types, past dates, corrections) + QR attendance — **fully offline**, with per-student conflict handling.
- Homework (compose/list/detail/evaluate), notices (board/compose/edit/delete), timetable, syllabus + lesson plans, calendar, tasks, my leave — offline per §7.
- Fees: collect fees **offline** with pending-payment overlay + provisional receipts + cash-up; dues/statement/receipt views; finance income/expense.
- Exams & marks: catalogue/detail, **offline marks entry with persistent drafts**; publish/rank stay online-only by design.
- Library, transport assignment, front office (enquiries, visitors, call/postal/complaint books), inventory, staff directory, certificates & ID cards, reports.
- Local printing: official PDFs via `staffapi/fileOpen`, locally rendered ID cards and provisional receipts, print profiles mirroring the web Print Studio (THERM-80 / A4).
- Packaging: per-user MSI, self-update via `staffapi/appVersions`, pilot at the school office on 3 PCs.

**Out of scope for v1 (named, with the reason):**
- **Connect Desktop** (family app) — later programme per the owner's sequencing; only a scoping note is produced (D3-7).
- **Approvals offline** — leave reviews, bank-payment review, rating moderation are *never queued*, permanently: a decision must be taken on current facts (the Android app's standing doctrine, honoured). Queues remain browsable offline; only the decision needs a connection.
- **Setup saves offline** — fee/exam/transport/inventory/staff setup stays online-only in v1 (structure online, operations offline); the five small exceptions (twin endpoints) are listed in §6.2.
- **Hostel and staff online classes** — they do not exist in Workspace (no screen, no endpoint); not a port, would be a new product build.
- **Staff-attendance marking, student admission-create** — no endpoint exists anywhere; not promised.
- **Offline binary uploads** (photos, documents) — online-only in v1; a staged-upload protocol is a v2 project.
- **SQLCipher** — v1 ships app-managed full-file encryption (§8); SQLCipher is a gated v1.1 migration.
- **Custom Rektrs fee tables** (`afm_*`/`cf_*`/`pkfp_*`/`bfp_*`) — real production data that no API reads; whether desktop fee views are complete without them is Open Question OQ-1 (§13). D2's fee estimate assumes vendor tables suffice or the custom tables join read-only.

**Standing build rules inherited from the proof:**
- **Gradle/Maven-free, forever.** The VM's Java-socket-reset defect kills build-tool daemons; every step is a foreground `javac`/`java`/`jpackage` process and every dependency is a **curl-vendored, SHA-256-pinned jar** — exactly the Android pipeline's discipline.
- **Headless UI tests use Xvfb.** Monocle is *not* available in the stock OpenJFX jars (`ClassNotFoundException`) — do not plan on it. (This VM's image also lacks `libXtst.so.6`; the proof worked around it with a locally extracted .deb + `LD_LIBRARY_PATH`. VM-only quirk — irrelevant on Windows/stock Linux.)
- **Build sequentially under `~/workspace`** (137 GB free), not `/tmp` (512 MB tmpfs). The VM is CPU-throttled (wall ≈ 5–10× CPU time) yet everything completed: javac ~15 s, FX run ~28 s, jpackage ~56 s for the proof.

## 3. Architecture

### 3.1 System shape

```
┌──────────────────────── IQRS Workspace Desktop (Windows, JavaFX 17) ───────────────────────┐
│  UI layer            JavaFX screens (§7) on the ported design system (§4)                   │
│  Domain layer        Repositories per domain (students, attendance, fees, …) reading the    │
│                      local DB ONLY; compose screens write domain rows + outbox intents      │
│  Sync layer          Push engine (outbox, FIFO, Staffsync) · Pull engine (Staffpull         │
│                      cursors, bootstrap, reconciliation) · Waiting/Conflicts service        │
│  Store               ONE encrypted SQLite file per login profile (§5, §8) + photo/PDF file  │
│                      cache under the profile folder                                         │
│  Transport           ApiClient (HttpURLConnection, the Android app's exact request shape)   │
└──────────────────────────────────────────┬─────────────────────────────────────────────────┘
                                           │ HTTPS REST (iqrs.edu.pk/api/…)
┌──────────────────────────────────────────┴─────────────────────────────────────────────────┐
│  Server (Smart School 7.2, Hostinger shared hosting — additive files only, no vendor edits) │
│  staffauth/login (+logout, expired_at) · Staffapi (existing reads) · Staffsync (existing 34 │
│  idempotent writes + tombstone patches) · Staffpull (NEW: 20 delta/bootstrap endpoints) ·   │
│  api_app_versions (NEW table: appVersions incl. the desktop slot)                           │
└─────────────────────────────────────────────────────────────────────────────────────────────┘
```

### 3.2 Load-bearing design decisions

1. **The local DB is the only read source.** After bootstrap, no screen waits on the network. Screens read typed local tables (not the Android raw-JSON cache, whose exact-key fragmentation is why the phone's offline mode only works for screens previously opened online). Pull refreshes tables in the background; a screen never blocks on it.
2. **Every write is an outbox intent or is declared online-only.** A write either (a) lands in the outbox with a `client_txn_id` minted once and persisted *before* first send, to be delivered by the push engine to a `Staffsync` endpoint; or (b) belongs to the explicit online-only set (approvals, publish, setup saves) and its screen disables the action offline with the reason in plain words. There is no third kind of write.
3. **One writer.** A single SyncService owns the only read-write DB connection (WAL, `synchronous=NORMAL`); UI windows read and submit intents. This kills the multi-window write races a desktop app invites and a phone never has.
4. **Server-wins for master data; human-resolves for contested operational data.** Pull overwrites local master rows — except rows referenced by pending outbox items, which are protected by the pending guard (§6.1) until their writes resolve. Conflicts that need a person land in the Waiting/Conflicts surface (§6.3), never in a log file.
5. **Additive server work only.** New controller (`Staffpull.php`), two small extension tables (`sync_tombstones`, `sync_marks_dirty`), one app-versions table, and ~120 patch lines inside *our own* Staffsync/Staffapi files. No vendor file is edited; the one vendor-table schema change that would help (marks `updated_at`) is an owner decision (OQ-2), not an assumption.
6. **Per-login profiles on shared PCs.** Each staff login gets its own encrypted DB under `%LOCALAPPDATA%\IQRS Workspace\profiles\<staff_id>\`. One profile open at a time; a machine-wide single-instance lock; nothing personal roams (DPAPI is machine-bound, so the data must not roam either).

### 3.3 The sync engine (both directions, one service)

- **Push** (§6.2): strict FIFO, one request in flight, Android's proven backoff (0 s / 30 s / 2 m / 8 m / 10 m), triggers = enqueue / app start / connectivity return / 15-minute tick / manual. Response classification is exact: transient claim (`__PENDING__` < 5 min) and transport failures retry under the *same* txn id; a stored `status:0` parks as NEEDS_ATTENTION and is never auto-retried; 401 pauses the whole run and preserves the queue.
- **Pull** (§6.1): per-table cursors `(updated_at, id)` with a 60-second overlap and client-side dedupe by PK; triggers = startup (if > 5 min stale), 15-minute interval, post-push (families mapped from the pushed kind), reconnect, manual. Bootstrap is the same endpoints with `cursor: null` — resumable per page, in order: handshake/catalogues → student/staff masters → structure → current-session transactions → hash/id-set/tombstone baselines.
- **Reconciliation**: tombstones for deletes made through our API paths; daily id-set hash checks for master entities (catches web-admin deletes); per-exam marks hash checks (§6.1). Attendance is never id-set-reconciled (no delete path exists; targeted register re-pull on open is the mitigation).

### 3.4 What "offline" honestly means here

Bootstrap and first login require a connection. After that, a teacher can run a full school day offline — registers, QR scans, homework, notices, fee collection, marks — and everything syncs when the connection returns, with conflicts surfaced per student/row for a named human. What offline never does: approve anything, publish results, change setup, or show data fresher than the last pull (every screen that shows money or marks carries its "as of" state from the pull ledger).

## 5. Local DB schema (per domain)

One SQLite file per login profile (≈115–125 unique tables in total; 138 `CREATE TABLE` statements across the design files including shared bookkeeping defined once and referenced by several domains). Full DDL lives in the six `wave-b/schema-*.md` files; this section is the map and the rules that bind them. Two cross-domain rules apply everywhere: **(R-DB-1)** every mirrored entity carries `server_id` + `server_updated_at` + `fetched_at`, and pull writes only server columns — never pending state; **(R-DB-2)** offline-born rows are real rows (`local_id` PK + nullable `server_id` + `create_txn_id` + `sync_state`), not just outbox payloads, so screens read one consistent store.

### 5.1 Master data (`schema-master.md` — 22 tables + FTS + bookkeeping)

`sessions, classes, sections, class_sections, subjects, subject_groups, subject_group_subjects, subject_group_class_sections, student_categories` (catalogues, full-refresh unit) · `students` (the full union field set: staff detail + the 25-field edit whitelist + family `ProfileDetails` depth where staff-plausible; credential fields explicitly excluded), `students_fts` (FTS5 over name/admission/father/guardian/phone) + `students_search_aux`, `student_custom_fields`, `student_sessions` (enrolment per session — **prior sessions kept, frozen read-only**, ~170 KB/session), `guardians` (locally deduplicated — no server guardian id exists; dedupe on phone+name) + `student_guardians` · `staff`, `staff_roles`, `class_teacher_assignments`, `teacher_subject_assignments` · per-login snapshot `current_user`, `user_capabilities`, `user_scope_sections`, `user_module_flags` · `enquiries`, `enquiry_follow_ups` (negative local ids + `client_txn_id` for offline creation) · `photo_cache` (metadata only — **photos are files, never BLOBs**: 288 px centre-cropped, SHA-1-named, lazy by default; full pre-fetch is an optional ~20–34 MB resumable job under a 50 MB LRU cap). **Size: ~4–5 MB per login** (budget 8 MB with WAL/headroom). Feeding endpoints mostly exist (`academicCatalog`/`classes`/`capabilities` full-refresh unit; `staffDirectory`/`me`; `enquiryList`/`enquiryDetail`); the one blocking new feed is the student-master pull (P1, §6.1).

### 5.2 Attendance (`schema-attendance.md` — 15 tables + 2 views + 2 triggers; DDL executed and smoke-tested by the lane)

Reference: `attendence_type` (server spelling preserved), `staff_attendance_type`, `holiday`. Snapshots: `att_class_section`, `att_roster_current` (the register never depends on the Students domain), `att_register_snapshot`/`att_register_student` (verbatim register ingest per class+section+date). **Two-layer marks:** `att_mark` (server-confirmed replica) + `att_mark_local` (pending overlay: type, remark, source register/qr/manual, marked_by, marked_at, `client_txn_id`, base-server capture); the view **`att_mark_effective` is the only permitted read path** (pending wins; conflict falls back to server value + `has_conflict` flag) — this is the structural fix for Android's stale-after-save gap. Sync expansion: `att_sync_batch` + `att_sync_batch_record` (per-student PENDING/SAVED/SKIPPED/CONFLICT outcomes). `att_conflict` (per-student, attempted-vs-server, named resolutions incl. requeue-under-new-txn), `att_audit_log` (append-only via triggers, 24-month minimum). **QR:** `att_qr_mark` written **at scan time in the same transaction** as batch + outbox + overlay (Android writes it only on delivery — the rescan hole); dedupe key normalised (`SID:`/`ADM:`/`RAW:`) under `UNIQUE(session, date, key)` + a partial unique index on the resolved student to catch card-vs-typed rescans. Retention: current + previous session in full; pending/conflict-open rows are never pruned.

### 5.3 Fees & finance (`schema-fees.md` — 23 tables + 1 view; DDL executed and overlay smoke-tested by the lane)

**Money rule (§0 of the design, overrides everything): all money is `INTEGER` paise** — never `REAL` (Android's `double` + whole-rupee rounding is a defect this fixes); amount/paid/discount/fine are always four separate figures; assessed fine is never recomputed locally. Tables: `fee_sync_state` · reference (`fee_types`, `fee_groups`, `fee_session_groups`, `fee_group_lines_ref`, `fees_discounts`, `student_fees_discounts`) · `fee_invoice_masters` + `fee_invoice_lines` (the `feeInvoice` snapshot — the only collectable unit) + `fee_deposit_entries` (`amount_detail` JSON normalised per `inv_no`, Σ-invariants checked per pull) · `fee_statement_snapshots`/`fee_statement_lines` · `fee_payment_history` (server receipt identity `invoice_id`/`sub_invoice_id`) · **`fee_collections_local`** (the authoritative collections ledger, 1 row per outbox `fee_collect`) + `provisional_receipt_seq` · `household_fee_summary` (written only when `is_complete=1` — all children in one pull batch, honouring the all-or-error rule) · `offline_bank_payments` (view-only; review stays live-only) · `finance_heads` + `finance_entries` · `payroll_payslips`/`payroll_components` (view-only) · `cashup_daily_totals` + `fee_reconciliation_issues` (8 named issue codes; `EFFECTIVE_NEGATIVE`/`LINE_VANISHED` block collection on the line; nothing is auto-corrected). The **overlay** itself is specified in §6.3 (money). Transport fee lines are statement-view-only — no `feeCollect` door exists for them (named gap).

### 5.4 Exams & marks (`schema-exams.md` — 17 tables)

Mirrors (setup is web/Staffapi-only): `exam_group`, `exam` (incl. cached `is_publish`/`is_rank_generated`), `exam_subject` (max/min marks, date/time/room), `exam_student` (roster in payload order; **`exam_student_id` is the save key**; name/roll/class denormalised so the grid renders with no cross-domain join). `marks_entry` = last server-known mark/absence per (subject, exam-student); NULL = not entered, never an invented 0. `exam_schedule_entry` (date-sheet projection). Snapshots: `grade_band` + `division_rule` (the `school_grade_system` scale exactly as `examCatalog` delivers it, wholesale-replaced per pull) and `exam_result_snapshot`/`exam_result_subject` (**server-computed** totals/percentage/grade/division stored verbatim — the desktop computes nothing official; this also fixes Android's uncached staff result sheet). **Drafts:** `marks_draft` + `marks_draft_entry` (raw `entered_text` verbatim + parsed value + row state; autosaved per edit — process death loses at most a keystroke) with txn rules R1–R6 (§6.2). `marks_refusal` is append-only (verbatim server reason + refused value + lineage) and mirrored onto the draft entry so refusals re-present under the field, by student, in the server's words, across restarts. Publish freshness is persisted (`exam_publish_check_run`): any cache-sourced count = FAILED ⇒ publish blocked.

### 5.5 Homework / lessons / communication (`schema-homework-comms.md` — 22 tables)

`homework` (built on the exact 7-field create payload; max marks arrive only via `homeworkUpdate`) · `homework_submission` (modelled as the roster it is — one row per class student, upsert key `(homework, student)`, so resubmissions work) · **`homework_evaluation`** (the bulk grid's own staging: drafts first, then one local transaction mints N outbox items — one `homeworkEvaluate` per student, own UUID each; per-item delivery/parking; a partial unique index enforces one live evaluation per submission; a resubmission supersedes, never silently retargets) · `syllabus_subject/lesson/topic` (with `server_covered` vs persisted `local_covered` override + `cover_txn_id`) · `lesson_plan` + `lesson_plan_comment` · `timetable_snapshot` + `timetable_period` (one table set serves class and teacher views; no date/period-number concepts exist upstream) · `notice` + `notice_edit_draft` + `notice_version_conflict` + `notice_local_state` · `calendar_event` · `staff_task` · `content_type`/`shared_content`/`shared_content_file` (metadata + paths only — **no file bytes or base64 ever stored**). The **teacher pre-download bundle** is data, not code: `offline_bundle`/`offline_bundle_step` with a 10-step spec (scope from classes/catalogue/capabilities → per-section timetables + syllabus trees → homework list → **per-homework detail+submissions, the load-bearing step: no submissions fetch = no `submission_id` = offline evaluation impossible** → lesson plans by date range (default −7 d…+14 d) → notice details for editable notices → calendar +30 d → tasks → content metadata). ### 5.6 Sync core + remaining modules (`schema-sync-core.md`)

`outbox` — the faithful `pending_writes` port (`client_txn_id TEXT UNIQUE CHECK 8–64`, kind, payload_json, summary, state, attempts, backoff fields, server_response) + justified desktop additions (`endpoint` frozen at enqueue, `next_attempt_at`/`state_changed_at`, `depends_on_txn_id`/`local_ref` for FK chains, `created_by`). `sync_state` (per entity: cursor_kind ∈ updated_at/full_refresh/exam_reconcile/none, the `(cursor_value, cursor_id)` pair, 60 s overlap, bootstrap state + snapshot watermark, schema version, server session) + `sync_meta`. `conflicts` — generic parent/child (batch → per-record diagnosis; types `ATTENDANCE_SKIPPED`, `MARKS_REFUSED`, `NOTICE_VERSION`, `STORED_REFUSAL`, `DEPENDENCY_BLOCKED`, `PULL_OVERLAP`). `audit_log` — two grades in one append-only table (triggers block updates and AUDIT-grade deletes): FEED (Android parity, pruned 90 d) and AUDIT (attendance/marks/fees + all refusals/resolutions, old→new values captured at compose time — back-filling forbidden; never auto-pruned in v1). ## 6. Sync protocol

### 6.1 Pull — the new `Staffpull` family (server build, D0)

One new additive controller, `POST /api/staffpull/*`, behind the **same** two gates as Staffapi (client headers vs `Auth_model`, then `User-ID` + token vs `api_staff_sessions`) plus the same capability and class-scope rules. **20 endpoints:**

| Group | Endpoints |
|---|---|
| Utility (3) | `manifest` (server_time, entitlement, per-table counts/max-cursors — also the Cloudflare probe target) · `tombstones` (catch-up) · `idSet` (generic id-set + SHA-256, `known_hash` short-circuit) |
| Families (17) | `catalogues` (full-refresh, ~21 tables) · `students` (students incl. guardian columns + `student_session`) · `staff` (+ role link-sets, leave balances) · `attendance` (student + staff, windowed) · `fees` (structure + masters + deposits + discounts + offline/transport) · `homework` (+ submissions/evaluations) · `notices` (+ roles, keeps the `version` alias) · `exams` (structure/assignments) · `marksHash` · `marks` · `timetable` (+ syllabus/lessons/forum) · `library` · `leave` · `frontOffice` · `contentCalendar` · `finance` (income Δ + `expenses` full-refresh section) · `extended` (transport/inventory/behaviour/HR extras/certificates) |

**Contract (every endpoint):** per-**table** cursors `"<updated_at>|<id>"`, `ORDER BY updated_at, id`, **60 s overlap window** with client dedupe/upsert by PK, the cursor never advances to `server_time`; envelope `{rows, next_cursors, has_more, server_time, tombstones, next_tombstone_cursor}`; limit default 500 / max 1000; **column whitelists** (no `staff.password` ever; the vendor `users` table is never pulled); a scope-hash change forces scoped families to re-bootstrap. Snapshot/bootstrap mode = the same endpoints with `cursor: null` (existing Staffapi reads are *not* reused as sync sources — 0/118 accept `since` and almost none return `updated_at`; they remain the live-read sources for online-only screens).

**Marks — the one delta-blind money-grade table.** `exam_group_exam_results.updated_at` has no `ON UPDATE` clause and no code stamps it, so corrections are invisible to any cursor. Design: **(a) hash reconciliation as the correctness floor** — `marksHash` returns a SHA-256 over `(exam_student_id, get_marks, attendence, note)` per (exam, exam-subject) pair; a mismatch triggers `marks` to replace-pull that pair only (roster-bounded, ≤ ~135 KB worst case), triggered by exams-structure changes, register open, and a daily sweep; **(b) a Staffsync dirty-marker** (`sync_marks_dirty`, upserted by `examMarksSave`) as an accelerator only — (b) alone is rejected because web edits bypass Staffsync. The other blind tables are tiny or bounded: `feetype` (2 rows) and `staff_designation` (23 rows) full-refresh inside `catalogues`; `expenses` full-refresh section inside `finance` with a 5,000-row escape threshold to hash reconciliation. The one-line `ALTER TABLE … ON UPDATE` that would make marks exact is **OQ-2, an owner decision** (vendor-upgrade drift risk) — assumed nowhere in this plan.

**Deletes — two layers.** *Layer 1:* a new extension-owned `sync_tombstones` table (global sequence = tombstone cursor, 90-day retention), written **inside the delete transaction** by our own paths only (Staffsync `noticeDelete`/`homeworkDelete`/`taskDelete`, Staffapi `contentDelete`), delivered embedded per family + via the `tombstones` endpoint. *Layer 2:* **id-set reconciliation** for vendor-web deletes our code cannot see — sorted ids + count + SHA-256 with a `known_hash` short-circuit, daily-at-startup / weekly forced, scoped to **master entities only** (students, student_session, staff, fee masters, deposits, homework, notices, events, shares, books/issues, exam assignments, enquiries/visitors — the whole set < 200 KB, ~0 bytes when hashes match). Full-refresh tables and marks pairs converge by absence/replace and need neither layer.

**Bootstrap sizing (from the 2026-11-06 production dump — a floor; the apps have written since):** today ≈ **4.2 MB raw JSON / ~15,400 rows** (students 1.26 MB; fees + discounts ≈ 2.4 MB; attendance/exams/homework/library were 0 rows at dump — the web system was then operating student records + fees, the rest is app-created now). Guards: attendance bootstrap is capped to a **stored 31-day window** (~52k rows ≈ 6.2 MB at steady state vs ~330k rows/yr unbounded; older dates lazy-backfill per register on open); **marks rows are never bootstrapped** (hash baseline only, per-pair pull on first open); steady-state first sync ≈ **10–11 MB**. Per-page transactional commits make an interrupted bootstrap resume from committed cursors, never from zero. Roster photos are a separate resumable background job (25–40 MB), never part of pull.

**Client pull engine:** per-entity state in `sync_state` (cursor, last_full_refresh, schema_version, scope_hash, hash_state, backoff); merge is server-wins **with a hard pending guard** — rows referenced by pending outbox writes (attendance rows, fee deposits, marks pairs) are never overwritten; their server versions wait in a deferred shadow store until the write resolves; deposits additionally re-diff the `amount_detail` JSON client-side per changed row. Backoff 30 s → 15 min; 401 pauses all sync; > 90 days offline forces re-convergence. **Cloudflare guard probe (launch-critical):** production sits behind Cloudflare bot-signature checks (curl passes; Python urllib got 403). The desktop client must pass an unauthenticated probe — POST expecting the API's **401 JSON**, where a **403 HTML page halts sync with no retry storm** — using an explicit non-default User-Agent and the Android app's exact request shape (its `HttpURLConnection` with no custom UA passes in production). This probe is a D0 deliverable; staging has no such check, so production proof cannot be borrowed from staging.

**Server build shape:** `Staffpull.php` ≈ 2,800–3,600 lines (generic engine ~600 + per-endpoint configs/shapers) + ~40 lines DDL + ~120 patch lines in our own files; zero vendor files edited; staging-first with a named battery (§11, D0 gate) whose key case is: *mark corrected via direct SQL → hash mismatch → `marks` converges*.

### 6.2 Push — Staffsync reuse + gaps

**All 34 existing idempotent writes are mapped; no v1 write strictly requires a new endpoint.** Every write takes `client_txn_id` (string 8–64) in the JSON body; the server `INSERT IGNORE`s it into `api_sync_log` (UNIQUE on the key **alone — global across endpoints and users, and replay is not re-checked against endpoint or payload**, so the desktop must mint true UUID v4s), stores `__PENDING__`, and replaces it with the final response on any deterministic outcome. Re-POSTing a finished key returns the stored response verbatim + `duplicate:true` and never re-executes — **stored failures included**; a fresh (< 5 min) pending answers "already being processed"; a stale (≥ 5 min) pending is released and re-executed; internal DB failures delete the claim so the same key may safely retry. HTTP 200 for nearly everything; business failure is `{status:0, message}` and is **permanent for that key** — corrections need a new txn id. There is **no batch envelope and no status-query endpoint**: 1 outbox change = 1 POST, and identical re-POST is the only outcome-recovery mechanism. Only `attendance` (`records[]` → `saved` + `skipped[]`) and `examMarksSave` (`entries[]` → `saved` + `refused[{id, reason}]`, marks never clipped) are partial-success — and both return `status:1` even when everything was skipped/refused, so **the client must inspect the counts, not `status`**.

**Reuse map (by family):** attendance ×2 (`attendance`, `qrAttendance`) · homework ×4 (`homework`, `homeworkUpdate`, `homeworkDelete`, `homeworkEvaluate`) · notices ×3 (`notice`, `noticeUpdate` — the only endpoint with optimistic concurrency, via `version` — `noticeDelete`) · fees (`feeCollect`, + `feeInvoice` read helper) · marks (`examMarksSave`) · leave (`myLeaveApply`) · front office (`enquirySave`, `enquiryFollowUpSave`, `visitorCheckIn`, `visitorCheckOut`, `taskSave`, `taskDelete`) · learning (`syllabusTopicStatus`, `lessonPlanSave`, `lessonPlanCommentSave`, + `lessonSave`/`topicSave`) · library (`libraryIssue`, `libraryReturn`) · finance ×4 (`incomeSave`, `expenseSave`, `incomeDelete`, `expenseDelete`) · inventory (`inventoryIssue`, `inventoryReturn`) · transport (`transportAssign`) · behaviour (`behaviourAssign`). Classification: **22 Class A** (Android already queues them correctly) · **7 sync-safe but unqueued/promotable** (below) · **5 the Android app never uses** (`visitorCheckIn`, `lessonSave`, `topicSave`, `incomeDelete`, `expenseDelete`). One ruling: **`visitorCheckIn` is the single visitor door** — `visitorSave` is a duplicate door with an identical contract; using both double-registers visitors.

**Client-side fixes (no server change; desktop requirements from day one):**
- **DR-MARKS-1…5 — the critical one.** The endpoint is Staffsync and idempotent, but the Android client posts marks *live* via `postAction`, has no `exam_marks` outbox kind, keeps drafts in memory only, and **re-mints the txn id on every Save tap** — defeating duplicate protection exactly when a response is lost. Desktop: outbox kind + persisted draft with the txn id minted **once at draft creation**, persisted with the draft, keyed by `(exam_id, exam_subject_id)`; an edit to a never-answered queued draft follows `revise()` (key kept); an edit after a *stored final answer* mints a **new** key (`supersedes_txn_id` + `revision_no`), because re-sending a refused key only replays the stored refusal.
- **DR-PLAN-1…3:** `lessonPlanSave`/`lessonPlanCommentSave` carry txn ids but are sent live — desktop queues them; a comment on an undelivered plan stays held-local until the plan's ack supplies the server id (no placeholder ids exist server-side).
- **Class B promotions** (endpoint sync-safe; Android sends live with fresh txn ids): `libraryIssue`/`libraryReturn` (availability + member auto-create are judged **at push time**; return date = server push date; no fine exists), `behaviourAssign` (session pinning + pair scope at push; points are server-computed), `transportAssign` (ids must exist at push; charges are web-generated downstream; still-WAITING assigns for the same student coalesce in place under the original txn id).

**True server gaps — the complete list, with rulings (sync-push §4):**
- **Costed twins (claim wrappers over existing Staffapi logic, each with a duplicate-replay battery):** `studentUpdate` twin in **D0** (version-checked, mirroring `noticeUpdate`; enabled by returning the already-stamped `students.updated_at` in the student read — `studentPhoto` stays online-only in v1, Staffsync carries no binary) · `itemStockSave`, `callLogSave`, `postalSave`, `complaintSave` twins in **D2**. Fallbacks if any twin slips: the screen ships online-only under its stated rule (stock-in: single live attempt, **no auto-retry ever**).
- **Online-only permanently (doctrine, not backlog):** leave reviews (`studentLeaveReview`, `staffLeaveReview`), `offlinePaymentReview`, rating moderation — approvals are never queued (a queued approval decides on a stale snapshot; the money case is stronger). `examPublish`/`examRankGenerate` — online-only under the PublishGate (live completeness counts or no publish).
- **Online-only in v1, twins are v2:** fee setup ×5 (`feeGroupSave`, `feeMasterLineSave`, `feeDiscountSave`, `feeGroupAssign`, `feeDiscountAssign` — v1 is structure-online/collection-offline), exam setup ×6, transport setup ×5, `staffSave` (its twin is preconditioned on adding an `updated_at` stamp; create-with-password stays live even in v2), inventory masters ×4, `complaintStatusSave`, `staffTimelineSave`.
- **Absent everywhere — not in v1:** student admission-create, library book/member catalogue saves, staff-attendance marking, incident-type catalogue saves, timetable/class/session setup, and **reversals** (no undo endpoint exists for feeCollect/attendance/libraryIssue/behaviourAssign — corrections are new writes, as on the web).

**Protocol rules (P1–P7, binding on the client):** 1 change = 1 POST · strict FIFO, one in flight, Android backoff · **topological ordering with ack-id rewriting** for FK chains (lesson→topic→plan→comment; enquiry→follow-up; visitor in→out; homework create→update/evaluate; notice create→update carrying `version`) — every FK must be a real server id, there is no temp-id support · ack inspection (counts, not `status`) · unknown outcome recovers **only** by identical re-POST · stored `status:0` = permanent NEEDS_ATTENTION (payload defects may be revised under the same key; state conflicts = discard + new key; QR items are discard-only) · true-UUID discipline (global namespace) · last-writer-wins everywhere except `noticeUpdate`'s version · server stamps times (visitor in/out, library return) — nothing can be backdated · the 5 Phase B writes + `feeInvoice` have **no server capability gate**, so the desktop enforces permissions in its own UI from the capabilities snapshot.

### 6.3 Conflict policy (per data class)

Owner rules applied, not re-litigated: master data = server wins · attendance/marks sync with audit trail + in-app conflict list · offline fees = provisional receipt, final number on sync. Detection reality: the server detects almost nothing (only `noticeUpdate` has a version), so the desktop adds **pre-push re-read + three-way diff** (base = what the compose screen loaded, local = the queued change, server = fresh read) for the classes that need it.

| Data class | Resolution headline | Resolver |
|---|---|---|
| Students / master | Auto-server-wins; local edits are drafts, never auto-pushed; a superseded draft is shown once + audit-logged | — (admin informed) |
| Attendance | Split push: clean students client-wins-with-audit; contested students (3-way diff) park. Approved/Medical Leave marks pre-default to "keep school's" | Marking teacher; admin after end-of-day escalation |
| QR attendance | Scan-time `(code, date)` local guard; Present-vs-Present converges; QR-Present vs a differing register mark parks | Class teacher / admin |
| Marks | Split push mirroring attendance; `refused[]` reasons honoured verbatim; a **published exam is a hard stop** — everything parks | Entering teacher; exam coordinator for others' |
| Fees — collection | Provisional receipt at capture; final ref on ack; money is never auto-clipped or adjusted — stale-balance cases park (apply-as-partial / refund-at-desk) | Cashier; admin for re-point/void |
| Fees — setup | Online-only, never queued; fresh-read + `affects_students` confirm sheet; changed-under-you blocks the save | — (live) |
| Homework + evaluate | Create = client-wins-with-audit; same-field edit/evaluate contests park; delete with a grown submission count parks with a plain-words cascade warning | Homework owner |
| Notices | Server `version` refusal parks with the 3-way diff — **never auto-rebased**; delete gets a desktop pre-push version re-read guard (the server checks nothing on delete today) | Creator / admin |
| Lesson plans / syllabus | Topic toggle = client-wins-with-audit, never parked; plan overwrites get informational entries; dependency chains display as blocked-by, not conflicts | Plan owner |
| Leave | Apply = client-wins-with-audit (it is a request; local overlap warning only). Approve = online-only, fresh-read at confirm; already-decided shows the decider | Approver (live) |
| Library | Push-time availability refusal **is** the detection; refusal parks with **no override** (physical truth); return-date honesty — server date and capture date both shown | Librarian |
| Inventory | Over-issue refusal parks, never auto-partialled; setup online-only (`itemStockSave` = highest double-apply risk in the system) | Store keeper |
| Transport | Contested assignment parks (child-safety stakes); setup online-only | Admin / transport in-charge |
| Front office | Enquiries/follow-ups + visitors = client-wins-with-audit inserts; checkout refusal = informational park; call log/postal/complaints online-only in v1 (twins in D2) | Front-office user |

**The duplicate-money argument (why offline fee collection is safe — 5 layers):** **L1** the server's `api_sync_log` txn claim closes replay (proven in production today). **L2** the desktop **local overlay** closes same-device double composition — the Android hole (it would happily queue two full-balance collections) is closed by construction: the collections ledger + overlay are written in the same `BEGIN IMMEDIATE` transaction as the outbox row, and compose validates `amount + discount ≤ effective_balance`, so after a full-balance collection the line shows Rs 0 / *Settled (pending)*. **L3** pre-push `feeInvoice` revalidation parks a push whose line has since settled (e.g. via bank-payment approval). **L4 — the residual simultaneous-push race** (two cashiers, two devices, same line, same minute) is closable **only** by a server in-transaction balance guard in `feeCollect`, which Wave A evidence does **not** show to exist: it is requirement **R-5**, costed in D0 as verify-then-build, and it is the **launch gate for multi-cashier offline collection** (single-cashier operation is fully safe on L1–L3; until R-5 ships, the admin UI must carry that honesty notice). **L5** `amount_detail` entries are append-only, so any double landing is visible and reversible, never silent. On ack, amounts move pending → `acked_unconfirmed` (balance unchanged) and become CONFIRMED only when a later pull's `amount_detail` diff shows the matching entry (`inv_no` = final `sub_invoice_id`); on NEEDS_ATTENTION the overlay contribution **stays** with a blocking "money held — do not collect again" banner and the server's verbatim reason; release is only via audited supervisor discard or a corrected re-issue under a new txn id.

**Undetectable-today register (R-1…R-11, conflict-policy §8) — what the server cannot currently tell us:** R-1 marks corrections (→ §6.1 hash substitute; the ALTER is OQ-2) · R-2 attendance overwrites indistinguishable from saves in the ack (desktop workaround: 3-way diff; server per-record outcome list is future work) · R-3 homework update/delete/evaluate have no version · R-4 notice delete has no version check · R-5 feeCollect balance guard (→ D0) · R-6 Class C writes have no txn id or precondition (reviews need `seen_status`) · R-7 pull itself + delete visibility (→ §6.1, in scope) · R-8 no `updated_by` anywhere — the UI must say "changed on the school system", never invent an author · R-9 QR ack doesn't reveal an overwrite · R-10 session-rollover skips carry no reasons · R-11 publish/lock state is absent from the marks roster (refusals are the only authoritative signal). Only R-5 and R-7 are built in this plan; the rest are handled by the named desktop workarounds and recorded here so nobody mistakes them for solved.

## 8. Offline auth + encryption

**Server reality (from `api-vendor-auth.md`):** `POST /api/staffauth/login {email, password}` against the `staff` table (bcrypt); the token is `bin2hex(random_bytes(32))` stored in `api_staff_sessions` with a **fixed 8,760 h (365-day) expiry, no sliding renewal, no refresh, no logout/revoke endpoint, no device binding, unlimited concurrent sessions** (phone and desktop never disturb each other). Every API call re-checks the token pair + `is_active`. The token is therefore a long-lived, unrevocable bearer secret — Android stores it in **plaintext** SharedPreferences; the desktop must do better, and this design does.

**Credential + key architecture (two-layer wrap — neither layer alone suffices):**
- A random 256-bit **DEK per profile per PC** encrypts the database. The DEK is wrapped twice: **outer** by Windows **DPAPI CurrentUser** (via vendored JNA + jna-platform `Crypt32`, `CRYPTPROTECT_UI_FORBIDDEN`, entropy bound to app + staff_id) — binds the data to this Windows user on this machine; **inner** by a **PIN-derived KEK** (PBKDF2-HMAC-SHA-256, 600k iterations, JDK built-ins) — separates staff who share one Windows login, which DPAPI alone cannot do. PIN alone is rejected (offline-brute-forceable); encrypted-file alone is rejected (the key has no home); Java KeyStore PKCS12 is rejected (a second store-password UX and the file travels).
- **The token lives only inside the encrypted DB** (additionally AES-GCM-sealed in `iqrs_meta`) — no plaintext file or registry copy anywhere. The profile descriptor (`profile.json`) holds no secrets: staff_id, name/role, email, client-recorded `login_at_utc`, derived `derived_expires_at = login + 8,760 h`, `warn_at = login + 335 d`, `urgent_at = login + 350 d`, salts, wrapped-DEK blobs, attempt counters. The server never returns `expired_at` — derived values are UX only; **the 401 is the authority**; clock-backwards is handled explicitly.
- DPAPI failure = refuse to enrol/unlock, never a silent downgrade. An admin-reset Windows password orphans DPAPI → `RECOVERY_REQUIRED` enrolment-loss path with a held-work warning (§8, never-strand).

**Unlock (AppLock ported and hardened):** PIN **mandatory, ≥ 6 digits** (passphrase offered for Admin/Accountant roles); the PIN is **cryptographic** — dual domain-separated salts (verifier vs KEK), and GCM unwrap failure is the truth, not a digest comparison. Persisted failed-attempt backoff: 5 → 30 s, 7 → 2 m, 9 → 10 m, 10+ → 30 m — **never wipe-on-failures** (anyone at the keyboard could otherwise destroy undelivered fee collections). Forgotten PIN: online re-login + a DPAPI-only **recovery wrap** restores the DEK and re-wraps under a new PIN — the outbox survives (the recovery wrap is policy-disableable, with the data-loss consequence stated on screen). Lock triggers: idle timeout (default 5 min on Shared PCs, no "Never" there), Ctrl+L/manual, and a time-gap heuristic for OS lock/sleep in v1 (JNA `WTSRegisterSessionNotification` is a v1.1 spike). **Windows Hello is honestly out of v1:** no Java SE/JavaFX Hello API exists; `UserConsentVerifier` is WinRT, releases no key, would need a signed native helper, and verifies the *Windows* user — the wrong identity on a shared account. Post-v1, personal laptops only.

**Session lifecycle:** first login is online-only; then PIN setup → DEK → DB → first snapshot. Expiry UX: the expiry date is always visible in Profile; amber daily-dismissible banner 335–350 d; persistent 350–365; red at 364. Renewal = one online re-login that replaces only the token row and resets the dates — DB, PIN, DEK and outbox untouched; early renewal is always allowed (recommended at session start). Expired **while offline** → `UNLOCKED_EXPIRED_OFFLINE`: read + queue new writes (labelled held; fee receipts print PROVISIONAL), no sync except one probe on reconnect. **401 mid-sync mirrors Android:** the whole pass pauses (persisted), the in-flight item returns to WAITING unpenalised, FIFO + txn ids preserved, a "Sign in to send" card shows, and re-login resumes automatically. A disabled-account message → `DISABLED_HOLD`, never a wipe. A Cloudflare 403/HTML response is explicitly **not** routed into the 401 flow.

**Sign-out is three different actions** (defaults driven by a per-PC Personal/Shared declaration): **Lock** · **Sign out (keep)** — Android parity, token cleared, data kept · **Sign out & remove my data (wipe)**. **The never-strand rule is mechanical:** wipe is *blocked* while the outbox is non-empty — online, you sync first (any NEEDS_ATTENTION still blocks); offline, you Lock instead, or produce a **verified encrypted handover bundle** (AES-GCM, one-time code on a printed receipt, checksum re-read, supervisor name logged) before wipe is enabled. There is no "delete anyway". Other staff on the same PC see only a held-count badge for a profile with pending work — never its contents.

**Encryption at rest — the honest v1 choice.** Evaluated against the proven toolchain (stock xerial sqlite-jdbc is plain; jars are curl-vendored and pinned): **(A) SQLCipher for JDBC** is the best end-state, but Zetetic's official JDBC driver is **Enterprise/paid and not on Maven Central**, and the free route is a single-maintainer fork (`sqlite-jdbc-crypt`) that lags the proven driver and is unproven in this pipeline. **(B) Field-level encryption is rejected** — it structurally misses exactly where the sensitive data lives: the JSON payloads (`payload_json`, cache JSON, summaries). **(C) v1 ships app-managed full-file AES-256-GCM** (64 KiB chunks, per-chunk nonce/tag) over the stock proven driver: decrypt on unlock, `journal_mode=DELETE` (no plaintext WAL sidecars), verify-then-atomic-rename on re-encrypt at lock, the profile folder additionally EFS-encrypted to cover the transient plaintext window, and a crash-leftover sweep on start. Its weakness is stated plainly: during an unlocked session the working file is plaintext (protected by the profile folder + EFS + the lock discipline). **SQLCipher is a gated v1.1 migration** with a 5-check spike (hexkey open; 330k-row battery; jpackage/AV behaviour; migration of an outbox-bearing DB; a named owner for the fork) — the DEK/wrap/PIN architecture is deliberately unchanged by that migration. Attachments, photos and handover bundles are per-file AES-GCM under HKDF(DEK) subkeys in all options.

**Revocation (lost laptop) — runbook + one small server addition.** No revoke endpoint exists, so the plan carries an admin runbook (~10 min, site-scoped phpMyAdmin via Websites → iqrs.edu.pk → Manage site → Databases): snapshot `SELECT * FROM api_staff_sessions WHERE staff_id=?` for audit, then `DELETE` — targeted only if the lost device's `created_at` row is confidently identifiable (the table has **no device/IP/UA column**), otherwise delete all rows for that staff member (their phone simply re-logs in); verify with a curl 401 guard probe; if the account itself is compromised, also set `staff.is_active=0` + change the web password (a password change alone does **not** kill tokens). Leaver flow must check shared PCs for held work **before** disabling an account — a disabled account cannot flush its own outbox. **In plan scope (D0, P1, not a v1 blocker):** additive `POST staffauth/logout` (deletes the caller's own session row) + `expired_at` in the login response; phase-2 (not costed): a `device_label` column + admin session list/revoke. Refresh tokens, sliding renewal and device enrolment are explicitly **not** proposed.

## 9. Printing

Android has **no printing at all** (no `PrintManager`, no client PDF; receipts are screen copies and share-text) — this subsystem is greenfield, aligned to the web's Wave 3 Print Studio and owner decision D5 (THERM-80 + plain A4 defaults; DUPLICATE marking always-on, no off switch). One internal print service serves everything: **AWT `java.awt.print.PrinterJob`** (the JavaFX Printer API was evaluated and rejected as primary — no PDF input, driver-mediated paper sizes unreliable at exact millimetres, unproven in the toolchain proof).

| Document class | Pipeline | Submission |
|---|---|---|
| Official fee receipt (A4), marksheets, admit cards | Fetch via `staffapi/fileOpen` → **PDFBox `PDFPrintable`, `ACTUAL_SIZE`, no silent shrink** | Print dialog |
| Certificates (A4 landscape) | Same PDFBox pipeline | Dialog |
| ID cards 86×54 mm (official PDF) | Same pipeline on an exact 86×54 mm paper — scaling forbidden, pre-flight paper check within 0.5 mm; fallback = locally rendered card | Silent-after-confirm (per batch) |
| Thermal 80 mm counter slip + provisional receipt | **Locally rendered** (AWT Graphics2D painter from structured receipt data) — never a scaled-down A4 PDF | Silent, only to a named test-print-validated thermal printer |

**Known gap (non-blocking, logged):** `fileOpen` has no profile parameter today, so the server's THERM-80 rendering cannot be fetched — a `profile=THERM-80` parameter is an open server item; the local thermal painter is the v1 answer regardless, because the provisional receipt can only exist locally.

**Offline printing:** locally rendered **student/staff ID cards** (from local master data; QR `IQRS-<id>`, barcode = admission no.) and the **provisional fee receipt** — fixed banner *"PROVISIONAL RECEIPT — payment recorded, receipt number not yet issued"* + the canonical `PROV-…` ref (§7.1) + Amount/Discount/Fine/Total as separate lines. After sync the record adopts the final `invoice_id[/sub_invoice_id]` (the PROV ref stays as a secondary identifier); a reprint after sync headlines the final ref, is stamped **DUPLICATE**, and offers the official A4 PDF as the preferred reprint; a NEEDS_ATTENTION delivery marks the provisional **void** in the ledger and no further copies print. Fee statement/dues prints from local data carry a mandatory *"Position as last updated …"* footer. **Online-only for a first print:** official fee_receipt / marksheet / admit_card / certificate / official ID-card PDFs, report CSVs, stored documents — a connectivity failure creates a **"Waiting to print"** job (a server `file:null` *refusal* never queues — its reason shows verbatim); on reconnect, jobs fetch → cache → A4 jobs wait for **one consolidated operator confirmation (never auto-print)**; silent thermal jobs may auto-print; jobs waiting > 7 days are flagged, not deleted.

**PDF cache (a deliberate divergence from Android's never-cache):** BLOBs inside the per-login encrypted DB, keyed by the exact `fileOpen` parameter set, SHA-256 + fetch metadata recorded; 10 MB/file cap, 250 MB/login cap with class-ordered LRU eviction. TTLs by mutability: fee_receipt = **no TTL** (immutable historical document, reprintable offline — DUPLICATE is handled at job/ledger level because official bytes are never altered); marksheet/admit_card = 7 days (a `published` flip stales them); certificate/ID/documents = 30 days; report CSV = 7 days with its own generated-at stamp. The confirm sheet always states the saved copy's date and prior print count.

**Profiles (mirroring Print Studio):** local-only `print_profiles` — web paper policy (paper kind from a closed list, mm dimensions, orientation, margins, scaling rule) + workstation binding (exact Windows printer name, submission policy, copies, `validated_at` from a **mandatory test print** — unvalidated profiles cannot go silent). Seeded: `THERM-80` (silent), `A4-PLAIN` (dialog), `A4-LANDSCAPE` (dialog), `CARD-86x54` (silent-after-confirm). Profiles never sync (printer names are per-desk facts); kind→profile routing is constrained so a card can never route to the thermal profile; a vanished printer stops the job with a plain reason — **no silent reroute to the Windows default printer, ever**.

**Failure honesty:** the UI/ledger distinguish **"Sent to <printer>"** (spooler truth) from **"Printed"** (operator-confirmed only). Batches are one PrinterJob per document for precise resume; a mid-batch paper-out/offline pauses at the named failing item with a three-way operator question — Yes (mark confirmed, resume next) / No (reprint, no duplicate stamp) / Not sure (reprint flagged possible-duplicate) — and resume never restarts from item 1; a crash treats in-flight items as outcome-unknown. An append-only print ledger (`print_jobs`/`print_job_items`) feeds all counts. **Dependency:** the school's physical printer hardware confirmation (D5) is still pending — the design works unbound/dialog-only until then, and D2's printing battery needs the real hardware (§12).

## 10. Packaging + auto-update

**Build location: a dedicated Rektrs Windows PC** (`IQRS-DESKTOP-BUILDER`). Evaluated honestly: the school/office PC is rejected as a builder (dirty environment, a production machine — it stays a mandatory *test* target); GitHub Actions `windows-latest` is deferred to Phase 2 (clean and reproducible, but recurring cost and a departure from the team's proven local scripted pattern). All scripts are non-interactive and CI-portable for a later lift-and-shift. **Pins:** Temurin JDK 17.0.21 on both hosts; **WiX Toolset 3.11.x only** (JDK 17's jpackage needs `candle.exe`/`light.exe`); sqlite-jdbc 3.47.1.0 + slf4j-api 2.0.16 with the proof's SHA-256s; `-win` jar checksums are captured at first fetch in Gate W0 and committed — never invented in advance. SQLCipher is not vendored for v1 (§8).

**Installer decisions:** **MSI only for v1**; `--win-per-user-install` (load-bearing: silent auto-update with no admin/UAC); `--win-upgrade-uuid` generated once at D0 and **frozen**; `versionName` strictly `x.y.z` (MSI ProductVersion); the desktop `versionCode` starts at 1 as an independent sequence (Android Workspace is 31 / 2.18 — do not conflate). **Gate W0** — the 7-step smoke build on the actual Windows machine (clean-profile silent install, upgrade-over-install, Windows 10 **and** 11) — must pass **before any installer date is promised**.

**Distribution (v1, single school):** versioned, immutable files at `https://iqrs.edu.pk/downloads/workspace-desktop/` (uploaded via SSH/rsync) + `install-guide.pdf`; D0 verifies MSI mime type, `Content-Length` and range-resume on the real Hostinger hosting. First rollout is seeded **in person via USB**; an intranet share is allowed only as a reinstall mirror; Store/email/GitHub Releases are rejected as school-facing channels. Multi-school later = the same school-agnostic installer, central/per-tenant hosting, per-site version rows giving natural rollout rings.

**Auto-update — extending `staffapi/appVersions`:** today the table doesn't exist, so the endpoint honestly answers `configured:false` and the (fully wired) Android notice machinery stays inert. Additions, all additive: **(a)** `appVersions()` recognises a `desktop` slot and returns 5 extra fields **on that slot only** (`installer_url`, `installer_sha256`, `installer_size_bytes`, `published_at`, `grace_days`) — existing `connect`/`workspace` payloads stay byte-identical (Familydocs remains connect-only, regression-checked); **(b)** the F5 `CREATE TABLE` as already specified + one `ALTER TABLE` adding those 5 columns; **(c)** a release SOP: the MSI is uploaded and externally verified (size + SHA-256 vs `release-manifest.json`) **before** the row is updated; canary on 1–2 office PCs for 24–48 h before the row bump; the floor (`min_supported_code`) is raised only in a later post-soak edit, never with the shipping edit; **lowering the floor is the instant kill-switch**. **Client behaviour:** check after session restore/sign-in + every 24 h + manually; silent background download to `%LOCALAPPDATA%\IQRS Workspace\updates\staged\`; size + SHA-256 verified **before** anything counts as staged (the checksum arrives via the authenticated API, the bytes via the public host — channel separation; HTTPS + school-host allowlist only; downgrade offers ignored); install-on-restart via `msiexec /passive /norestart` hand-off with a 1-attempt anti-loop rule. The decision table mirrors Android's R5 (`NONE`/`AVAILABLE`/`REQUIRED`) extended with grace: below `min_supported` → non-dismissible notice during `grace_days` (default 7, from persisted first-seen), and a blocking screen after grace **only if the installer is staged** — if it cannot download, a logged one-day offline pass applies, so **the school is never locked out of fee work by its own internet outage**. **Bootstrap (D0):** the Rektrs API/deploy lane (not the school office) creates the table + ALTER + endpoint change staging-first, inserts the `desktop` row plus `connect`/`workspace` rows set to the live Android codes (re-read from `iqrs-app-v2/config/*.properties` at execution time), and passes a **blocking Android regression battery** (no card at current builds; crafted rows prove AVAILABLE/REQUIRED) before any of it repeats on production. Known v1 limitation, stated: the update check needs a staff session (same as Android); the escape hatch is the public download page + install-over-the-top.

**Rollback & local-DB discipline:** roll-**forward** only (revert code, bump code+patch, republish) — the updater never downgrades. Local DBs carry `schema_meta` + `PRAGMA user_version`; migrations are forward-only and additive, run in transactions, with **backup-before-migrate** (WAL checkpoint + copy, keep last 3, auto-restore + recovery screen on failure); a downgrade guard refuses newer-schema DBs; and a fixture gate proves pending outbox rows (including fee provisional receipts) survive every migration byte-for-byte in payload terms.

**Code signing: v1 ships unsigned — deliberately, with a priced trigger.** Unsigned reality, stated plainly: SmartScreen's *"Windows protected your PC / Unknown publisher"* + *More info → Run anyway* on manual installs; per-user install avoids UAC but not SmartScreen; every new binary hash starts reputation-cold; self-signed improves nothing unless pre-trusted per PC. OV certificates (≈ USD 130–440/yr — SSL.com low, Sectigo mid, DigiCert high; prices checked 2026-11-10) show "Rektrs (Private) Limited" but reputation still builds over time; EV (≈ $290–685/yr) is rejected (its instant-reputation advantage has been materially reduced). V1 instead spends on: an illustrated English/Roman-Urdu SmartScreen install guide, the authenticated-channel checksum discipline, and a signtool step built into the pipeline **from build #1** (env-gated) so adopting OV later is custody/config only. **Trigger to buy OV: the second school's onboarding, or the school reporting friction — recorded at D0.** Microsoft Trusted Signing is flagged as an unverified-eligibility Phase-2 evaluation only. **macOS/Linux:** later only — per-OS jpackage builds (Linux app-image is already proven on this VM); no v1 dates, and nothing in v1 forecloses them.

## 13. Open questions for Assad (3 — only what genuinely needs him)

**OQ-1 — The custom fee tables (blocks D2's fee scope, nothing else).** The production database carries Rektrs' custom fee-module tables (`afm_*`, `cf_*`, `pkfp_*`, `bfp_*`) with real data, and no API — vendor, Staffapi or Staffsync — reads them. Desktop fee views are designed against the vendor fee tables (the same tables the web Collect Fees and the apps use). **Question:** is any part of a student's *true* fee position (a plan, a family account balance, a posting batch) kept *only* in those custom tables? If yes, D2 needs a small read-only discovery lane first and its fee estimate is re-done; if no, D2 proceeds exactly as costed. (A two-hour read-only sampling of the tables' DDL + a few rows would also answer it — say the word and it runs as part of D0.)

**OQ-2 — The marks `ALTER TABLE` (optional improvement, plan works without it).** Marks is the one money-grade table whose `updated_at` never moves, so desktop marks sync uses hash reconciliation (exact, but a whole exam-subject pair re-pulls on any change). A one-line `ALTER TABLE exam_group_exam_results MODIFY updated_at … ON UPDATE current_timestamp()` in a future release window would make marks a plain cursor sync like everything else. It is a change to a **vendor** table: small, reversible, but a vendor upgrade could silently revert it. **Question:** approve it as a future release item, or leave marks on the hash design permanently? The plan assumes *no* until you say yes.

**OQ-3 — The two physical dependencies (gate D1/D3 scheduling, cost nothing to answer).** (a) **Designate the Windows build machine** — the plan assumes a dedicated Rektrs Windows 10/11 PC (`IQRS-DESKTOP-BUILDER`) on which Gate W0, the DPAPI spike and every MSI are built; it is needed from **week 1**, not from D3. (b) **The school's printer hardware** — the D5 confirmation is still outstanding: does the office actually have an 80 mm thermal printer (and which A4/card printers)? Printing is designed to work dialog-only until this is known, but D2's printing battery and the pilot need the real devices named.
